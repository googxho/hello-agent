# agent-v9 实验手册

> **7 个实验，每个 1~2 分钟。一个实验只测一个点。**
>
> 实验 2 是本版的主线：**改坏一个东西，看分数掉给看** ——
> 那就是「改了 prompt 不知道变好还是变坏」的答案。
>
> ⚠️ 手册里所有「你应该看到」都来自**真跑捕获**。
> 分数、耗时、token、回答措辞每次都会浮动 —— **看特征，别抠数字**。
> （例外：涉及固定用例的分数，我们就写实地标出来。）

**④ 关于「起点状态」—— 这一版的规则和以前不一样**

v9 **没有持久化**（不带 v4 的记忆），所以**对话本身**天然干净，不用 `LLM_PERSIST_ENABLED=0`。
但有两个目录会跨实验留下痕迹：

| 目录 | 留什么 | 影响谁 |
|---|---|---|
| `runs/` | 每次评估的运行记录 | 实验 2 起的 `--baseline latest` **就靠它** |
| `notes/` | `save_note` 写的笔记 | 实验 2 的「残留拦截」演示就靠它留下 `homework.md` |

所以每个实验都标了起点：🆕 = 全新开始 ／ ↩️ = **接着上一个实验**（多半是拿它的记录做基线）。
**按顺序做**，链条才连得上。

> 小注：手册里 `runs/` 后面的文件名带着**你那一次运行的时间戳** ——
> 和这里的对不上是正常的，看结构就行。

**⑤ 花费预告 —— 每卷末尾都会报账**

一次整卷（9 条用例）≈ **16 次调用 · 约 14k tokens · 约 2 分钟**（deepseek-flash 口径）。
全部 7 个实验做完大约 9 万 tokens。**每一卷的分数板最后一行就是真实账本** ——
这本身就是「可观测」的演示：花了多少，你当场就知道。

## 实验 2：改坏提示词——分数掉给看 ↩️ ⭐⭐⭐

**🎯 要感受什么**

**「变好了还是变坏了」有了答案。** 故意把 Agent 改坏，看尺子有没有反应。

**⏱ 2 分钟**

**起点** ↩️ 接着实验 1（`runs/` 里有基线，`notes/` 里有实验 1 生成的 homework.md / break.md）

**📋 步骤**

```bash
python main.py --eval --prompt prompts/system-degraded.md --baseline latest --tag degraded
```

✅ **你应该看到**（对比面板，节选）：

```
对比基线 runs/20260920-000408-run.json
  通过率    9/9 → 4/9（-5）
  提示词    db60ebd0 → ef17ddd4（变了）
  ✅ 新通过   无
  ❌ 新失败   calc-big、calc-decimal、time-today、save-note、multi-step
  ➖ 持平     4 条（4 通过 / 0 失败）
```

失败明细里（节选）两条特别值得看：

```
  save-note（问题：把「周五交作业」记成一条笔记，标题用 homework。）
    ✗ 调用 save_note —— 没有调用 save_note（这次实际调用：一个都没有）
    ✗ 生成文件 homework.md —— homework.md 存在，但不是这次写的（和跑之前一模一样）——
      很可能是上一次评估留下的残留。先清空资料目录（rm -rf …/notes）再跑，这条才代表真实能力

  calc-decimal（问题：3.11 乘以 7.62 等于多少？请保留两位小数。）
    ✗ 调用 calculator —— 没有调用 calculator（这次实际调用：一个都没有）
    回答开头：3.11 × 7.62 = 23.6982，保留两位小数为 **23.70**。…
```

**👀 看什么**

1. **`9/9 → 4/9（-5）`** —— 这两行数字，就是你以前只能靠感觉猜的东西
2. **「提示词 …（变了）」** —— 分数变化的第一嫌疑人被点名了（sha 指纹前后对照）
3. **save-note 的第二条红** —— 文件明明在，但判红：**「不是这次写的」**。
   残留文件想冒充战功，被拦住了
4. **calc 两条的红法** —— 回答开头里它心算**居然对了**（7006742 对、23.70 对），
   但 `tool_called` 依然判红

**💡 所以呢**

- ⭐ 这就是本版的正题：**改个东西 → 跑一次 → 差值 + 新失败清单**。
  以前你要「多聊几句、凭感觉」，现在是一行 `-5` 和五个具体名字
- **评估测的不止答案，还有过程**：心算对了照样红 —— 因为它绕开了
  「calculator 那把尺子」。这次侥幸算对，下次 `5678 × 9999` 就翻车
- **假通过比假红更毒**：这个「残留拦截」不是设计文档里憋出来的，
  是开发中真被耍了一次才补上的 —— 见 README 的「③ 如何验证它真的解决了」

**❓ 如果不一样**

- **分数没掉甚至满分**：先看「对比基线」行指的是不是实验 1 那份；
  再跑一次这一卷看看是否稳定（deepseek-flash 偶尔异常能扛）
- 一个额外的真实故事：这个「坏提示词」的**第一版写软了**（规则是「工具能免则免」），
  结果 **9/9 → 9/9，纹丝不动** —— 因为工具的 `description` 里印着
  「凡是涉及数字运算**必须**调用本工具」。**工具描述也是提示词**，
  软话压不住它。后来加了「**不要调用任何工具**」这种狠话，分数才掉下来。
  （这个发现本身就是一次「评估逼你想清楚变量」的实例。）

**⏱ 1 分钟**


# 第二组 · 制造能力损失

## 实验 4：拿掉计算器——能力损失也测得见 ↩️

**🎯 要感受什么**

提示词没动，动的是**能力本身**。尺子能不能分清「措辞变化」和「能力变化」？

**⏱ 1~2 分钟**

**起点** ↩️ 接着实验 3（基线 = 9/9 的 restore 记录）

**📋 步骤**

```bash
LLM_DISABLED_TOOLS=calculator python main.py --eval --baseline latest --tag no-calc
```

✅ **你应该看到**。开头的准考证多了一行（这是你要求的实验，它如实承认）：

```
│ ⚠ 已关闭工具：calculator（LLM_DISABLED_TOOLS 指定）——
│ 依赖它们的用例会失败，这正是你要看的
```

对比面板（节选）：

```
对比基线 runs/20260920-000452-restore.json
  通过率    9/9 → 7/9（-2）
  提示词    db60ebd0（没变）
  工具开关  无 → calculator（变了，LLM_DISABLED_TOOLS）
  ❌ 新失败   calc-big、calc-decimal
```

**👀 看什么**

1. **「工具开关 无 → calculator（变了）」** —— 凶手被直接点名。
   提示词没变、模型没变、温度没变，所以**不许说「波动」**
2. 两条红都是 `tool_called calculator` —— 而回答里它继续靠心算（还对了）

**💡 所以呢**

- 「可观测」不是「多打日志」，而是：**每个可能出现的变化，都有一个对应的证据位**。
  面板盯着四样东西：提示词 / 模型 / 温度 / 工具开关
- 这个设计是**被实验逼出来的**：最早的版本只要提示词没变就会写
  「只可能来自波动」——实验 4 当场打脸（分数是关工具搞掉的）。
  现在的规则：**四样都没变，才允许说「波动」**
- 这是全手册最重要的一课：**评估要能测出「能力」的变化**，
  而不只是「说法的变化」。你以后换模型、加工具、改门槛，都靠它

**❓ 如果不一样**

模型心算错得更多的话，失败明细会换一种红法：「回答里没有 7006742」。
两种红都算数 —— 一条用例可以同时对着「答案」和「过程」放哨。

# 第三组 · 从分数到原因

## 实验 5：单条重跑——分数指向问题，明细指向原因 ↩️

**🎯 要感受什么**

分数告诉你「哪条挂了」，明细告诉你「为什么挂」。调试时别整卷重跑，用 `--only`。

**⏱ 1 分钟**

**起点** ↩️ 任何时刻都行（这次故意带上坏提示词，制造一个「挂得清清楚楚」的样本）

**📋 步骤**

```bash
python main.py --eval --only time-today --prompt prompts/system-degraded.md --tag debug
```

✅ **你应该看到**（节选）——注意开头多出的那一行警告：

```
│ ⚠ 只跑 1 条（--only time-today）—— 这是调试版成绩，别当整卷用
...
  ✗ time-today     工具: 无 · 0/2 项检查过 · 1.9s

✗ 失败明细（1 条）：

  time-today（问题：今天是几号？现在是星期几？）
    ✗ 调用 get_current_time —— 没有调用 get_current_time（这次实际调用：一个都没有）
    ✗ 回答匹配 /星期[一二三四五六日天]/ —— 回答不匹配 /星期[一二三四五六日天]/｜
      回答开头：我没法确定当前的确切日期——我的记忆里没有实时时钟……
```

**👀 看什么**

1. 明细把「**期望什么**」和「**实际是什么**」并排放（铁律 7 的标准姿势）
2. 「实际调用：一个都没有」—— 一眼定位到「该调没调」，而不是「答得不好」
3. 单条调试只要 1 次调用、几百 tokens —— 整卷要 14k，**调试用单条，验收用整卷**

**💡 所以呢**

调试循环长这样：**整卷分数定位 → `--only` 重跑看明细 → 改重跑 → 整卷验证**。
小提醒：`--only` 的记录也会写进 `runs/`；下次对比时，面板会自己认出
「用例集不同」、只对比共同有的那些 —— 这是它的本职工作，不是报错。

**❓ 如果不一样**

想看它正常的样子：去掉 `--prompt` 再跑同一条，工具就会调起来。

## 实验 6：裁判也会坏——判定是一条会坏的链路 ↩️

**🎯 要感受什么**

「判定」不是免费的真理。它坏了，分数就是**假的** —— 而你要能分辨「谁坏了」。

**⏱ 2 分钟**

**起点** ↩️ 任何时刻都行

**📋 步骤（两连发）**

```bash
# 6a：把裁判逼到墙角（100 tokens 肯定写不完）
LLM_JUDGE_MAX_TOKENS=100 python main.py --eval --only judge-token --tag judge-trunc

# 6b：正常参数再来一次
python main.py --eval --only judge-token --tag judge-ok
```

✅ **6a 你应该看到**（失败明细节选）：

```
  judge-token（问题：像给完全不懂技术的朋友解释一样，讲讲大模型里的 token 是什么。）
    ✗ 裁判评判：解释通俗、有比喻或具体例子，没有堆砌术语；读者定位是完全的外行。
      —— 裁判的回答被截断：100 tokens 用光了还没写出结论（finish_reason=length）——
      这是判定环节的故障，不是模型答得不好。先按未通过记；把 LLM_JUDGE_MAX_TOKENS 调大再跑
    回答开头：打个比方就好懂了。**token 就是模型世界里的"文字积木"。** 想象你有一套乐高。…
```

✅ **6b 你应该看到**（节选）——裁判过了，而且给了理由：

```
  🧑‍⚖️ judge-token：裁判 PASS：回答用"字块""乐高积木"等比喻和具体例子解释 token，
  语言通俗，基本没有堆砌术语，适合完全外行理解。
```

**👀 看什么**

1. **6a 里回答本身是好的**（看「回答开头」：乐高比喻挺好）—— 坏的是裁判没电了
2. 失败原因**把锅分得清清楚楚**：「这是判定环节的故障，不是模型答得不好」+
   该拧哪个旋钮（`LLM_JUDGE_MAX_TOKENS`）
3. 6b 的裁判理由和你上次看到的**措辞不一样**（另一次运行写的是「切香肠、乐高和小纸条」
   或「模型眼里的字、吃小块、工作台桌面」）—— **判定稳定、语言浮动**

**💡 所以呢**

- 如果 6a 的报错只说「判定失败」，你八成会跑去改提示词 —— **修错了方向**。
  判定故障和模型故障必须分开报，这是评估的**归因能力**
- 实测数据（2026-09-19，deepseek-flash）：`max_tokens` 给 **100/150 → 3/3 次全空**；
  200 也不稳；**600 才稳**。所以默认值是 600 —— 不是拍脑袋，是撞出来的
- 裁判是「另一个模型的观点」：**标准是你写的、它自己也会飘、也要运维**

**❓ 如果不一样**

6b 偶尔也挂？先看理由原文，再决定是重跑还是调参数 —— 别急着信，也别急着改。

## 实验 7：同一份卷子，连考两次 ↩️

**🎯 要感受什么**

温度 0 的分数有多稳？以及：**别拿单次抖动当圣旨**。

**⏱ 2 分钟**

**起点** ↩️ 任何时刻（两次连跑自成一体）

**📋 步骤**

```bash
python main.py --eval --tag rerun-a
python main.py --eval --baseline latest --tag rerun-b
```

✅ **你应该看到**（对比面板节选）：

```
对比基线 runs/20260920-000543-rerun-a.json
  通过率    9/9 → 9/9（+0）
  提示词    db60ebd0（没变）
  ⏭ 提示词 / 模型 / 温度 / 工具开关都没变 ——
  分数变化只可能来自模型侧随机波动（温度 0 也不保证逐位复现）
  ✅ 新通过   无
  ❌ 新失败   无
  ➖ 持平     9 条（9 通过 / 0 失败）
```

**👀 看什么**

1. 两次都 9/9，**+0** —— 温度 0 + 固定用例，这次很稳
2. 但耗时和 token 每次都不一样（13,996 vs 你那次的实际值）——
   请求没有逐位复现这回事
3. 「⏭ …都没变」这行：系统明确告诉你**它找不到其他解释**

**💡 所以呢**

- 稳定的来源是配置：固定用例 + 温度 0 + 同样的提示词
- 但**别赌它逐位复现**：哪天看到 ±1 的抖动（某条用例的措辞影响了子串匹配、
  裁判换了说法），先想波动，再想「我是不是改坏了什么」
- 真正防退化靠的是**习惯**：改动前后各跑一卷，看差值；而不是记住某次的分数

**❓ 如果不一样**

这次就抖了 ±1？恭喜，你撞到了**评估的噪声** —— 把那一卷的 `--only` 明细看一下，
如果是「措辞差一个字」之类的假红，想想判据是不是可以放宽（比如正则别写太死）。

# 收尾：你把一把尺子带走了

这一版给你的不是新能力，是**判断力**：

```bash
python main.py --eval --baseline latest        # 改动前后，一眼看差值
python main.py --eval --only <id>              # 某条红了，单独看原因
python main.py --eval                          # 一卷全新的基线（比如换模型后）
```

三个习惯，请装进日常工作流：

1. **动手之前先留基线**（哪怕只是 `--tag 改动前`）
2. **动手之后立刻对比**（`--baseline latest`）
3. **分数掉了别慌**：`--only` 看明细 —— 是模型的锅、判据的锅、还是环境的锅（残留文件/裁判故障）
