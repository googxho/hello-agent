# hello-agent v9

> 从 v1 的**最小 Agent**重新出发，只加**一个**知识块：**评估与可观测**。
>
> 一句话说清这一版干的事：
>
> **把「感觉它变好了」变成「分数说它变好了」—— 让每一次改动都留下数字。**

---

## 🧪 先做实验，再看代码

这份 README 讲「为什么」。想先动手感受它，去看 **[EXPERIMENTS.md](EXPERIMENTS.md)** ——
7 个小实验、每个 1~2 分钟，全程是「制造破坏 + 看分数反应」。

最值得先做的两个（已经跑过，结果真实）：

| 实验 | 你会看到 |
|---|---|
| 改坏提示词，跑评估 | `通过率 9/9 → 4/9（-5）`，并列出**新失败**是谁 |
| 关掉计算器，跑评估 | `9/9 → 7/9（-2）`，对比面板直接指出「**工具开关**变了」|

## 每一版都回答四个问题

### ① 上一版遇到了什么具体问题？

其实不是「上一版」—— 是 **v6 以来一路攒下的旧账**，到 v8 收尾时再也躲不掉了：

**v7 的收尾清单原话：**

> 「旋钮四件套（门槛 / k / depth / top_k）：好结果依赖手工实验，没有系统的评估办法」
> 「『改了参数到底变好还是变坏』没法回答：目前全靠人肉看日志」

**v6 的一个实测（记录在案）**：同一句「我想让程序跑得更快」问两次 ——
一次它调用了 `search_notes`，一次它凭自己的知识答了一大篇。
你没有尺子，就分不清「这是波动」还是「这是退步」。

**v8 把地基铺到了最后一米**：输出变成机器可读的 JSON、批量表格能跑 ——
但那张表**能「读」，不能「判」**：「期望的答案该是什么、这一条算不算过」，
还是只能靠你的眼睛。

一句话：**没有评估，一切优化都是瞎猜。**

### ② 这一版引入什么最小概念？

> **一条评估回路：固定用例集 → 自动判定 → 分数 → 和上一次对比。**

```
用例集（9 条手写用例：问题 + 可自动判定的期望）
     │
     ▼
挨个跑一遍 Agent ──── 每条用例一个全新 Agent（互不污染）
     │                每次运行留下轨迹（trace）：调了哪些工具、参数、结果
     ▼
判定（两种口径）：
   · 规则判定：包含什么字、调没调工具、有没有生成文件  —— 免费、离线、可复现
   · 裁判判定（llm_judge）：语气、通俗度这类「写不成规则」的  —— 要钱、要校准
     │
     ▼
分数（通过率 + 分类统计 + 花费账本）+ 运行记录写进 runs/*.json
     │
     ▼
--baseline latest ──→ 「变好还是变坏」有了答案：
    通过率 9/9 → 4/9（-5） · 提示词 db60ebd0 → ef17ddd4（变了）
    ❌ 新失败 calc-big、calc-decimal、time-today、save-note、multi-step
```

**「最小」的边界**（刻意不做的，留给以后）：

| 没做 | 为什么先不做 |
|---|---|
| 数据集管理、多用户、并发跑分 | 9 条用例、单进程，够把「回路」这一个概念说透 |
| 统计显著性、置信区间 | 那是「分数噪声」的进阶课题，先学会看单次对比 |
| 在线监控 / trace 平台 | 先把「离线回归」做扎实（ECOSYSTEM 里讲了这两种派别） |
| **重试 / 压缩 / 记忆 / 检索 / 结构化输出** | ⭐ 见下 —— 本版从 v1 出发，**被测对象越简单，结论越干净** |

**为什么基于 v1、而不是接着 v8 长？**（这是有意的选择）

评估测的是「Agent 的行为」。如果被测对象身上挂着压缩、检索、重试……
一条用例挂了你得先排查：是模型的锅？压缩的锅？检索的锅？
这一版的目的是**学会测量**，所以把被测对象收回到最小 ——
这正是 v6 留下的老教训：「评估一个组件时，要把它单独拎出来测」。

### ③ 如何验证它真的解决了？

**离线验证**（`--selftest`，95 项断言，零 API Key、零花费）：

- 用例集加载的**每一种坏法**都有断言：坏 JSON 带行号、未知检查类型列可用清单、
  重复 id 说清「会对不上账」……
- 判定逻辑（含千分位/空格的归一化、残留文件拦截、裁判解析）逐条喂假数据测穿
- 对比逻辑：新通过 / 新失败 / 持平 / 用例集差异 / 「都没变」提示
- Agent 循环用**剧本客户端**重放（假替身第四次出场）：工具报错回灌、
  `MAX_ROUNDS` 兜底、用例间互不污染
- **日志质量本身被做成断言**（铁律 7）：比如「没用裁判时也要说一句『零额外调用』」

**真实运行验证**（全部是跑出来的，不是设计文档）：

| 做了什么 | 结果 |
|---|---|
| 干净基线跑一次 | `9/9（100%）· 17 次调用 · 14,303 tokens` |
| 换「坏提示词」再跑 + 对比 | **`9/9 → 4/9（-5）`**，新失败 5 条点名列出 |
| 改回默认提示词再跑 + 对比 | **`4/9 → 9/9（+5）`**，新通过 5 条点名列出 |
| 关掉 calculator 再跑 + 对比 | **`9/9 → 7/9（-2）`**，面板指出「工具开关 无 → calculator（变了）」|
| 同一份卷子连跑两次 | `9/9 → 9/9（+0）`，面板提示「都没变，只可能来自波动」|

⭐ 第三列才是关键：**故意制造的能力损失，尺子真的测出来了** ——
这就是 ROADMAP 里要求的「反例验证」：不会变差就说明评估没测到东西。

**这一版开发中亲手抓到的两个真 bug**（都变成了断言，值得单独说）：

1. **假通过**：`file_exists` 检查显示「副作用 ✓」——可那轮模型根本没调 `save_note`，
   `homework.md` 是**上一次评估的残留**。修法：跑之前给资料目录拍快照，
   文件必须是**本次运行新写出来的**才算数。
   （评估里最毒的错不是假红，是**假通过** —— 它给你分数，却什么都没发生。）
2. **裁判假红**：裁判模型偶尔返回**空内容**，排查发现 `max_tokens=200` 全被
   内部思考吃掉（`finish_reason=length`），一个字都没来得及说。修法：
   默认调到 600；并且失败时明说「**这是判定环节的故障，不是模型答得不好**」——
   否则你的失败清单会指向错误的嫌疑人。

### ④ 下一版的新痛点是什么？

这一版给了你一把尺子 —— 于是**第一个被测出来的系统性弱点**浮出水面：

- 看实验 2 的失败清单：5 条里有 4 条是「工具行为」挂掉；
  其中 `multi-step`（查时间 → 存笔记）**两步全挂**，是整卷最惨的一条。
  v9 的用例最多两步；再长呢？**你不知道，因为没有更长的用例能测。**
- 而「更长的用例」测的是另一个东西：**它会不会先把任务拆开、再一步步做** ——
  现在它是走一步看一步，两步以上就开始丢步骤。
- 另一个坑（评估自己带来的）：**手写 9 条用例，覆盖有限**；
  为分数调提示词，早晚会「对着考题复习」（过拟合）。
  用例集从哪来、怎么扩 —— 这是评估的长线课题，不是这一版能收干净的。

**→ 下一版方向：08 · 规划与任务拆解。**

用这把新尺子去回答：「先出计划再执行」到底有没有用、在哪类任务上有用。
（细节的起点 / 预计撞的墙 / 验证思路，见 ROADMAP.md 的 08 节。）

## 快速开始

```bash
myenv
cd agent-v9

# 0) 离线自检 —— 不需要任何 Key，不花钱
python main.py --selftest          # 95 项断言

# 1) 跑一次评估（要 API Key；9 条用例 ≈ 16 次调用 ≈ 14k tokens ≈ 2 分钟）
python main.py --eval

# 2) ⭐ 本版的正题：改点什么，再跑一次，和上一次对比
#    改提示词：直接编辑 prompts/system.md，或拿现成的「坏提示词」实验
python main.py --eval --prompt prompts/system-degraded.md --baseline latest

# 3) 只跑一条（某一类挂了，单独重跑、看失败明细）
python main.py --eval --only time-today --prompt prompts/system-degraded.md

# 4) 交互对话（和 v1 一样的最小 Agent；它不带记忆，退出即忘）
python main.py

# 5) 看配置从哪来、当前哪几项在生效
python main.py --config
```

`--eval` 的退出码（以后挂 CI 用）：`0` = 全过 · `1` = 有用例没过 · `2` = 跑不起来。

## 核心概念：一条评估回路

### 三个部件，各司其职

| 部件 | 在哪 | 干什么 | 设计要点 |
|---|---|---|---|
| **用例集** | `evals/cases.jsonl` | 一行一个用例：`id` + `prompt` + `checks` | 纯文本、手写、可改；格式坏了会告诉你**第几行、缺什么** |
| **判定** | `evaluator.py` | 每条期望 → 过/不过 + **人话理由** | 规则优先；判不了才请裁判 |
| **运行记录** | `runs/*.json` | 每次评估的全部事实（含每条的回答和工具轨迹） | 对比的基线就是它；出问题不用重跑就能回看 |

### 两种判定，两种性格

| | 规则判定（确定性） | 裁判判定（LLM-as-judge） |
|---|---|---|
| 例子 | 包含「7006742」、调用过 `calculator`、生成了 `homework.md` | 「解释是否通俗、有比喻」 |
| 成本 | 零 | 一次模型调用 |
| 复现 | 逐位可复现 | 会飘，要校准 |
| 风险 | 太死板 → **假红一片**（所以做了千分位/空格归一化） | 太模糊 → 裁判自己也在猜 |

**原则：规则能写的，别请裁判。** 裁判只用在「含义级」的标准上 ——
而且永远记住：**裁判的输出是「另一个模型的观点」，不是真相。**

### 一条用例的判定长什么样

失败时，输出必须回答四个问题（铁律 7）：
**哪条期望没过、期望是什么、实际是什么、下一步看哪里。**

```
  time-today（问题：今天是几号？现在是星期几？）
    ✗ 调用 get_current_time —— 没有调用 get_current_time（这次实际调用：一个都没有）
    ✗ 回答匹配 /星期[一二三四五六日天]/ —— 回答不匹配｜回答开头：我没法确定今天……
```

### 对比面板：只在这四样都没变时，才说「波动」

```
对比基线 runs/20260919-235258-restore.json
  通过率    9/9 → 7/9（-2）
  提示词    db60ebd0（没变）
  工具开关  无 → calculator（变了，LLM_DISABLED_TOOLS）   ← 凶手在这
  ❌ 新失败 calc-big、calc-decimal
```

（这个设计是实验 4 逼出来的：最早的面板只要提示词没变就说「只可能来自波动」，
结果打脸 —— 分数变化其实是关了工具造成的。**面板不许给假因果。**）

> 已知简化：面板跟踪「提示词 / 模型 / 温度 / 工具开关」四项；
> 其他参数（如 `LLM_JUDGE_MAX_TOKENS`）目前不在对比里 —— 用到时要自己留神。

## 裁判也需要校准

这是「判定」最难的一堵墙，v9 只做到**把问题摆到台面上**：

- **标准是你写的**：criterion 含糊，裁判就自己补全标准 —— 它不会替你纠错
- **它也会坏**：实测 `LLM_JUDGE_MAX_TOKENS=100` 时 3/3 次被截断（空回答），
  v9 的报错会明说「这是判定环节的故障，不是模型答得不好」并把旋钮名给你
- **它凭什么可信**：业内做法是「人工标一小批，和裁判对齐」；
  或者干脆别用绝对判定，改成「两份回答选更好的那份」（pairwise）——
  这些是评估的长线课题，先知道有这回事

## 日志怎么读

| 你会看到 | 意思是 | 下一步 |
|---|---|---|
| 开头的 `提示词：…（sha xxxx）` | 评估用的就是这份提示词 | 想换就 `--prompt`，或直接改文件 |
| `⚠ 只跑 1 条（--only …）—— 别当整卷用` | 这次是调试版成绩 | 想整卷跑就别带 `--only` |
| 行尾 `2/2 项检查过` | 这条用例的检查全过 | 1/2 就看下面的失败明细 |
| `🧑‍⚖️ judge-token：裁判 PASS：…` | 过了的裁判判定，把**理由**也给出来了 | 校准裁判时，它就是第一手材料 |
| 失败明细里的「实际调用：一个都没有」 | 模型没调工具 | 是提示词没说清？还是工具被关了？|
| 「不是这次写的（和跑之前一模一样）」 | 文件是**残留**，不是本轮产物 | `rm -rf notes` 再跑 |
| 「裁判的回答被截断」 | 判定环节故障，**不是**模型的锅 | 调大 `LLM_JUDGE_MAX_TOKENS` |
| 「⏭ 提示词 / 模型 / 温度 / 工具开关都没变」 | 没有明显成因 | 多半是真波动，看趋势别抠单次 |
| 「⏭ 没有用例需要模型判定」 | 这卷一分钱判定费都没花 | 正常 |
| 「⚠ 用例集不同（只对比了共同有的 1 条）」 | 拿单条调试版和整卷比了 | 想干净对比就两次都用整卷 |

## 常见问题

**Q：`--eval` 报「评估要真的调用模型，没有 Key 跑不了」**
仓库根 `.env` 里的 `LLM_API_KEY` 没填。没有 Key 也可以先跑 `--selftest`（全离线）。

**Q：用例集报错「第 3 行不是合法 JSON」**
`evals/cases.jsonl` 每行必须是一个完整 JSON、不能换行断开。按行号去看那一行。

**Q：`--baseline latest` 说「没有对比基线」**
`runs/` 里还没有上一份记录 —— **这次就是第一份基线**。下次再跑加上它即可。

**Q：分数和我预期不一样，是不是评估坏了？**
先看失败明细的「理由」——每条检查都写了「实际是什么」。
最常见的三种：模型没调工具（提示词问题）、文件是残留（清 `notes/`）、
裁判故障（看它的报错原文）。

**Q：`--only` 的记录会不会污染 runs/？**
会，它也是一份正式记录。想避免混淆：给它 `--tag debug` 起个名字，
或者用 `--baseline 具体文件` 指到你要比的那一份。

**Q：评估一次花多少钱？**
9 条用例 ≈ 16 次调用 ≈ 14k tokens（deepseek-flash 口径，约两分钟）。
每卷结尾都会报账 —— 这就是「可观测」的日常。

**Q：为什么交互对话没有记忆？**
本版故意从 v1 出发（被测对象要简单）。要记忆/检索/结构化输出，去看 v2~v8。

## 动手练习

按难度排序：

1. **加一条你自己的用例** —— 在 `evals/cases.jsonl` 追加一行，
   比如要求回答必须提到某个词，跑 `--eval` 看它过不过。
2. **把判据改错，看它变红** —— 把 `calc-big` 的期望值改成 `1234567`，跑 `--eval --only calc-big`。
   你会看到「分数只反映你写下的判据」—— 判据错了，评估就是误导。
3. **给 `save-note` 加一条交叉核对** —— 除了「生成了文件」，
   再检查文件**内容里**有没有出现「交作业」（提示：模仿 `file_exists` 写一个新的检查类型）。
4. **扩到长任务** —— 写一条 3~4 步的用例（比如「问时间 → 存笔记 → 说出笔记得标题」），
   跑几次，看看它丢步骤的概率 —— 这就是下一版（规划）要治的病。
5. **把评估挂到自动化里** —— 用退出码（0/1/2）接一个 git hook 或 CI：
   prompt 改动必须让评估不退化，才算数。

## 这个版本没带什么

**不是退化，是刻意**：v9 想教「测量」。被测对象身上挂着太多东西，
出问题时分不清是谁的锅。所以这一版只搬来了 v1 的最小 Agent：

| 你能想到的能力 | 在哪一版 | v9 |
|---|---|---|
| 上下文管理 / 压缩 | v2 / v3 | ✗ 不带（评估单条用例，用不到）|
| 持久化记忆 | v4 | ✗ 不带（每条用例本来就该从零开始）|
| 检索 / 向量 / 混合 | v5 / v6 / v7 | ✗ 不带 |
| 结构化输出 | v8 | ✗ 不带（判定直接读回答文本，够用）|
| **评估与可观测** | **v9** | ✅ 本版的正题 |

等评估这把尺子稳了，**再把复杂能力搬回来量** —— 那才是它发挥价值的地方。
