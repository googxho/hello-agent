# agent-v4 实验手册

> **「它记得住吗」这件事，光读代码感受不到 —— 要亲手关掉再打开。**
>
> 这一版的实验分三组：
>
> 1. **感受新能力**（关掉终端再打开，它还记得你）
> 2. **亲手破坏它**（把文件改坏、删掉、关掉开关 —— 看它怎么活下来）
> 3. **感受边界**（存档、清空、写盘成本、长对话）

---

# ⭐ 开始之前（必读，5 分钟）

**这一节把「怎么把 Agent 跑起来」讲一遍。**
后面的每个实验，都从这个状态出发 —— 所以请先把这一节做完，别跳。

### 0.1 打开一个终端

**在 VS Code 里按 `Ctrl + `` `（反引号，键盘左上角、`Esc` 下面那个键）。**

✅ 你应该看到：窗口底部弹出一个终端面板，光标在闪，等待你打字。

> 💡 面板已经开着？那就再按一次同样的键 —— 它是切换显示/隐藏的。

### 0.2 激活虚拟环境

在这个终端里，敲下面这行，然后回车：

```bash
myenv
```

✅ 你应该看到：命令行提示符**前面多出 `(myenv)`** 字样，像这样：

```
(myenv) a123@kukiMacBook-Pro hello-agent %
```

❓ **如果提示 `command not found: myenv`**：这个别名只在交互式 shell 里生效，
改用全路径（效果完全一样）：

```bash
source /Users/kuki/work/claude-code/jupyterlab/myenv/bin/activate
```

### 0.3 进入版本目录

敲下面两行，每行回车一次：

```bash
cd /Users/kuki/homework/hello-agent/agent-v4
pwd
```

✅ 第二行的输出应该是：

```
/Users/kuki/homework/hello-agent/agent-v4
```

**如果这里不对，后面全部会错** —— 所以先确认一下。

### 0.4 先跑一次自检，确认环境没问题

```bash
python main.py --selftest
```

✅ 最后一行应该是 `✓ 全部 69 项断言通过`。

❓ **如果报 `ModuleNotFoundError`**：说明 0.2 步的虚拟环境没激活成功，回去重做。
❓ **如果有几项 ✗**：把失败的项发出来，别继续 —— 后面的实验都会受影响。

> 💡 这一步**不需要 API Key，也不花钱**，还会顺便告诉你会话文件在哪 ——
> 它跑测试用的是系统临时目录，**碰都不碰**你真实的 `session.json`。

### 0.5 Agent 里面能敲的几个命令

启动程序后（下面实验里会教），在 `你 >` 提示符后面可以敲这些：

| 命令 | 作用 |
|---|---|
| `/context` | 看上下文占用了多少 token、压缩过几次 |
| `/summary` | 看摘要原文（它压缩出来的「长期记忆」）|
| `/session` | 看磁盘上那个会话文件的真实情况 |
| `/reset` | 清空对话历史（**v4 会连磁盘文件一起删**）|
| `/exit` | 退出程序 |

⚠️ **这些是敲给 Agent 的，不是敲给 shell 的** —— 注意看提示符是
`你 >`（Agent）还是 `(myenv) ... %`（shell）。

### 0.6 怎么退出程序（后面每个实验都要用）

在 `你 >` 提示符后面，敲：

```
/exit
```

✅ 你会看到 `再见 👋`，然后回到 shell 提示符（`(myenv) ... %`）。

> 也可以按 `Ctrl + D`（发送 EOF），效果一样。

### 0.7 每个实验开头的那句「前置」

后面每个实验的开头都会有一行：

> **前置**：终端已开 · `(myenv)` 已激活 · 当前目录是 `agent-v4`（见 0.1~0.3）

它的意思是：**动手之前，先确认这三件事**。
如果你中间关过终端、或者切过目录，就回到 0.1~0.3 重做一遍。

### 0.8 出问题了去哪看

| 症状 | 先检查这个 |
|---|---|
| `command not found: python` | 虚拟环境没激活 → 0.2 |
| `No such file or directory: main.py` | 目录不对 → 0.3，敲 `pwd` 看一眼 |
| Agent 说「没有 API Key」 | 仓库根的 `.env` 里 `LLM_API_KEY` 填了没 |
| 其他报错 | 把完整报错发出来，别猜 |

# 第一组 · 它记得住了

## 实验 1：关掉终端再打开，它还记得你 ⭐⭐⭐

**🎯 要感受什么**

这是 v4 存在的全部理由：**上一个进程里发生的事，下一个进程还能接上。**

v3 里，这一步的结局是它客气地告诉你：「如果你之前是在别的会话里设定的暗号，我这边看不到。」

**⏱ 大约 4 分钟**

**📋 动手步骤**

> **前置**：终端已开 · `(myenv)` 已激活 · 当前目录是 `agent-v4`（见 0.1~0.3）

---

**第 1 步：删掉旧会话，从干净状态开始**

```bash
rm -f session.json
```

✅ 应该**什么输出都没有** —— 这就代表成功了。
（`rm -f` 的特点是：删不到也不报错。）

---

**第 2 步：启动程序**

```bash
python main.py
```

✅ 你应该看到横幅（节选）：

```
╭────────────────────────────── Agent ───────────────────────────────╮
│ hello-agent v4 · 记得住、也存得下的最小 Agent                      │
│ 模型 deepseek-flash  @  https://api.deepseek.com                   │
│ 上下文预算 4,000 tokens · 最近 8 条受保护                          │
│ 记忆压缩 开 · 摘要模型 deepseek-flash · 摘要上限 500 tokens        │
│ 持久化 开 · 每轮自动存盘 → session.json                            │
│                                                                    │
│ /context 看上下文    /summary 看摘要    /session 看会话文件        │
╰────────────────────────────────────────────────────────────────────╯
📂 还没有会话文件（第一次运行就会有）→ /Users/.../agent-v4/session.json
```

📌 **注意最后那一行** `📂 还没有会话文件` —— 因为第 1 步刚删掉。
**它不是报错，是「如实告诉你现在的状态」。**

---

**第 3 步：埋下一个暗号**

在 `你 >` 后面敲这句（一整句，然后回车）：

```
请记住这个暗号：紫色河马。只回复「好的」两个字，不要调用工具。
```

✅ 你应该看到：它回一句「好的」，然后出现**本次实验最重要的一行**：

```
💾 已存盘 → session.json（308 B · 1.3 ms） —— 之后每轮都会自动存，不再重复提示；/session 可随时查看
```

📌 **这一行只出现一次**（第一轮存盘时），之后就不刷屏了 ——
不是没存，是**每轮都在存、懒得重复说**。想看随时敲 `/session`。

---

**第 4 步：退出程序**

敲 `/exit` 回车。

✅ 你应该看到 `再见 👋`，回到 shell 提示符。

---

**第 5 步：完全关掉这个终端** ⬅️ 别跳这一步

点终端面板右上角的**垃圾桶图标**（或者敲 `exit` 回车）。

✅ 终端面板消失 / 提示符变成「已终止的进程」字样。

> 为什么要关终端？因为要让你**真切地看到**：那个 Python 进程已经彻底没了。
> 它的内存、它的变量，全都随着这次关闭蒸发掉了。

---

**第 6 步：重新开一个终端，重新准备**

```bash
myenv
cd /Users/kuki/homework/hello-agent/agent-v4
```

✅ 提示符前面又有 `(myenv)`，`pwd` 显示目录正确。

---

**第 7 步：再次启动**

```bash
python main.py
```

✅ **这次横幅下面那一行变了**：

```
📂 已恢复上次会话 · 2 条消息 · 文件保存于 8 秒前
```

📌 **这一行就是 v4 的全部意义。** 全新的进程，全新的内存 ——
但它从磁盘上把上一场对话捡了回来。

---

**第 8 步：问它暗号**

```
暗号是什么？
```

✅ 它应该答出 **「紫色河马」**。

---

**👀 你应该看到的关键行**

| 阶段 | 你会看到 |
|---|---|
| 第一次启动 | `📂 还没有会话文件（第一次运行就会有）→ …/session.json` |
| 答完第一句 | `💾 已存盘 → session.json（308 B · 1.3 ms）` |
| 第二次启动 | `📂 已恢复上次会话 · 2 条消息 · 文件保存于 8 秒前` |
| 问暗号 | **「紫色河马」** ✅ |

**❓ 如果不一样**

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 第二次启动还是显示「还没有会话文件」 | 第 4 步退出时没等到存盘 / 或者第 1 步删过之后没再聊 | 重做第 2~4 步，确认看到 `💾 已存盘` |
| 显示「已恢复」但答不出暗号 | 它可能真的没记住（模型问题） | 敲 `/context` 看消息条数是否 ≥ 5 |
| 报 `JSONDecodeError` | 文件坏了（很少见） | 走实验 3 的流程，顺便体验一下容错 |

**💡 所以呢**

`messages` 和 `summary_text` 以前只活在内存里。现在它们在磁盘上有一份 ——

```
内存里的状态 ──写─→ session.json ──读─→ 内存里的状态
```

**概念就这么一句话。** 但真正值钱的东西在实验 3 —— 磁盘上的东西会坏，
程序必须能扛住。那才是这一版的知识量。

## 实验 2：磁盘上那个文件里到底存了什么 ⭐⭐

**🎯 要感受什么**

持久化不是黑盒。**那个文件是给人读的**（我们特意选了缩进过的 JSON）。

**⏱ 大约 3 分钟**

**📋 动手步骤**

> **前置**：终端已开 · `(myenv)` 已激活 · 当前目录是 `agent-v4`（见 0.1~0.3）

---

**第 1 步：直接读文件**

```bash
cat session.json
```

✅ 你应该看到（内容取决于你刚才聊了什么）：

```json
{
  "version": 1,
  "saved_at": "2026-09-17T23:12:53",
  "summary": null,
  "messages": [
    {
      "role": "user",
      "content": "请记住这个暗号：紫色河马。只回复「好的」两个字，不要调用工具。"
    },
    {
      "role": "assistant",
      "content": "好的"
    }
  ]
}
```

**逐段看这四个字段：**

| 字段 | 是什么 |
|---|---|
| `version` | 格式版本号 —— 以后结构变了靠它判断能不能读（见实验 3）|
| `saved_at` | 最后一次写盘的时间 |
| `summary` | 压缩出来的长期记忆。**现在还没有**（那是 null 的意思）|
| `messages` | 会话里的消息，原样存的 |

---

**第 2 步：注意到「少了什么」**

📌 **文件里没有系统提示词**（那句「你是一个可以通过调用工具来完成任务的助手…」）。

因为**提示词属于代码，不属于会话**。这样以后你改了提示词，老会话也能用上新版。

✅ 自己验证一下：

```bash
grep -c "可以通过调用工具" session.json
```

如果输出是 `0`，说明提示词确实没被存进去。

---

**第 3 步：启动程序，看「内存里」和「磁盘上」的差别**

```bash
python main.py
```

然后敲：

```
/session
```

✅ 你应该看到：

```
文件路径  /Users/kuki/homework/hello-agent/agent-v4/session.json
大小      308 B
最后写入  2026-09-17 23:12:53（1 分钟前）
内容      2 条消息 · 还没有摘要

（内存里当前有 3 条消息 —— 下一轮结束时会再存一次）
```

📌 **注意最后一行的括号**：内存里 3 条，磁盘上 2 条 ——
差的那 1 条正是你刚敲的 `/session` 之前…… 嗯，其实差的是**当前这一轮**。

**这行括号是刻意留的：磁盘上的和内存里的，不是一回事。**

**👀 你应该看到的关键行**

`/session` 的输出里有四行基本信息 + 一行「内存 vs 磁盘」的对照。

**❓ 如果不一样**

| 现象 | 原因 |
|---|---|
| `cat: session.json: No such file or directory` | 还没聊过天（文件是第一轮答完之后才生成的）→ 先做实验 1 |
| 文件里 `summary` 不是 null | 你聊得够久，已经触发过压缩了 —— 这是好事，去 `/summary` 看看 |

**💡 所以呢**

**格式选择是个真实的工程决策。** 这里选了 JSON，理由只有一个：

> 学习阶段，**「人能看懂」比「省空间」重要得多。**

生产环境你可能会换成 SQLite（能查、能索引）、或者二进制格式（快、小），
但那是**在你看清数据长什么样之后**才该做的决定。

# 第二组 · 亲手把它拆掉

> **要证明一个能力真的在起作用，最好的办法是把它拿掉、或者弄坏。**
>
> 这一组三个实验，都是让你「破坏」点什么 —— 然后看它怎么活下来。

## 实验 3：把会话文件改坏 ⭐⭐⭐

**🎯 要感受什么**

磁盘上的东西**你控制不了**：可能被手改坏、可能被别的程序截断、可能旧版本写的。

**一个能上生产的程序，必须能对着一堆烂数据说：我读不了，但我还能跑。**

**⏱ 大约 5 分钟**

**📋 动手步骤**

> **前置**：终端已开 · `(myenv)` 已激活 · 当前目录是 `agent-v4`（见 0.1~0.3）

---

**第 1 步：先确认有一个正常的会话文件**

```bash
ls -l session.json
```

✅ 显示文件大小（比如 308 字节）。
❓ **如果文件不存在**：先做实验 1，或者随便聊一句让它生成。

---

**第 2 步：亲手把它写坏**

```bash
echo '{ 这根本不是合法的 JSON' > session.json
cat session.json
```

✅ 文件内容变成了一行垃圾：

```
{ 这根本不是合法的 JSON
```

---

**第 3 步：启动程序，看它怎么反应**

```bash
python main.py
```

✅ 你应该看到**黄色的**一行：

```
📂 会话文件读不了（JSONDecodeError），已把它改名备份到 session.json.corrupt，这次从零开始
```

📌 三件事同时发生了：

1. **它没崩** —— 正常进入对话，横幅照常显示
2. **它给了原因** —— `JSONDecodeError`（而不是「出错了」）
3. **它给了去处** —— 坏文件被改名成 `session.json.corrupt`

---

**第 4 步：验证坏文件真的还在**

新开一个终端（或者先退出程序），敲：

```bash
ls -l session.json*
```

✅ 你应该看到两个文件：

```
-rw-r--r--  ...  session.json.corrupt     ← 你写坏的那份，被改名保留了
-rw-r--r--  ...  session.json             ← 程序重新开始写的新的
```

📌 **它没有删掉你的数据** —— 只是挪到旁边去了。
因为里面可能是你聊了一下午的内容，**程序没有资格替你做主扔掉它**。

---

**第 5 步：手动救回数据（如果那是真的）**

万一那个坏文件里有你要的内容，你可以直接打开它看：

```bash
cat session.json.corrupt
```

（这里内容是我们故意写的垃圾，真实场景里你能从里面捞出消息。）

---

**第 6 步：再试一种坏法 —— 一个合法的 JSON，但结构不对**

```bash
echo '{"version": 1, "messages": "我不是一个列表", "summary": null}' > session.json
python main.py
```

✅ 应该看到类似的黄色提示，但原因不同：

```
📂 会话文件里的 messages 不是消息列表，已备份到 session.json.corrupt，这次从零开始
```

📌 **注意它检查的是「结构」而不只是「能不能解析」** ——
因为一个能解析但结构错误的文件，会让程序在后面某个莫名其妙的时刻炸掉。

**👀 你应该看到的关键行**

| 你干了什么 | 它的反应 |
|---|---|
| 写进去一段非 JSON | `会话文件读不了（JSONDecodeError），已把它改名备份到 …` |
| 写进去结构不对的 JSON | `会话文件里的 messages 不是消息列表，已备份到 …` |
| （两种情况下）| **程序照常启动，能继续聊天** |

**❓ 如果不一样**

| 现象 | 原因 |
|---|---|
| 程序真的崩了（抛异常退出） | 那是 bug，请记录下来 —— 容错是这一版的底线承诺 |
| 没看到 `.corrupt` 文件 | 检查你敲的是 `ls -l session.json*`（星号不能少）|

**💡 所以呢**

去看 `storage.py` 里 `load_session()` 的这段：

```python
try:
    raw = path.read_text(encoding="utf-8")
    data = json.loads(raw)
except (OSError, json.JSONDecodeError) as exc:
    backup = _quarantine(path)          # 改名备份，不是删除
    return LoadResult(status="corrupt", note=f"...已备份到 {backup.name}，这次从零开始")
```

**任何异常都不许上抛** —— 而是降级成一个明确的状态。

读盘的结果被归成四种状态，每一种都有一句给人看的说明：

| 状态 | 什么时候 | 程序怎么办 |
|---|---|---|
| `restored` | 文件正常 | 恢复会话 |
| `missing` | 文件不存在（第一次运行）| 从零开始 —— **这是正常的，也要说一句** |
| `corrupt` | 解析失败 / 结构不对 | **改名备份** + 从零开始 |
| `future_version` | 更新版本的程序写的 | 不敢乱读，**保持原样** + 从零开始 |

> **「出错的时候怎么办」，比「正常的时候怎么办」更能定义一个程序的质量。**
> 正常路径决定它有多好用，出错路径决定你敢不敢用它。

## 实验 4：关掉持久化 ⭐⭐

**🎯 要感受什么**

**同一个 Agent、同一段对话**，只关掉持久化开关 —— 它立刻变回 v3 那个「陌生人」。

**⏱ 大约 4 分钟**

**📋 动手步骤**

> **前置**：终端已开 · `(myenv)` 已激活 · 当前目录是 `agent-v4`（见 0.1~0.3）

---

**第 1 步：清掉旧文件**

```bash
rm -f session.json session.json.corrupt
```

---

**第 2 步：带着开关关闭启动**

```bash
LLM_PERSIST_ENABLED=0 python main.py
```

✅ 横幅里会出现**红色**的一行：

```
持久化 已关闭 —— 退出就忘光
```

下面还有一行提示：

```
📂 持久化已关闭（LLM_PERSIST_ENABLED=0）：这次聊的不会写盘，退出即蒸发
```

---

**第 3 步：埋下和实验 1 一模一样的暗号**

```
请记住这个暗号：紫色河马。只回复「好的」两个字，不要调用工具。
```

✅ 它回「好的」。

📌 **注意：这次没有 `💾 已存盘` 那一行** —— 因为压根没写盘。
（这也是「没动作也要说话」的一种：横幅和启动行已经提前告诉你了。）

---

**第 4 步：退出、重开终端、再启动**

```bash
# 退出（在 Agent 里敲）
/exit

# 重开终端后再：
myenv
cd /Users/kuki/homework/hello-agent/agent-v4
```

顺便体会一下开关的设计 —— 它做了三件事：

1. **`LLM_PERSIST_ENABLED=0` 写起来就停**（不用改代码）
2. **横幅变红**，告诉你现在是「失忆模式」
3. **启动行说明白**「不会写盘」

> 一个开关如果只改变行为、不改变显示，那用户永远会怀疑自己开没开。
> 这是 v3 实验 6 教过的道理，v4 继续用。

## 实验 6：`/reset` 之后，磁盘真的干净了吗 ⭐⭐

**🎯 要感受什么**

持久化带来的第一个坑：**你有两份状态（内存 + 磁盘），它们会打架。**

**⏱ 大约 3 分钟**

**📋 动手步骤**

> **前置**：终端已开 · `(myenv)` 已激活 · 当前目录是 `agent-v4`（见 0.1~0.3）

---

**第 1 步：确认有一个非空的会话文件**

```bash
ls -l session.json    # 应该有几百字节
```

❓ 没有？先随便聊一句。

---

**第 2 步：启动，然后用 `/reset`**

```bash
python main.py
```

在 `你 >` 后面敲：

```
/reset
```

✅ 你应该看到：

```
已清空对话历史（摘要一起清掉）· 磁盘上的会话文件也删掉了
```

📌 **注意后半句** —— 它**同时**清理了内存和磁盘，而且**告诉了你**。

---

**第 3 步：验证磁盘**

先退出（`/exit`），然后：

```bash
ls -l session.json
```

✅ 应该报 `No such file or directory` —— 文件真的没了。

---

**第 4 步：见证「如果不删会怎样」**

想理解这个设计，可以自己模拟一下「只清内存、不删磁盘」的后果：

```bash
python main.py
# 聊一句，比如：你好
# 然后敲 /exit
# 让文件存在（如果刚才 reset 删了，这一句会重新生成它）
```

再想想：如果 `/reset` **只清内存**，会发生什么？

✅ 答案：

1. `/reset` 之后内存是空的，看起来一切正常
2. 但你继续聊一句 → **新一轮存盘把「空历史 + 这一句」写进文件**
3. 更糟的情况：`/reset` 之后你直接退出 → **文件还是旧的** → 重启后它又全想起来了

**你明明清了，它却记得** —— 这是最让人怀疑人生的 bug 类型。

**👀 你应该看到的关键行**

`/reset` 的回复里那半句 `· 磁盘上的会话文件也删掉了`。

**💡 所以呢**

> **只要你有「两份状态」，就一定会遇到它们不一致的时刻。**

这一版的处理很朴素：把「清空」定义成**一次覆盖两边的操作**，
并且**如实汇报每一步的结果**：

- 删到了：`磁盘上的会话文件也删掉了`
- 本来就没有：`磁盘上本来就没有会话文件`

（后者也是铁律 7：没做到的动作，也要说清楚原因。）

## 实验 7：看着会话文件一轮一轮长大 ⭐

**🎯 要感受什么**

**写盘的成本到底有多大**，以及一个反直觉的现象：文件不会无限增长。

**⏱ 大约 5 分钟**

**📋 动手步骤**

> **前置**：终端已开 · `(myenv)` 已激活 · 当前目录是 `agent-v4`（见 0.1~0.3）

---

**第 1 步：从干净状态开始**

```bash
rm -f session.json session.json.corrupt
python main.py
```

---

**第 2 步：聊五轮，每轮之后敲一次 `/session`**

在 `你 >` 后面依次敲（一句一次，**每句答完之后敲一次 `/session`**）：

```
1. 你好
2. 帮我算 12345 * 67890
3. 北京有哪些著名景点？简单说三个
4. 帮我算 999 * 111
5. 用一句话解释什么是「上下文窗口」
```

然后把每次 `/session` 里的 **「大小」那一行**记到下面的表里：

| 轮次 | 文件大小 | 消息条数 |
|---|---|---|
| 1 | | |
| 2 | | |
| 3 | | |
| 4 | | |
| 5 | | |

✅ 你应该看到：**大小和条数一起往上涨**。

---

**第 3 步：看看写盘有多快**

第一轮那条 `💾 已存盘` 里有个数字：

```
💾 已存盘 → session.json（308 B · 1.3 ms）
```

📌 `1.3 ms` —— **千分之一点三秒**。
一毫秒是什么概念？你眨一次眼大约 100~400 毫秒。

所以「每轮都写盘」几乎不花钱 —— **这就是为什么选「每轮存」而不是「退出时存」**。

---

**第 4 步（可选，但要开新终端）：看看压缩怎么影响文件大小**

如果你用的是很小的预算，聊久一点会触发压缩，然后再敲 `/session`：

```bash
# 在另一个终端里（先 myenv + cd agent-v4）
LLM_MAX_CONTEXT_TOKENS=500 LLM_KEEP_RECENT=4 python main.py
```

聊到出现 `🗜 第 1 次压缩`，然后 `/session`。

✅ 观察：**消息条数会骤降** —— 因为旧对话被压成了一条摘要。

📌 也就是说：**文件大小不会无限增长** —— v3 的压缩在管着上限。

**👀 你应该看到的关键行**

- `💾 已存盘 → session.json（308 B · 1.3 ms）`
- `/session` 里的 `大小` 和 `内容` 两行

**💡 所以呢**

两个结论：

1. **写盘很便宜**（毫秒级）→ 所以「每轮存」是划算的买卖。
   它防的是「聊了两小时，一不小心 Ctrl+C，全蒸发」
2. **文件不会无限大** → 因为 v3 的压缩在控制上下文，存的就是上下文

> ⚠️ 但注意：这是**上下文策略**的副产品，不是持久化自己做到的。
> 如果哪天你关掉压缩又狂聊，文件就会一直涨 —— 那时该回头看 v3。

| `/session` | `内容  N 条消息 · 摘要 X tokens` |
| 重启后 | `📂 已恢复上次会话 · N 条消息 · 含摘要 X tokens · …` |
| 问暗号 | **「紫色河马」** ✅ |

**❓ 如果不一样**

| 现象 | 原因 |
|---|---|
| 重启后没有「含摘要」几个字 | 第 3 步里摘要可能还没生成 → 回第 2 步多聊两轮 |
| 它答不出暗号 | 先 `/summary` 看看摘要里有没有暗号。**摘要里没有 = 压缩的问题（v3）**；摘要里有但答不出 = 恢复的问题（v4） |

💡 **上面那张排查表本身就是个好习惯**：出问题时，先判断是**哪一层**坏了。
分层清晰的价值，在排查的时候才真正体现出来。

**💡 所以呢**

**两版能力接上了：**

```
v3 压缩：把旧对话 → 摘要（信息不丢）
v4 持久化：把 [消息 + 摘要] → 磁盘（跨越进程）
```

所以现在的完整链路是：

```
你说的话 ──→ 上下文（v2 管预算）──→ 摘要（v3 压缩）──→ 磁盘（v4 持久化）
```

**每一版解决一个问题，但它们叠起来才是「一个有记忆的 Agent」。**
