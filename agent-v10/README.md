# hello-agent v10

> 从 v9 的**测量版**继续出发，只加**一个**知识块：**规划与任务拆解**。
>
> 一句话说清这一版干的事：
>
> **执行之前先让模型交一份「步骤清单」——把全局从它脑子里请出来，写在纸面上。**

## 每一版都回答四个问题

### ① 上一版遇到了什么具体问题？

**v9 是诊断书，不是处方。** 它量出的第一个系统性弱点摆在这里：

> 坏提示词下 `multi-step`（查时间 → 存笔记，**仅仅两步**）两步全挂，
> 是整卷 9 条用例里最先趴下的一类 ——
> 它在「走一步看一步」，任务一长就丢步骤。

但「一长就丢步骤」有一个尴尬的空白：**v9 的用例最多只敢写两步**。
「三步呢？五步呢？到底多长算长？」——不知道，因为没有更长的用例能测。

而且发现问题 ≠ 会解决。v9 的失败清单告诉你「工具行为挂了」，
但没回答「怎么让它别挂」。这一版来开处方。

### ② 这一版引入什么最小概念？

> **Plan-and-Execute：先出计划，再执行。**

```
用户任务
   │
   ▼
📋 规划调用（planner）——单独一次模型调用
   │   把任务拆成步骤清单，用 submit_plan 工具「交卷」
   ▼
计划消息 ——写进上下文（每一步执行时都能看到全局）
   │
   ▼
⚙️ 执行循环（v1 的老循环）——每完成一步
   │   模型调用 update_plan 打勾；进度就地更新
   ▼
回答
```

**三个零件**（都在为同一句话服务：*让每一步都看得见全局*）：

| 零件 | 干什么 | 落在哪 |
|---|---|---|
| `submit_plan` | 规划器「交卷」的通道 —— 工具即 schema（v8 的老思想） | `planner.py` |
| **计划消息** | 计划注入上下文；挂**在任务消息旁边**（不是在开头），每轮都在场 | `agent.py` |
| `update_plan` | 执行中打勾报进度 —— **不改变世界，只更新自己的账本** | `agent.py`（实例级工具） |

**「最小」的边界**（刻意不做的，留给以后）：

| 没做 | 为什么先不做 |
|---|---|
| 重规划（计划错了改计划） | 先量出「静态计划」的价值与边界，才知道重规划该解决什么 |
| 计划持久化 / 跨会话续作 | 那是 v4 的领域；本版连对话记忆都没有 |
| 计划给用户确认 | 人机协同的种子（知识块 10），先别抢跑 |
| 按复杂度决定「该不该规划」 | ⭐ 这一版故意**无条件规划**——简单任务也被拆，看它到底税多少（见 ③） |

**为什么基于 v9、而不是别的版本？**

v9 的尺子是这个项目的「元工具」：**没有它，你无法回答「规划到底让什么变好了」**。
所以 v10 = v9 的底盘一字不动（评估回路 / 用例集 / 对比面板全部保留），
只在执行链路前面加了规划。被测对象继续「最小」——没有记忆、没有压缩、没有检索，
这样分数里每一分变化都只可能来自规划。

**顺带把尺子也升了一级**（为长任务服务，不算第二概念）：

- 新检查类型 `file_contains`：不只看文件生成了没有，还看**写进去的内容对不对**
- 对比面板变量从 4 个变 5 个：新增「规划配置」——不然「有规划 vs 无规划」的
  分数变化会被面板说成「波动」，那就是假因果（v9 实验 4 的教训继续生效）

### ③ 如何验证它真的解决了？

**离线验证**（`--selftest`，**171 项断言**，零 API Key、零花费）：

| 组 | 覆盖 |
|---|---|
| ⑧ 规划 · 纯函数 | 解析 6 种坏计划（空/重复/超限/坏 JSON…）、渲染、标记的四类边界（越界/非法 status/重复/改状态） |
| ⑧ 规划 · Agent 集成 | 剧本重放整条链路；**降级三连**（不交卷 / 两次失败 / 网络断）；多轮替换；sabotage 的「模型不知情」保证 |
| ⑧ 规划 · 评估集成 | `file_contains` 全边界、计划序列化往返、对比面板第五变量、**七种日志文案**（铁律 7） |

（前 96 项是 v9 的原班人马——规划没让旧能力退化。）

**真实运行验证**（全部是跑出来的，不是设计文档）：

| 做了什么 | 结果 |
|---|---|
| 对照组：`LLM_PLANNING_ENABLED=0` 跑全卷 | `12/12` · 26 次调用 · 22,885 tokens |
| 规划组：默认配置跑全卷 + 对比 | **`12/12 → 11/12（-1）`** · 55 次调用 · 79,729 tokens |
| 拆开看成本 | 规划本身 10,362 tokens（13%）；其余涨幅来自 `update_plan` 的额外轮次 |
| 长任务三连（3/4/5 步） | **两组都全过** —— 3~5 步还不够让「无规划」丢步骤 |
| 八步挑战（手动 REPL，非卷面）| 无规划 **2/2 完成**；有规划 **3 次里 2 次中断**（见下） |
| 破坏实验 A：砍掉计划最后一步 | 分数**没掉** —— 模型从任务原文里补回了缺失的步骤 |
| 破坏实验 B：颠倒计划顺序 | 分数**没掉** —— 模型按任务原文的正确顺序执行 |

**这一卷的诚实结论**（比漂亮的数字重要）：

1. **规划的价值没有在分数上显现**——因为 v9 那个「multi-step 趴下」是
   *坏提示词实验*里的场景；提示词正常时，这套模型在 3~5 步任务上本来就稳。
   **规划的收益点可能在更长的任务/更复杂的依赖上，本卷测不到。**
2. **规划的代价是真实且可量化的**：调用的账单、被贴上每轮的上下文、
   一次任务多 2~3 倍的 token。
3. **还抓到一个「不该规划」的铁证**：`no-tool-paris`（「法国的首都是哪里？」）
   在无规划时满分，规划后被拆成 2 步、还调了两次 `update_plan` ——
   撞上「不调用任何工具」的检查，**-1 分就是这么来的**。
   简单任务上，规划是纯税。
4. **破坏实验给出了计划影响力的边界**：在「任务原文清晰完整」的前提下，
   计划是**位置优势**（把步骤放在近期注意力里），不是**信息优势**（原文里都有）——
   所以砍步/颠倒都能被原文兜住。计划真正不可替代的场景（超长任务、
   原文模糊、多轮后原文漂远）——正是 v2/v3/v5 那些「上下文管理」的领域。
5. ⭐ **8 步任务上抓到了「任务一长就出事」的第一个真实样本**（手动实验，样本小）：
   同一个八步任务，无规划 2/2 干净完成；有规划 3 次里 2 次**中断**——
   模型在后半段输出了原始的工具调用语法文本（`<｜｜DSML｜｜…>`）而不是真正的
   tool_calls，循环把它当成「最终回答」，任务提前结束。
   原因不确定（规划版轮次翻倍是嫌疑，不是定论）——但妙的是：
   **中断位置被计划账本精确记录**（「8 步：4 完成 / 4 未标记」）——
   分数没赢，但「哪里断的」从此可查。这是计划的可观测性价值，也是下一版的火种。

### ④ 下一版的新痛点是什么？

这一版最大的发现是「**计划做出来之后，没有人对它负责**」：

- **计划是死的**：执行到第 3 步发现「第 5 步根本不成立」——静态计划不会改，
  要么硬着头皮做，要么推翻重来。而**改计划的前提，是系统先要知道「当前进展和计划对不上」**。
- **进度靠自觉**：`update_plan` 想调才调；模型不调，计划就停在 0/N——
  没有任何机制发现「它偏了」。
- 顺带的欠账：简单任务被无条件规划（本卷 -1 分那个案例）。

看出来了吗——这三个坑指向同一件缺失的能力：**自我检查**。

**→ 下一版方向：09 · 反思与自我修正（Reflexion）。**

用它来回答：「跑完一步先检查再继续」到底有没有用？「错了能自己发现吗？」
（细节的起点 / 预计撞的墙 / 验证思路，见 ROADMAP.md 的 09 节。）

## 快速开始

```bash
myenv
cd agent-v10

# 0) 离线自检 —— 不需要任何 Key，不花钱
python main.py --selftest          # 171 项断言

# 1) 交互对话（默认带规划）—— 看它先交计划、再一步步打勾
python main.py
#    试试：算一下 12 × 34，再把结果记成笔记，标题用 dozen

# 2) 对照实验：关掉规划，同一句话再来一次
LLM_PLANNING_ENABLED=0 python main.py

# 3) 用尺子量：先跑对照组，再跑规划组做对比
rm -rf notes runs
LLM_PLANNING_ENABLED=0 python main.py --eval --tag no-plan
rm -rf notes
python main.py --eval --tag plan --baseline latest

# 4) 破坏实验（REPL 里做，见 EXPERIMENTS.md 实验 4/5）

LLM_PLAN_SABOTAGE=reverse python main.py
LLM_PLANNER_MODEL=no-such-model python main.py
```

`--eval` 的退出码沿用 v9：`0` 全过 / `1` 有没过 / `2` 跑不起来。

## 设计解说（几个想清楚了的地方）

### 计划消息为什么挂在「任务旁边」，不是最上面？

v3 的摘要固定在 index 1（最上面），因为它是「历史」。计划不一样——它是「马上要做的事」：
注意力对上下文中间/开头的内容会变淡（*Lost in the Middle*），所以计划要
**离执行现场最近**：挂在任务消息之后、执行消息之前。实测那条 messages 形状：

```
system → user → 【任务计划】(system) → assistant/tool 执行序列…
```

多轮对话里，旧任务的计划会被撤下（它已完成使命），新计划替换进来——
**上下文里永远只有一份「当前任务」的计划**。

### `update_plan` 为什么不是普通工具？

普通工具（calculator / save_note）**改变外部世界**，注册在全局表里；
`update_plan` **只更新 Agent 自己的账本**（当前计划的勾选状态），
所以它是**实例级工具**：

- 只在「确实有活跃计划」时才出现在工具清单里（模型看不到用不上的工具）
- 实现直接挂在 Agent 实例上——不是全局注册表（两个 Agent 实例的计划互不干扰，
  评估里每条用例一个 Agent，天然隔离）
- 三种边界都有人话回执：越界步号 → 「编号以计划为准」；乱写 status →
  「只能是 done 或 failed」；重复标记 → 「已忽略」。**错误回灌给模型自己纠正**（v1 老机制）

### 规划失败为什么必须降级？

规划是「增强」，不是「主流程」。所以 v10 延续 v3 起的降级哲学：

- 模型不交计划 / 计划不合法 → 重试（默认 2 试）
- 重试也不行 / 网络断 → **退回无规划执行**，理由记进 `run.plan_error`，
  **对话一个字都不受影响**

实测的降级日志（`LLM_PLANNER_MODEL=no-such-model`）：

```
⚠ 规划失败：规划调用失败：BadRequestError: …400… —— 已退回无规划执行（检查 LLM_PLANNER_MODEL / 网络？）
```
——报告里连「该拧哪个旋钮」都给了。

### 「你看到的 = 模型看到的」

计划渲染文本就是注入上下文的原文——勾选状态、进度行，日志和上下文同款。
`update_plan` 的每一次调用都会在交互模式实时打印（工具实况），
报账行也会显示「另有规划 1 次 · +897 tokens」。

## ⚠️ 诚实的已知问题（这一版自己承认的）

1. **无条件规划，简单任务被税**（-1 分的元凶）：纯问答也被拆步骤 + 打勾。
   分流（按复杂度决定要不要规划）是明确的下一步欠账。
2. **计划文本贴在每一轮请求里**：3~5 步的计划约 200~300 tokens，
   执行轮次越多，这个成本乘得越大。
3. **`update_plan` 让轮次变多**：一次标记可能占掉一整轮对话——
   实测全卷调用次数从 26 涨到 55，很大一部分是它。
4. **长任务上见过「原始工具语法泄露」型中断**：模型输出 `<｜｜DSML｜｜…>` 文本
   而不是工具调用，循环误当成最终回答 → 任务静默半途而废（8 步挑战 3 次里 2 次；
   **样本小，且可能与具体模型/服务端有关，别当定律**）。
5. **进度是「自觉」的**：模型不调 `update_plan`，计划就停在 0/N，
   没有机制发现异常（下一版的正题）。
6. **「计划 vs 任务原文」谁说了算**：reverse 破坏实验里模型按原文执行——
   我们只知道「原文赢了这一局」，还不知道条件变化时会怎样。
