# 10 · 流式与人机协同

> **Streaming & Human-in-the-Loop**

> **一句话**：把「黑盒跑五分钟」变成「实时直播 + 随时叫停 + 关键点要签字」。
>
> **它治什么病**：等半天没反应（不知道它在干嘛、还活着吗）；
> 中途没法干预（方向错了，跑到头才发现 —— 而后果已经发生）。

📌 **本页回答四个问题**：

1. **为什么会有这个概念**——长流程 Agent 的「时间结构」出了什么问题？（问题）
2. **主流怎么解决**——流式传输、中断、审批闸门的来龙去脉（方案）
3. **为什么是这么解的**——感知延迟、不可逆性、代价不对称（原理）
4. **还有什么别的路**——SSE vs WebSocket、全自动 vs 分级授权（对比）

---

## 一、这个问题从哪来

### 1.1 两个具体的痛点（任何 Agent 用户都感受过）

**痛点一：等半天没反应。**

v9 跑一次评估要 2 分钟 —— 还好，那是命令行工具，你会等。
但交互场景完全不一样：你问一个需要 3 次工具调用的问题，
界面上**什么都没有发生**。10 秒、20 秒……
你不知道它是在思考、卡死了、还是在偷偷烧钱。

**痛点二：中途没法干预。**

它第 1 步就把你的需求理解反了，然后在错误方向上勤勤恳恳走了 9 步。
你眼睁睁看着（假设你能看到）它把一份报价单越算越离谱 ——
但你插不上话，只能等它「做完」再从头来。而这 9 步的 token 已经烧掉了。

### 1.2 根子在哪：Agent 的「时间结构」和传统软件不一样

传统软件的交互模型是**请求-响应**：点一下，几百毫秒内给你结果。
而 Agent 是**长流程 + 多步骤 + 多工具**的运行体：

```
一次「提问」内部，可能是：想 3 秒 → 调工具 5 秒 → 想 4 秒 →
调工具 8 秒 → 改方案 3 秒 → 再调工具 6 秒 → 写答案 10 秒
```

- 对用户：这段时间是**全黑**的；
- 对系统：这里面有大量**可以且应该**给用户的介入点。

**批处理思维（一次性跑完再展示）用在 Agent 上，同时牺牲了体验和安全性。**
这个知识块要解决的就是：把 Agent 从「黑盒批处理」改造成
「透明直播 + 可介入流程」。

### 1.3 一个关键的成本结构（后面所有设计的出发点）

复盘的代价是不对称的：

```
第 1 步发现方向错 → 损失 ≈ 0        （重说一句就行）
第 5 步发现 → 损失 = 4 步的 token + 时间
第 9 步发现 → 损失 = 前面全部 + 可能已经发出的副作用（邮件、订单、文件）
```

⭐ **发现越早，代价越小。** 所以「尽早暴露信息」和「尽早提供干预点」
不是体验优化 —— 是**成本优化**。流式和人工审批，本质都是把「发现时刻」提前。

## 二、来龙去脉

### 2.1 流式：从 Web 技术到 LLM 的标配体验

**技术底座（早于 LLM 很久）**：

- **SSE（Server-Sent Events）**：HTML5 时代的浏览器标准 ——
  服务器 → 浏览器的**单向**文本事件流（`text/event-stream`），
  带**自动重连**语义。轻、简单、兼容 HTTP 基础设施。
- **WebSocket**：双向全双工，需要协议升级 —— 强大但更重。
- **轮询（polling）**：最土的办法，反复问「好了没」—— 浪费、延迟大。

**LLM 时代的转折点**：

- **2022-11 ChatGPT 上线**：把「打字机式输出的体感」变成了大众对 AI 的默认预期。
  这是一个用户体验的分水岭 —— 它证明**「看见它在写」本身就有巨大价值**，
  即使总时长没变；
- **2023-03 OpenAI API 开放 `stream=true`**：流式从产品奇技变成 API 能力，
  生态跟进（各家 API、SDK、前端框架）；
- **2023-2024 的工程坑**：tool_calls 的流式传输 ——
  函数参数是**分片到达**的（JSON 拼装问题），一个工具调用的参数可能分 10 个 delta。
  这是所有从「对话流式」升级到「Agent 流式」的人都撞过的墙
  （ROADMAP 里也预估了这一堵：流式下 tool_calls 是分片到达的，要自己拼装）。

### 2.2 人机协同：从「确认框」到「一等公民的暂停」

**早期（2023）**：人机协同 ≈ 危险操作前弹一个确认框。
问题很快暴露：**确认框太多 → 用户闭眼点「同意」**（审批疲劳），
安全设计变成安全表演。

**进化（2024-2025）**：业界把「暂停/恢复」做进了 Agent 运行时：

- **LangGraph 的 `interrupt` + checkpointer**（2024-2025 的代表）：
  Agent 的每一步状态都被持久化，可以在任意节点**暂停**，
  等外部（人）提供输入后**从暂停点恢复** —— 暂停不再是「异常」，是状态机的一个正常状态；
- **计划审批模式**（Cursor 等编程工具的 Plan Mode、Deep Research 的先出报告大纲）：
  执行前先给出计划让人改 —— 把干预点**前置到最便宜的时机**（第 1.3 节的逻辑）；
- **分级授权**（编程 Agent 的权限模型）：读操作放行、写操作按危险级别处理，
  「本次会话记住此决定」减少重复打扰；
- **协议化**（2025）：MCP 在 2025-06 的规范里加入 **elicitation** 原语 ——
  server 可以在任务中途**向用户发起提问**，把「问人」标准化成协议能力。

一句话总结这条线：**人机协同从「UI 层的弹窗」进化成了「运行时的状态」**——
可暂停、可恢复、可持久化、可跨进程。

## 三、机制拆解

### 3.1 流式的三层结构

```
传输层：SSE / WebSocket / chunked transfer      ← 字节怎么过来
事件层：文本 delta、tool_call 分片、状态事件      ← 字节翻译成什么
渲染层：打字机、工具面板、进度条、耗时统计         ← 呈现给人和程序
```

**事件层的设计决定体验质量**。好的事件协议不止有「文本增量」，还包括：

- **工具调用事件**：什么时候开始调什么工具、参数是什么、结果是什么 ——
  这是 Agent 场景独有的、最有信息量的事件（「它在查文件」比「它在输出文字」重要得多）；
- **状态事件**：等待模型 / 执行工具 / 重试中 ——
  让 UI 能回答「它还活着吗」这个最原始的问题；
- 结算事件：token 用量、耗时 —— 可观测性（v9 的账本）在流式里的延伸。

> 💡 对照记忆：这和你日志里那条「黑盒工具的每个动作都要能被看见」是同一个哲学
> （铁律 7）—— 只不过流式把它实时化了。

### 3.2 中断：先分清「能不能后悔」

中断设计的第一问题不是技术，而是**后果**：

| 正在做的事 | 中断的后果 | 处理方式 |
|---|---|---|
| 生成文字 | 丢弃半截文本，零副作用 | 直接取消（AbortController 之类） |
| 只读工具（查询、搜索） | 无副作用 | 取消即可，重跑一次 |
| 写工具（存文件） | 已写的部分可能留下 | 幂等设计 + 重启时对齐状态 |
| 不可逆外部动作（发邮件、下单） | **无法撤回** | ⭐ 关键设计：把「执行」本身做成两段 —— 先预览/确认，再提交 |

⭐ **核心原则：不可逆的操作，不要指望「中断」去救 —— 要在执行前用「审批」拦住。**
中断是安全网，审批才是设计。

### 3.3 人机协同的三个档位（按干预强度递增）

```
档位一：确认（approve / deny）
  高危动作前暂停：「要写文件 xxx，同意吗？」→ 是/否
  适用：不可逆、有副作用、高成本的操作

档位二：纠偏（interrupt & correct）
  跑偏时给方向：「别查这个了，换个思路/这个结果不对，忽略它」
  适用：方向性偏差、外部信息变化

档位三：接管（take over）
  用户直接改产物/改计划，Agent 从修改后的状态继续
  适用：计划审批、产出物修订（Deep Research 的「改大纲再跑」）
```

三个档位的**共同技术底座是同一个东西：可暂停、可恢复的状态**——
这就接到了项目里一个你熟悉的概念：

> **暂停 = 把状态存下来；恢复 = 读回来继续。**
> 这不就是 v4 的 session.json 吗？
> 区别只是：v4 存的是「会话」，而这里要存的是「执行到哪一步了」——
> 每一步而不是每一轮，含工具状态而不是只含消息。

### 3.4 半截状态的三个工程问题

流式 + 中断 + 恢复引入了一类全新的麻烦：**系统经常处在「一半」的状态**。

- **半截消息**：流式输出到一半断线 —— 这半截要不要进历史？
  （答：要对「已完成」和「未完成」有明确的标记，不能把半截当完整回复存档。）
- **半截工具调用**：tool_call 的参数 JSON 只收到一半 ——
  必须等完整再执行（拼装校验），绝不能执行残片；
- **半截任务**：暂停恢复后，有些工具可能「执行过但没记录」——
  需要幂等操作 + 恢复时的状态对账。

## 四、为什么是这么解的（第一性原理）

### 4.1 感知延迟 ≠ 实际延迟

用户体验的核心指标不是「总耗时」，是**「首字延迟（TTFB）+ 信息的稠密度」**：

- 总耗时一样的两套系统，一套黑屏 30 秒，一套 0.5 秒就开始输出 ——
  用户对后者的评价高一个数量级；
- 更关键的是 「**进程感**」：好的流式界面让用户随时能回答
  「它在干什么、干到哪了、有没有异常」—— 这本质上是一个**可观测性问题**
  （v9 的 trace 是离线可观测，流式是实时可观测，同族）。

### 4.2 不可逆性决定一切审批设计

把操作按两个维度分类：**后果严重度 × 可逆性**。

```
严重 + 不可逆（发邮件、下单、删数据）→ 必须审批，默认拒绝
严重 + 可逆（写本地文件）            → 可放行 + 事后可回滚
轻微 + 可逆（查询、读取）            → 静默执行
```

审批不是「越多越安全」——**审批的位置要与不可逆性对齐**。
拦错了地方（在只读操作上狂弹窗）只会制造审批疲劳，
而真正危险的写操作反而因为「又弹窗了」被顺手点过。

### 4.3 代价不对称 → 干预点要前置

回到 1.3 的成本结构：错误发现得越早越便宜。
所以「干预点」的最佳位置排序：

```
计划阶段（改一句话的成本） >> 执行中途（重做几步） >> 做完之后（全部重来）
```

这就是为什么 2025 年主流产品都在**计划审批**上发力 ——
它是最便宜、收益最大的干预点（和 08 的「计划外显」刚好接上：
**计划外显是可干预的前提**）。

### 4.4 人的注意力是稀缺资源

人机协同的隐藏敌人不是「用户不关心」，而是「用户会疲劳」：

- 每个确认框都在消耗用户的注意力预算；
- 一旦确认变成机械动作，安全机制就归零（闭眼点同意）；
- 所以设计目标是**高信噪比**：默认安全、只在高危处打扰、
  记住「同类决定」（allowlist / 会话内记住）——把打扰次数降到个位数。

## 五、横向对比

### 5.1 传输技术选型

| 技术 | 方向 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **SSE** | 服务器 → 客户端 单向 | 简单、走 HTTP、自动重连、过代理友好 | 只能单向 | ⭐ LLM 输出的主流（配合 POST 发起请求） |
| **WebSocket** | 双向 | 全双工低延迟 | 升级握手、连接管理复杂、基础设施要求高 | 语音对话、需要双向高频交互 |
| **分块 HTTP（chunked）** | 单向 | 最原始 | 无事件语义、无法自动重连 | 简单场景 |
| **轮询** | 拉取 | 实现最简单 | 延迟/浪费 | 兜底 |

> 常被问到：「为什么 LLM 流式用 SSE 而不是 WebSocket？」
> 答：LLM 输出是**服务器到客户端的单向流**，SSE 的方向刚好匹配；
> 且它基于 HTTP、自动重连、对代理/防火墙友好。
> WebSocket 的双向能力在这里是过剩的 —— 复杂度和收益不匹配。
> （需要双向时 —— 比如语音打断 —— WebSocket 才有意义。）

### 5.2 人机协同的产品形态

| 形态 | 代表 | 干预时机 | 特点 |
|---|---|---|---|
| 无干预（全自动） | 批处理任务、cron Agent | 无 | 快，但错误的代价全由你承担 |
| 事后审计 | 日志 + 回滚 | 完成后 | 不打扰，但发现太晚 |
| 计划审批 | Plan Mode / Deep Research | ⭐ 最便宜时机 | 一次审批管全程方向 |
| 高危动作审批 | 编程 Agent 权限模型 | 写入/外部动作前 | 和不可逆性对齐 |
| 全程副驾驶 | 实时打断、纠偏 | 任何时候 | 最强控制，最重交互（适合高价值任务） |

### 5.3 暂停/恢复的技术路线

| 路线 | 做法 | 适合 | 局限 |
|---|---|---|---|
| 「问一句再继续」式 | 工具内部阻塞等输入（最简单的 HITL） | 单进程 CLI | 不能跨进程/跨会话 |
| **状态机 + 检查点** | 每步状态持久化，任意点暂停恢复（LangGraph 风格） | 生产级 Agent | 工程量：状态设计、序列化、迁移 |
| 事件溯源 | 记录所有事件，重放出任意状态 | 审计要求高 | 更重 |

> 💡 对照记忆：v4 你纠结过「每轮存 vs 每步存」——
> 当时说「LangGraph 是每步存，崩溃时你丢半轮它不丢」。
> **为什么它必须每步存？因为人机协同要在「步」的粒度上暂停。**
> 你当时觉得「多出来的能力，现在不需要」——现在你知道它的来处了。

## 六、争议与边界

### 6.1 流式的双刃剑

- 好处：透明、可干预、体感快；
- 反面：**它也会暴露 Agent 的丑陋** —— 用户看着它反复试错、推翻自己。
  有些产品刻意「放慢或隐藏中间过程」（比如只显示「正在思考…」的状态行），
  在透明度和信任之间做平衡。
- 结论：**流什么、流多少，是一个产品决策** —— 技术能全流，不代表应该全流。

### 6.2 审批疲劳是安全性的最大敌人

真实事故模式：用户被训练成「无脑点同意」之后，
恰好那次危险操作也混在弹窗里被点过了。
缓解设计：分级授权、批量授权（会话内记住）、把「危险」做得视觉上真的不一样。

### 6.3 中断的原子性无解，只能规避

「工具执行到一半取消」在分布式系统里是无解的经典问题（两阶段提交那一族）。
实用策略不是追求「原子中断」，而是**设计上让危险动作变成两段**：
先预览（可取消）→ 再提交（快且可靠）。

### 6.4 隐私与留痕

流式意味着**一切都在实时经过你的系统**：用户的输入、模型的半成品、
工具的结果 —— 日志、留存、脱敏要提前设计，别等出事再想。

## 七、怎么答

### Q1：「LLM 应用为什么要做成流式？技术难点在哪？」

1. **动机**：感知延迟（首字延迟 vs 总时长）、可观测（它还活着吗、在干嘛）、
   可干预（早发现早止损）。
2. **技术**：SSE 为主（匹配单向流、HTTP 兼容、自动重连）；
   难点在**事件协议**：tool_calls 是分片到达的 JSON，要拼装校验后才能执行；
   半截消息/半截任务的边界处理。
3. **加分**：说清「流式不是 UI 特效，是把 Agent 的内部状态变成实时可观测信息」——
   和 trace/可观测性是一族技术。

### Q2：「怎么做 Human-in-the-loop？」

按三个维度答：

1. **干预档位**：确认 / 纠偏 / 接管；
2. **干预时机与代价**：计划审批最便宜，执行后最贵 —— 干预点前置；
3. **分级授权 + 防疲劳**：按「后果严重度 × 可逆性」决定哪里放闸门；
   默认安全、高信噪比、记住决定。

### Q3：「Agent 的暂停/恢复怎么实现？」

- 本质：**状态外置 + 持久化 + 可重放** ——
  Agent 运行时不再是「一个函数调用」，而是一个可冻结/可解冻的状态机；
- 类比你们 v4 的会话持久化：从「存对话」升级为「存执行状态」；
- 工程要点：检查点粒度、幂等工具、恢复时对账。

### Q4（追问）：「用户中断了一个正在写文件的工具，怎么办？」

- 先分类：只读（取消即可）/ 可回滚（取消 + 清理）/ 不可逆（不该走到这一步 ——
  说明审批前置没做好）；
- 再讲兜底：幂等设计让「重做」安全；恢复时对账清理半截状态；
- 收尾到设计原则：**能用审批拦住的，不要赌中断**。

## 八、回到 hello-agent

现状对照：你现在所有版本都是**全批量**的 —— 输入后等完整回复，
终端把那几行日志吐完才轮到你说话。这不是缺陷，
是「先学内核、后学交互」的正常阶段。但你已经摸到三块拼图：

| 你有的 | 与这一块的关联 |
|---|---|
| v4 的会话持久化（重启恢复） | 暂停/恢复的**最原始形态** —— 存状态、读回来 |
| v9 的 trace 与账本（离线可观测） | 实时流式的**离线表亲** —— 都是「让系统自证清白」 |
| 铁律 7 的日志哲学 | 流式的精神内核：每个动作要有标记、没动作也要说话 |
| v9 一个实测的体感 | 一次 eval 要 2 分钟、交互一轮多步任务要等十几秒 —— 你亲身体会过「黑盒等待」 |

**做这一块的实验时的建议顺序**（ROADMAP 的墙也写了）：
先做「流式输出」（把等待变成直播，感受 tool_calls 分片拼装的坑），
再做「中断」（AbortController 或键盘信号，感受半截状态怎么处理），
最后才做「审批闸门」（这时你才会发自内心地设计「什么该拦」）。

> ⚠️ 这个知识块有一个和其他块不一样的地方：
> **它的「正确答案」高度产品化** —— 有人喜欢全透明，有人喜欢静默副驾驶。
> 所以要练的不是「实现一个标准答案」，而是**说清每个设计选择的取舍**。
