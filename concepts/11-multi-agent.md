# 11 · 多 Agent 协作

> **Multi-Agent Collaboration**

> **一句话**：多 Agent 的第一性理由不是「人多力量大」，而是**上下文隔离**——
> 用通信的代价，换每个角色一个干净的视野。
>
> **它治什么病**：一个 Agent 兼太多角色（规划、执行、检查），提示词互相打架；
> 一个上下文装不下所有信息。

📌 **本页回答四个问题**：

1. **为什么会有这个概念**——单 Agent 到底在什么情况下不够用？（问题）
2. **主流怎么解决**——角色分工、编排、交接的来龙去脉（方案）
3. **为什么是这么解的**——「上下文隔离」的第一性原理（原理）
4. **还有什么别的路**——以及 2025 年那场「要不要多 Agent」的大辩论（对比）

---

## 一、这个问题从哪来

### 1.1 单 Agent 的四个瓶颈

随着任务变复杂，一个 Agent 的提示词里开始叠加角色：

```
「你是一个严谨的分析师，同时大胆地提出假设，
 并且要逐字校验每个数字，但别忘了保持创造性……
 先做计划，再执行，执行中要自我批评，最后输出时保持简洁。」
```

矛盾出现了 —— 这些要求**互相冲突**（严谨 vs 大胆、计划 vs 灵活）。
再看四个具体的瓶颈：

1. **角色指令打架**：一个系统提示词塞多个职责，模型的注意力被平均稀释，
   每个角色都做不好（回到 08 的「注意力预算」原理）；
2. **上下文互相污染**：规划时的长篇讨论、执行时的工具噪音、检查时的挑剔意见，
   全挤在同一个窗口里，互相干扰；
3. **工具与权限混杂**：执行角色不需要「删除文件」的能力，
   但它和规划角色共享同一个工具集 —— 出错的暴露面是全部；
4. **串行**：子任务明明互相独立，却只能排队一个个做。

### 1.2 一个思想源头（讲出来很有味道）

1986 年，Marvin Minsky 在《The Society of Mind》里提出：
**智能不是一个单一的「我」，而是许多简单智能体的协作涌现。**

LLM 时代这句话被反复引用 —— 因为多 Agent 框架的推销词几乎就是它的直译。
但注意：**Minsky 说的是心智的涌现理论，不是工程架构**。
把它当作哲学动机可以，当作技术论据要小心（有人可能就等着你踩这个坑）。

### 1.3 你其实见过最小型的「多 Agent」

你们 v9 的评估体系里有两个角色：

```
角色 A：被测 Agent   —— 系统提示词是「回答问题、用工具」
角色 B：裁判（judge）—— 系统提示词是「检查答案是否通俗、有比喻」
```

两个角色、两套提示词、两次独立的模型调用 ——
**这就是「生成器 + 鉴别器」的最小角色分离**。
你已经体验过它的好处（裁判不用关心答题，只做判定）
和它的坑（v9 实测：裁判被截断时，产生了假红）。

## 二、来龙去脉

### 2023 上半年：角色扮演的实验阶段

- **CAMEL**（Li et al., 2023-03）：两个 Agent 扮演「用户」和「助手」互相对话，
  研究多智能体的协作行为 —— 第一次系统性地用「角色设定」驱动任务完成；
- **Generative Agents**（Park et al., 2023-04，斯坦福「AI 小镇」）：
  25 个 Agent 在小镇里生活，验证了「记忆流 + 反思 + 计划」的 Agent 架构 ——
  影响的是后来的记忆设计（你们 ECOSYSTEM 里 B 派记忆的远亲），
  不是「多 Agent 干活」本身；
- **Multiagent Debate**（Du et al., 2023-05）：多个模型实例各自答题、
  互相看对方的答案并critique，多轮辩论后收敛 ——
  在事实性和推理任务上确实涨点，但成本翻倍，而且存在「盲从多数」的羊群效应。

### 2023 下半年：工程化框架的爆发

- **MetaGPT**（Hong et al., 2023-08）：把「软件公司的 SOP」编码进多 Agent ——
  产品经理 → 架构师 → 工程师 → 测试，流水线式协作。
  核心卖点：**SOP 输出结构化产物（文档/图纸），让每个角色拿着标准化输入开工**；
- **AutoGen**（Wu et al., 2023-08，微软）：可对话 Agent 框架 ——
  角色 = 会聊天的对象；协作 = 群聊（GroupChat）+ 群聊管理员调度。
  「所有协作都是消息」这个模型影响了一整代框架；
- **ChatDev**（Qian et al., 2023）：虚拟软件公司的完整流程复刻。

这个阶段的坑很快暴露：**角色越多越像演戏** ——
消息在 Agent 之间转圈、踢皮球、成本爆炸、产出还不如单 Agent 认真写。

### 2024：编排范式成形

- **CrewAI**（2023 底开源）：role / goal / backstory 三件套 + 顺序或层级流程，
  产品化程度高；
- **OpenAI Swarm**（2024-10）：实验性框架，提出 **handoff（交接）** 概念 ——
  Agent 不是「聊天对象」，而是「可以被移交控制权的状态」；
  它是教育性质的，后来的 **OpenAI Agents SDK**（2025-03）是其生产化版本；
- **LangGraph**（2024 起）：把多 Agent 建模成**状态图** ——
  节点是 Agent，边是转移条件；supervisor（主管调度）、swarm 等模式官方示例化。

### 2025：大辩论 —— 「多 Agent 到底是不是伪需求？」

**2025 年 6 月，两篇重磅文章正面碰撞**（这是这一块最值钱的谈资）：

**正方：Anthropic《How we built our multi-agent research system》**

- 他们的 Research 产品用 **orchestrator-worker 架构**：
  主 Agent 出研究计划，派出若干子 Agent 分头搜索，主 Agent 汇总；
- 结论：多 Agent 在「**广度优先、子任务互不依赖**」的研究任务上显著更好；
- 同时坦白了代价：**token 消耗约为普通对话的 15 倍**；
  强依赖任务、需要共享大量上下文的任务不适合。

**反方：Cognition《Don't Build Multi-Agents》**（Devin 的开发公司）

- 核心论点：**并行子 Agent 各自做「隐式决策」（没写进消息的假设），
  合并时决策互相冲突，产出崩坏**；
- 两条原则（值得背下来）：
  1. 「分享上下文，而且分享完整的执行轨迹 —— 不是只转发个别消息」
     （*Share context, and share full agent traces, not just individual messages*）
  2. 「每个动作都携带隐式决策，而互相冲突的决策带来糟糕的结果」
     （*Actions carry implicit decisions, and conflicting decisions carry bad results*）
- 他们的建议：**单线程线性 Agent + 上下文压缩** ——
  宁可一个窗口扛着，也别让决策在隔离的窗口间「口头」传递。

**这场辩论的本质**：不是谁对谁错，而是**任务结构不同**：

```
任务可拆性高（研究、搜索、并行探索）→ 多 Agent 收益 > 通信成本 ✓
任务强耦合（写一个大代码库、多步依赖链）→ 隔离的代价 > 隔离的收益 ✗
```

**2025 年下半年的实践共识**大致收敛成：

1. 默认单 Agent；出现「上下文装不下 / 角色指令实锤打架 / 真能并行」再拆；
2. 拆分的最小形态是 **agent-as-tool**（把子 Agent 包装成一个工具让主 Agent 调用），
   而不是「一群平级 Agent 开会」；
3. 信息传递尽量用**结构化产物**（文件、工单、计划），而不是自由对话。

## 三、机制拆解

### 3.1 五种拓扑（先认清形状，再谈实现）

```
① 主管制（supervisor / orchestrator-worker）    ② 流水线（pipeline）

      ┌─ Worker A                    Agent1 → 产物 → Agent2 → 产物 → Agent3
 Boss ┼─ Worker B                       （每站只看上一站的交付物）
      └─ Worker C

③ 对等辩论（peer / debate）                     ④ 交接（handoff）

   A ←→ B ←→ C（互看答案，多轮）                [前台 Agent] ──移交──→ [专家 Agent]
                                                  （控制权转移，不是并行）

⑤ 共享黑板（blackboard）

        ┌──────────────┐
        │  共享工作区/产物 │ ← 各 Agent 读、写、认领任务
        └──────────────┘
```

| 拓扑 | 代表 | 强项 | 坑 |
|---|---|---|---|
| 主管制 | Anthropic Research、LangGraph supervisor | 可控、可静默、易调试 | 主管是瓶颈；主管的汇总质量决定上限 |
| 流水线 | MetaGPT、ChatDev | 流程稳定、产物标准化 | 僵化；**上游错误被下游放大** |
| 对等辩论 | Multiagent Debate | 多视角、纠偏 | 成本高；可能「盲从」；收敛不保证 |
| 交接 | Swarm / Agents SDK | 交互自然（像转接客服） | 状态交接设计难；容易踢皮球 |
| 共享黑板 | 经典 AI 传统 | 解耦、可追溯 | 并发与一致性管理 |

### 3.2 通信：三种「信息传递」方式的谱系

```
消息传递（黑盒互相喊话） → 共享产物（交接结构化文件） → 共享上下文（同一个窗口）
     ↑ 损耗最大                                                  ↑ 无隔离收益
```

Cognition 的整篇文章可以理解为对第一种的否决：
**自由文本消息会丢「决策的上下文」**；他们的主张是往第三种靠
（单线程 = 完全共享），或者用第二种补齐（把决策写进产物/计划文件）。

### 3.3 隔离的三个层次

| 隔离层 | 隔离什么 | 收益 |
|---|---|---|
| **上下文隔离** | 各自的对话历史/工作记忆 | 注意力满血；窗口物理扩容 |
| **工具隔离** | 各自可用的工具集 | 角色专注；出错面收窄 |
| **权限隔离** | 各自可做的动作范围（如只有执行 Agent 能写文件） | 安全（最小权限原则） |

> 💡 实现多 Agent 时，最容易被忽略的是第 2、3 层 ——
> 很多框架的「角色」只是换了个提示词，工具权限完全没变。
> **能指出「隔离要隔离三层，不只是提示词」，立刻区分水平。**

### 3.4 汇合：谁来「合成」

并行子任务的产出必须被**合成**（synthesize）：
通常由主管 Agent 或上层负责。两个关键设计：

- 子任务产出要**结构化**（否则合成者要读一堆散文）；
- 合成者需要**子任务看不到的全局视角** —— 这正是主管存在的意义。

## 四、为什么是这么解的（第一性原理）

### 4.1 上下文隔离 = 注意力满血（最硬的理由）

回顾 08 的「注意力稀释」：一个上下文里塞 5 个主题，
每个主题拿到的注意力就只剩 1/5。

```
单 Agent 扛全局：10 万 token 的上下文，5 个主题混在一起，注意力摊薄
多 Agent 分片：  5 × 2 万 token 各管一摊，每个都「满血」关注自己的主题
```

而且当任务总信息量**超过单窗口物理上限**时，分片不是优化，是**唯一出路**。

### 4.2 专业化：指令冲突消失 + 最小权限

- 每个 Agent 的系统提示词只写一个职责 —— 08 学过的「粗计划」原则用在了提示词上：
  **一个角色只装一种世界观**，不矛盾、不稀释；
- 工具/权限按角色最小化 —— 规划和检查角色的工具集可以完全不同，
  出错暴露面成倍收窄（安全收益）。

### 4.3 并行：广度任务的加速

独立子任务同时开跑（如「同时查 20 个来源」）—— 这是 Anthropic
说「多 Agent 赢在广度优先」的直接原因。

### 4.4 那么代价是什么（Cognition 一方的理由也补全）

- **通信损耗**：意图从 A 的脑子 → 消息 → B 的脑子，两次有损压缩；
- **决策冲突**：A 假设了「用 JSON 输出」，B 假设了「用 Markdown」，合并时爆炸 ——
  这就是「隐式决策」问题的本质：**没写下来的假设 = 没传递的假设**；
- **误差累积**：流水线上游的错被下游当事实加工（和 09 的级联一模一样）；
- **成本与调试**：消息数量随 Agent 数近似平方增长；
  n 个 Agent 的协作轨迹比单线程难调试一个数量级。

### 4.5 结论：一个判断公式（能背就背）

> **多 Agent 成立的条件：每个子任务足够独立，
> 以至于「隔离带来的注意力/权限收益」大于「通信损耗 + 冲突风险」。**
>
> 子任务越独立、越并行、越需要不同的工具权限 → 越该拆；
> 子任务互相牵制、需要「心照不宣的共识」→ 越该单线程。

## 五、横向对比：单 Agent vs 多 Agent 的选型表

| 维度 | 单 Agent（默认） | 多 Agent（按需） |
|---|---|---|
| 上下文 | 一个窗口，注意力摊薄 | 隔离，各自满血 |
| 成本 | 低（线性） | 高（通信 ≈ 平方级；Anthropic 实测约 15 倍于普通对话） |
| 调试 | 一条轨迹，清晰 | 分布式轨迹，成本高 |
| 错误传播 | 链式，可追溯 | 跨 Agent，难归因 |
| 并行 | 无 | 天然支持 |
| 权限隔离 | 难（工具集共享） | 易（按角色分配） |
| 适合 | 强依赖、需一致决策的任务 | 广度探索、可并行、角色权限分明 |

**行业参照**（2025 年的两个公开样本，态度针锋相对）：

| | Anthropic Research 系统 | Cognition 的建议 |
|---|---|---|
| 架构 | orchestrator + 多个子 Agent | 单线程 + 压缩 |
| 任务 | 广度研究（子任务独立） | 编程（强依赖、隐式决策多） |
| 结论 | 多 Agent 显著更好（贵） | 多 Agent 会崩（冲突决策） |

> 💡 两者不矛盾 —— **各自在自己的任务结构里正确**。
> 把「任务结构决定架构」这层说透，比背哪个博客都值钱。

## 六、争议与边界

### 6.1 「伪需求」论的合理成分

多 Agent 最常被吐槽的三种翻车（按频率排）：

1. **演戏**：角色设定华丽（产品经理/架构师/测试），产出一堆互夸的会议纪要，
   真正干活的质量没提升；
2. **踢皮球**：交接来交接去，没有角色对最终结果负责；
3. **成本失控**：Agent 数 × 消息数增长，账单上涨远超质量收益。

**防御策略**：每个子 Agent 的产出必须**可验证**（能被主管或程序检查）；
交接必须有**结构化产物**（计划、文件、工单），不是「聊过了」；
先证明单 Agent 不行（ROADMAP 原话：**先确认单个 Agent 真的做不好，再上多 Agent**）。

### 6.2 什么时候不要多 Agent

- 1~2 步的任务（杀鸡用牛刀）；
- 子任务之间需要频繁互相参考上下文（隔离反而是伤害）；
- 你没有能力调试分布式轨迹（先建好可观测性 —— v9 的教训）。

## 七、怎么答

### Q1：「什么时候该用多 Agent？」

答题骨架（先反问任务结构，再给判断）：

1. **第一性理由**：多 Agent 是**上下文工程的手段**，不是「智能化」的手段 ——
   为了给每个角色一个干净的视野。收益来源：注意力隔离、权限隔离、并行；
2. **判断公式**：子任务独立性 vs 通信损耗 + 决策冲突风险；
3. **两派实证**：Anthropic（广度研究，多 Agent 有效但贵 ~15 倍）vs
   Cognition（强依赖编程，隔离导致隐式决策冲突，主张单线程）——
   不是对错之争，是任务结构之争；
4. **落地建议**：默认单 Agent；需要拆分时，优先
   agent-as-tool / 结构化产物交接，而不是平级群聊。

### Q2：「多 Agent 协作最大的难点？」

- **决策传递**：动作携带隐式假设，消息传递有损 ——
  解法是把决策显式化（产物/计划）或干脆共享完整轨迹；
- **一致性**：谁对最终结果负责、冲突决策怎么裁决；
- **成本与调试**：平方级消息 + 分布式轨迹。

### Q3：「handoff 和 supervisor 的区别？」

- supervisor：调度权保留在主管 —— 主管派活、收活、汇总；
- handoff：控制权**转移**给下一个 Agent（前台转专家，不回主管）——
  像客服转接；适合角色接力的场景，双方各自带着自己的上下文。

### Q4（追问）：「让多个 Agent 辩论能提高正确率吗？」

- 有实证收益（Du et al. 的多轮辩论在事实性上有提升），但有前提：
  各 Agent 要有**独立视角**（不同 prompt/不同信息），否则只是复读；
- 成本和「盲从多数」问题真实存在；
- 务实替代：单 Agent 多次采样 + 聚合（self-consistency）常常更便宜 ——
  辩论的收益要大过它的溢价才行。

## 八、回到 hello-agent

**你已经有的最小形态**：v9 的评测里，「被测 Agent」和「裁判」
就是一次角色分离（生成器 vs 鉴别器）——而且你亲历了它的收益和坑：

- 收益：裁判专注「判定」，不受答题过程的污染（各司其职）；
- 坑：裁判也是模型 —— 它被截断时你能准确归因
  （「这是判定环节的故障，不是模型答得不好」），
  这个故障归因能力在多 Agent 系统里只会更重要（分布式轨迹更难归因）。

**做这一块的实验时**（等真做再翻回来）：

1. **最小验证**：同一批用例，让一个「规划 Agent」先把任务拆成 2~3 步
   交给「执行 Agent」，和单 Agent 直跑对比分数与 token 账本 ——
   大概率你会亲自观察到「通信损耗」是怎么吃掉收益的；
2. **观察点**：执行 Agent 拿到的任务描述里，有多少是规划 Agent
   「默认对方会知道」的隐式决策？（这就是 Cognition 说的问题的实证。）
3. **别忘了 ROADMAP 的警告**：这一块最容易被过度使用 ——
   先让单 Agent 撞墙（有实测证据），再拆。
