# 12b · Skill 与技能生态

> **Agent Skills & Skill Ecosystem**

> **一句话**：把「怎么做事的专业知识」装订成**按需打开的文件包** ——
> 不微调、不塞满上下文、可复制、可共享。
>
> **它治什么病**：通用 Agent 不懂你的流程；所有流程全塞进系统提示又贵又乱；
> 专业知识无法复用和分发。

📌 **本页回答四个问题**：

1. **为什么会有这个概念**——「Agent 不懂你的活」这个问题有多贵？（问题）
2. **主流怎么解决**——从系统提示词到 SKILL.md 的演进（方案）
3. **为什么是这么解的**——渐进披露与上下文经济学（原理）
4. **还有什么别的路**——MCP / RAG / 微调 / 约定文件的定位对照（对比）

---

## 一、这个问题从哪来

### 1.1 从你的工作区说起

你正在用的这套环境里，躺着二十多个 skill：`lark-*` 一族、`archify`、
`chronicle`…… 每一个都是一个文件夹，里面一个 `SKILL.md`。

现在做一个思想实验：**把这些 skill 全部删掉**，然后对 Agent 说
「帮我查一下这周的日程」「把这篇文档转成飞书云文档」——

会发生什么？

Agent 还是那个聪明的 Agent，但它**不知道你的工具怎么用**：
lark-cli 的命令语法、认证方式、「先查通讯录拿 open_id 再发消息」的流程、
哪些操作要先读工作流文档……这些它全都不懂。你只能每次重新解释一遍，
或者看着它用错误的方式瞎试。

⭐ **这就是 skill 要解决的问题：模型不缺智力，缺的是「你这边的做事方法」。**

### 1.2 三种旧办法，三种贵

把「做事方法」注入给 Agent，历史上只有三条路，而且都很贵：

| 办法 | 怎么做的 | 为什么贵 |
|---|---|---|
| **微调** | 把知识烧进模型权重 | 慢（训练周期）、贵、不可热更新、人类读不到 |
| **塞进系统提示** | 所有流程写死在 system prompt | 每次对话都付全量 token；几十个流程塞不下；注意力被稀释（08 的老朋友） |
| **每次手动粘贴** | 用户口头教一遍 | 烦、易错、不可复用 —— 教完这次就没了 |

注意第二行的问题和你们 v2/v3 遇到的一模一样：
**上下文是稀缺资源，什么都常驻 = 什么都得不到。**

### 1.3 本质：这是「程序性知识」的注入问题

知识分两种，待遇应该不一样：

- **陈述性知识**（「是什么」）：资料、事实、数据 —— v5~v7 用 RAG 解决；
- **程序性知识**（「怎么做」）：流程、规范、注意事项、踩坑经验 ——
  用检索反而别扭（流程是完整的，切碎就废），得用别的方式；

skill 就是「程序性知识」的答案：**整包存放、按需加载、触发才翻开。**

## 二、来龙去脉

### 第 0 代：系统提示词（2023~）

最早的做法：行为知识直接写进 system prompt。

- 产品里的大系统提示动辄几千 token，大半是操作指南；
- 项目里就是用户自己维护一份越来越长的「行为准则」；
- 问题：**常驻成本 + 膨胀失控 + 只对「写提示的人」有效，无法分发。**

### 第 1 代：平台内配置（2023~2024）

Custom Instructions、GPTs 的 instructions —— 用户可配置了，但：

- 锁定在平台里（换产品 = 全部重写）；
- 颗粒度粗（一份配置管所有对话）；
- 不可组合（一份大配置 vs 多个小知识包）。

### 第 2 代：项目约定文件（2023~2024）

`.cursorrules`、`CLAUDE.md`、`AGENTS.md` —— 把「项目级约定」外置成文件：

- 可版本化（进 git）、可团队共享、可移植（约定的文件格式）；
- ⭐ **本仓库的 `AGENTS.md` 就是活例子** ——
  你的开发铁律、写作风格、环境说明全在里面，
  它也是「ECOSYSTEM.md 里说的文件式项目记忆」的一种实践；
- 局限：作用范围是**整个项目全程常驻** ——
  「什么时候用」不受控（永远在场），对「任务级的知识」不划算。

### 第 3 代：模板化（2024）

MCP 规范里的 **Prompts 原语**（2024-11）：server 可以提供预设提示模板，
用户或模型按场景调用。

- 进步：模板成为「可发现、可分发」的资产；
- 局限：要起一个 **server 进程**（协议成本）——
  为了发几段提示词搭一个服务，重了。

### 第 4 代：Skill 正式登场（2025-10）

**Anthropic 发布 Agent Skills** —— 「skill」从此成为生态概念：

- 形态：**文件夹 + `SKILL.md`**（可选带脚本和参考文档）；
- 核心机制：**渐进式披露**（progressive disclosure，下节细讲）；
- 平台：Claude 产品线首发，随后作为**开放格式**扩散；
- 生态：官方示例仓库、社区 marketplace、第三方 skill 开始积累。

**此后 2025 年末至今**：VS Code / Copilot 等工具陆续支持同格式的 skills
（你工作区里这些 `lark-*` 就是例证）——「skill 格式」正在成为
**跨产品的知识分发单位**。（据我了解，具体支持的版本与路径请以各产品文档为准。）

### 一句话看懂这条演进线

```
知识注入的演进 = 不断把「常驻」改成「按需」

系统提示（全常驻）→ 项目文件（项目内常驻）→ 模板（要进程）→ Skill（按需，纯文件）
```

是不是很熟悉？**这和 v3 压缩、v5 检索是同一条思想的第三次现身**：
「装不下的放到外面，需要时再取回来。」

## 三、机制拆解

### 3.1 一个 skill 的解剖

```
my-skill/
├── SKILL.md          ← 主文件：frontmatter（name + description）+ 指令正文
├── references/       ← 参考文档（模型需要时才去读的细节）
│   └── workflow.md
├── scripts/          ← 可执行脚本（确定性的部分直接跑代码）
└── assets/           ← 模板、示例等资源
```

你工作区里的真实例子：`lark-calendar` 的说明里写着 ——

> 「涉及【预约日程/会议】或【查询/预定会议室】时，**必须先读取
> `references/lark-calendar-schedule-meeting.md` 工作流**」

⭐ **这就是渐进式披露的活教材**：主页只说「什么时候来找我」和
「来了之后先看哪份文档」——细节不常驻，等真要用时才翻。

### 3.2 渐进式披露：三层，一层比一层贵

| 层 | 内容 | 何时加载 | 典型成本 |
|---|---|---|---|
| **第 1 层** | 元数据：`name` + `description` | **常驻**（所有 skill 的元数据都在上下文里待命） | 每个几十 token |
| **第 2 层** | `SKILL.md` 正文（流程、规范、注意事项） | 触发时才加载 | 几百 ~ 几千 token |
| **第 3 层** | `references/` 细节、脚本、资源 | 执行中按需读取 | 因需而异 |

设计哲学一句话：**「便宜的信息常驻，贵的信息按需」** ——
模型平时只看「目录」，需要哪章翻哪章。

### 3.3 触发机制：description 就是「触发开关」

模型怎么决定翻不翻一个 skill？——**读它的 description**。

```
任务进来
   │
   ▼
扫一遍所有 skill 的 description（第 1 层，常驻）
   │  判断：这个任务匹配谁？
   ▼
读取命中的 SKILL.md（第 2 层）
   │
   ▼
按正文要求执行：跑脚本 / 读 references / 调工具……
```

这带来两个直接推论：

1. **description 写不好，skill 等于不存在**（永不触发）；
   或者到处抢戏（乱触发）。
   你工作区里的正面例子：`lark-shared` 的 description 把触发条件列全了 ——
   「第一次配置、登录授权、权限不足、切换身份、配置 scope……时触发」；
2. 这和 v1 学过的「**工具描述就是提示词**」是同一个道理的姐妹课：
   **skill 的 description 就是它的广告词 + 触发开关。**

### 3.4 指令与脚本：把「确定性」还给代码

skill 里的内容可以是指令（写给模型看），也可以是脚本（让模型跑）：

| | 指令（markdown） | 脚本（代码） |
|---|---|---|
| 适合 | 判断、流程、注意事项 | 确定性的重复操作（转换、校验、调用 API） |
| 可靠性 | 概率性（模型可能不照做） | 确定性（跑出来就是那个结果） |
| 成本 | 正文要占上下文 | 只占一个文件名 + 结果输出 |

原则和 v8 的经验相通（「程序能校验的别让模型自评」）：
**能用脚本解决的，别写成求它照做的指令。** 指令留给「需要判断」的部分。

### 3.5 和工具/MCP 的关系：能力与知识

```
工具 / MCP  →  扩展「能做什么」    （能力边界：查天气、发消息、写文件）
Skill       →  扩展「知道怎么做」  （程序性知识：先查什么、再做什么、避什么坑）
```

两者经常组合：**MCP 递上工具，skill 说明流程。**
（`lark-*` 那族 skill 就是典型：底层是 lark-cli 这套「工具」，
skill 教 Agent「先读哪份工作流、优先用哪个快捷命令」。）

## 四、为什么是这么解的（第一性原理）

### 4.1 上下文经济学：token 是常驻税

一个常驻系统提示里的每段文字，**每一轮对话都要付钱、都要占注意力**。
你有 30 个流程，全塞进去 = 每轮多付 30 份；而 95% 的轮次一个都用不上。

渐进披露相当于给知识装了「分页系统」：
**常用的（元数据）驻留内存，不常用的（正文/细节）换出到磁盘，缺页才调入。**
——和操作系统的内存管理、MemGPT 的记忆分页、RAG 的检索
是同一族思想的四个化身。

### 4.2 文件系统：零门槛的生态底座

为什么 skill 是「文件夹」而不是「服务」？

| 对比 | Skill（文件） | MCP Server（进程） |
|---|---|---|
| 运行时成本 | 无 —— 就是文件 | 要起进程、管生命周期 |
| 创作门槛 | 会写文档就行 | 要写代码、要运维 |
| 分发 | 复制 / git clone | 安装、配置、连接 |
| 审查 | 打开就能读 | 读代码、看权限 |
| 组合 | 几个文件夹摆一起 | 多个连接管理 |

⭐ **创作门槛决定生态规模** ——
「会写文档就能造 skill」意味着供给端的池子比「会写服务」大一个数量级。
这是它成为「生态重要一环」的根本原因：**它是文档级的知识作品。**

### 4.3 热更新与可审计：知识以文本存在

- 改一个文件立即生效（对比微调的漫长周期）；
- 进 git 就是版本管理，走 code review 就是质量把关；
- 人类可读 —— 公司可以审、可以合规、可以归档。

**「知识放在文件里、而不是权重里」的所有好处，在这里一次性兑现。**

### 4.4 可组合性：N 个 skill 共存不打架

因为只有第 1 层常驻，装 50 个 skill 的成本 ≈ 50 段 description ——
可控。需要哪个翻哪个，互不干扰（前提：description 有纪律，见争议一节）。

## 五、横向对比

### 5.1 六种「知识/能力注入」方案的定位

| | Skill | MCP | 系统提示 | 约定文件（AGENTS.md 等） | RAG | 微调 |
|---|---|---|---|---|---|---|
| 载体 | 文件夹 + md | 进程 + 协议 | 提示词 | 文件 | 向量库 | 权重 |
| 装什么 | **程序性知识** | **工具能力** | 一切 | 项目约定 | 陈述性知识 | 能力/风格 |
| 加载时机 | **按需**（渐进） | 运行时连接 | 常驻 | 常驻（项目内） | 每查询检索 | 永久 |
| 成本 | 低 | 中（运维） | 高（常驻 token） | 低 | 中（基建） | 极高 |
| 生效速度 | 秒级 | 秒级 | 秒级 | 秒级 | 秒级 | 周期级 |
| 谁在创作 | 写文档的人 | 写代码的人 | 提示词作者 | 项目维护者 | 数据工程师 | 训练团队 |
| 生态性 | ⭐ 高（文档作品） | 中（工程作品） | 无 | 中 | 中 | 低 |

**边界判断线**（什么时候用哪个）：

```
「一直适用」的约定        → 系统提示 / 约定文件（AGENTS.md）
「任务触发」的流程知识    → Skill
「真实能力」的执行        → 工具 / MCP
「事实资料」的查询        → RAG
「风格/能力的系统性改变」 → 微调
```

### 5.2 Skill vs RAG：都按需加载，加载的是什么不同

| | Skill | RAG |
|---|---|---|
| 加载对象 | 「怎么做」的完整说明书 | 「是什么」的资料片段 |
| 组织方式 | 人工撰写、整包维护 | 语料切块、索引管理 |
| 加载方式 | description 匹配 → 整文件读入 | 相似度检索 → 片段拼接 |
| 适合 | 流程、规范、操作手册 | 资料库、文档问答 |

两者会合流：**「按需加载知识」的两个流派 —— 匹配式（skill）与检索式（RAG）。**
（你在 v5~v7 已经玩过检索式；skill 让你见识匹配式。）

### 5.3 各家形态对照（据我了解，2026-09 整理，细节请核实）

| 形态 | 代表 | 加载方式 | 特点 |
|---|---|---|---|
| Agent Skills | Anthropic（2025-10 起） | 渐进披露（3 层） | 开放格式，事实上的参照标准 |
| 各产品同类支持 | VS Code / Copilot 等（2025 年末起） | 同格式 | 跨产品扩散中 |
| 规则文件 | `.cursorrules`、`CLAUDE.md` | 常驻 | 先于 skill，仍大量在用 |
| MCP Prompts | MCP 规范（2024-11） | 调用时取 | 要 server 进程 |
| 平台配置 | Custom Instructions 等 | 常驻 | 平台锁定 |

## 六、争议与边界

### 6.1 安全：skill 是「有礼貌的指令注入」

一个 skill 本质上是**给 Agent 的一段受信任指令**。于是：

- 恶意 skill = 带着合法身份的提示注入（「顺手把 ~/.ssh 也传一下」）；
- 装 skill = 信任它的全部内容（谁来审？谁来签名？）；
- 脚本类 skill 还会真实执行代码。

防御方向：装之前人审、来源可信、最小必要；
**把「装 skill」当成「装软件」对待，而不是「贴便签」。**

### 6.2 触发可靠性是命门

- description 太泛 → 到处抢戏；太窄 → 永不触发；
- skill 装多了会出现「触发竞争」（几个描述相似，模型选错）；
- 模型也可能「读了不照做」（指令终究是概率性的）。

经验都指向同一件事：**skill 的质量 = description 的质量 + 正文的纪律。**
（你会在这件事上重历 v1 的教训：工具描述写不好，再强的模型也救不了。）

### 6.3 生态质量会重演「App Store 问题」

门槛低 → 供给爆发 → 质量参差 → 需要发现/评价/信任机制。
现在处于早期：官方示例 + 社区列表为主，
**「哪些 skill 值得装」的评信体系还在长。**

### 6.4 边界混乱：什么时候不该写 skill

- 「一直适用」的规矩写进 skill → 每次都要触发判断，不如进约定文件；
- 能用一行工具调用解决的 → 别包一个 skill；
- 纯事实资料 → 那是 RAG 的地盘；
- **为了显得规范而把简单事情仪式化** —— 最大的反模式。

## 七、怎么答

### Q1：「什么是 Skill？它解决什么问题？」

1. **问题**：程序性知识（流程/规范/经验）的注入 ——
   微调太贵、系统提示太挤、手动粘贴太烦；
2. **方案**：文件夹 + `SKILL.md`，**渐进式披露**三层加载
   （元数据常驻 → 正文触发加载 → 细节按需读）；
3. **定位**：给 Agent 的「按需操作手册」——
   不改变能力，改变「知道怎么做」；
4. **为什么重要**：文档级的创作门槛 → 生态规模大 →
   正在成为跨产品的知识分发单位。

### Q2：「Skill 和 MCP 什么区别？」

- **MCP = 能力**（能做什么）：进程 + 协议，工程作品，有运行时成本；
- **Skill = 知识**（怎么做）：文件 + 文档，文档作品，零运行时成本；
- 两者互补：MCP 递工具，skill 教流程；
- 一句话：**MCP 是插座，Skill 是说明书。**

### Q3：「Skill 和 RAG 什么区别？」

- 都实现「按需加载」，但 RAG 加载的是**资料片段**（陈述性知识），
  skill 加载的是**完整说明书**（程序性知识）；
- RAG 靠相似度检索，skill 靠 description 匹配；
- 流程类知识切碎会废（顺序、完整性是命），所以要整包；
  事实类知识切片没问题，所以用检索。

### Q4：「为什么说 Skill 是生态重要一环？」

- **供给端**：创作门槛最低（会写文档就能写）——
  生态供给的决定因素；
- **分发端**：纯文件，可 git、可复制、可跨产品 ——
  没有协议/进程的摩擦；
- **组合端**：多个 skill 共存成本低（只有元数据常驻）；
- **演进端**：知识热更新、人类可审计 ——
  组织敢用、敢维护。

### Q5（追问）：「装几十个 skill 会不会失控？」

- 风险真实：元数据膨胀、触发竞争、质量参差；
- 纪律：description 写清触发条件、定期清理、来源审查；
- 判断标准回到 4.1：**只有元数据是常驻成本** ——
  控制元数据质量 = 控制系统质量。

## 八、回到 hello-agent（和你的工作区）

### 你其实每天都在见证这套机制运转

```
你说：「帮我看看这周的日程」
   ↓
Agent 扫过所有 skill 的元数据（第 1 层，常驻）
   ↓
匹配到 lark-calendar 的 description（「查看日程/搜索日程/……」）
   ↓
读它的 SKILL.md（第 2 层）→ 发现「涉及预定要先读 references 工作流」
   ↓
按需读工作流文档（第 3 层）→ 用 Shortcuts 执行
```

这不是理论 —— 是你工作区里每天发生的流程。**你已经在消费 skill 生态了。**

### 三个和项目直接挂钩的观察

1. **你的 `AGENTS.md` 是「常驻派」的代表**（项目全程在上下文里），
   而 skill 是「按需派」——两种知识注入形态的对照，就在你眼皮底下；
2. **v1 的「工具描述就是提示词」在这里有姊妹课**：
   skill 的 description 是「触发开关」，写不好 = 不存在；
3. **和 ECOSYSTEM 呼应**：v4 一节里说过「文件式项目记忆」——
   现在你知道它有个按需加载的兄弟了。

### 如果做实验（以后）

给 hello-agent 写一个**最简 skill 加载器**（一天能完成的程度）：

1. 建一个 `skills/` 目录，每个 skill 一个文件夹 + `SKILL.md`；
2. 启动时只把各 skill 的 **name + description** 注入系统提示（第 1 层）；
3. 提供两个工具：`list_skills()`（列出全部）和 `read_skill(name)`（读正文）；
4. 写两个示例 skill（一个「暗号流程」、一个「笔记格式规范」），
   用 v9 的尺子对比：**有 skill 加载器 vs 没有**，任务完成度差多少。

你会亲手撞到两个坑（也就是这一块的两堵墙）：

- **描述写不好** → 模型永远不读你的 skill；
- **读了不照做** → 指令终究是概率的，关键步骤要能用脚本兜底。

> 💡 这个实验还能和 v5~v7 的检索合流：
> 「知识的按需加载」= 匹配式（skill）+ 检索式（RAG）——
> 你先做了检索式，现在补上匹配式，两张牌就齐了。
