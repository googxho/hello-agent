## 一、这个问题从哪来：三笔账

一个 Agent 从「我电脑上跑得挺好」到「别人敢把活交给它」，中间要过三道关，
每道关背后都是一笔要算的账：**钱账（贵）、乱账（并发）、长账（运营）**。

### 1.1 第一笔账：钱 —— token 是话费，而且有复利

**先说计价方式**：调模型按 token 计费，并且**输出通常比输入贵**
（据我了解，主流供应商的输出/输入单价比大约在 3~5 倍之间；
具体价格变化很快，以官方定价页为准）。

**再说 agent 的特殊之处** —— 它是台「复利机器」：

- 每一轮调用都要把**全部历史**发过去（v2 学过：上下文就是每次请求的行李）
  —— 5 轮的对话，第 5 轮在替前 4 轮重复付「输入费」；
  输入成本随轮数**近似平方增长**，不是线性。
- agent 的调用次数是**乘数**：规划 +1 次、反思 +N 次、失败重试 +N 次、
  重规划 +N 次……**每个「高级特性」都是一张独立的账单。**

这不是理论。我们项目里就有**自己跑出来的两张账单**：

| 实测 | 调用次数 | tokens | 结论 |
|---|---|---|---|
| v9 基线（9 条用例） | 17 | 14,295 | 「一小题一次调用」的原味成本 |
| v10 同样 12 条用例 · 无规划 | 26 | 22,885 | 底盘 |
| v10 同样 12 条用例 · **加规划** | **55** | **79,729** | 一个特性把账单变成 **3.5 倍**（其中规划自身 10,362） |

⭐ 「规划在简单任务上是纯税」在 v10 里不是修辞 —— 是账本。

**最危险的状态是「没有账本」**：你不知道钱花在哪条用例、哪个用户、
哪个功能上。v9 的 `runs/*.json`（每次评估的调用数/token 账）
就是你拥有的第一份成本归因。

### 1.2 第二笔账：乱 —— 人一多，一切会变

单人单机时被掩盖的问题，会在并发下同时爆出来：

**① 状态串台。**
v12 的 `thread_id` 已经预告了正确方向：状态要按「会话」隔离。
但并发把它升级成新问题：多个任务同时跑，
**进程内存里的状态**（v4 之前的 session）会互相踩；
即便是文件（v12 的 SQLite 检查点库），单机文件库也**扛不住多进程写**
—— 我们在做 `durability-lab.py` 时就亲手撞过 SQLite 的锁/文件问题。

**② 上游限流。**
供应商有配额（RPM 每分钟请求数 / TPM 每分钟 token 数）。
多用户并发时**必然会撞 429**。撞上之后客户端本能会重试 ——
而**重试风暴会把拥堵放大**（每个失败的请求都在火上浇油）。

**③ 幂等的鬼门关（这一条最毒）。**
「重试」遇上「有副作用的工具」= **副作用执行两次**：

- 我们的 `save_note` 若被重试，就是两条重复笔记；
- 放大到真实世界：重复扣款、重复发邮件、重复下单 ——
  agent 的「工具」大多带副作用，**这个坑一定会踩**。

v12 里我们演过一次迷你版：用户拒绝写入后，模型说「无法完成」触发重规划，
新计划又要写 —— 围着用户决定绕圈。那是「拒绝的语义」问题，
也是将来「幂等与重放的语义」问题的序章。

**④ 部分失败。**
agent 跑到一半，服务重启了 / 部署新版本了 / 用户关页面了。
v12 用 `--pause-at` + `--resume` 演示了「怎么续」——
但在生产里，「续」的语义要精确设计：**哪些节点可以重跑、哪些副作用绝不能重复**。
（v12 的答案：「副作用放审批之后」「advance 只记账，重跑无害」——
这些设计纪律在生产里从「讲究」变成「必须」。）

### 1.3 第三笔账：长 —— 上线之后，日子还长

**① 进程模型变了。**
CLI 脚本 → 长驻服务 → 容器/平台。换的不只是运行方式，
是「谁负责生命周期」：挂了谁拉起、发版怎么不丢请求、资源怎么限制。

**② 状态得有家。**
进程内存（重启就丢）→ 单机文件（SQLite，我们还用得挺香）→
共享存储（Postgres / Redis）。
v12 的 checkpointer 之所以是个「生产味」的设计，就在这 ——
**状态和计算分离**，计算可以随便重启，「记忆」放在可靠的地方。

**③ 看不见就管不好。**
日志（我们每版都在做）→ 调用链 trace（每一步的输入输出、父子关系）→
指标面板（延迟 / 成本 / 成功率）。
生产里出问题的第一个问题永远是「发生了什么」——
没有可观测性，连复现都做不到。

**④ 变更管理。**
prompt 是代码（v9 已经给它算了 sha 指纹）、模型是依赖（要锁版本）、
工具是接口（改了要评估）。改完怎么知道变好还是变坏？
v9 的评估 + 对比面板是这个问题的雏形；
生产里的答案是：**灰度发布 → 对比指标 → 不对就回滚**。

**⑤ 安全与合规。**
key 管理（我们放 `.env`，生产用密钥管理服务）、
用户数据隔离（别让 A 的检索搜到 B 的笔记）、
**工具权限**（v12 的 `interrupt` 审批在生产里是一套审批流 + 审计日志：
谁、在什么上下文、批准了什么操作）。

## 二、主流怎么解决：三个方案箱

### 2.1 成本：优化有顺序，顺序比技巧重要

**第 0 步（最常被跳过）：记账。**

- 每次调用记下：模型、输入/输出 token、耗时、**属于哪个任务/用户/功能**
- 「能归因，才能优化」——先回答「钱花在哪」，再问「怎么省」
- 没有这层，后面所有优化都是盲人摸象（v9 的 runs/ 就是这个雏形）

**第 1 梯队（几乎零代价，先做）：**

- **上下文精简**：v2 / v3 / v5 的老手艺在生产放大 ——
  历史剪枝、检索只注入相关段、摘要替代全文。
  「能不带的东西，别带上飞机。」
- **prompt 缓存（prompt caching）**：主流供应商都提供缓存机制
  （据我了解，命中部分的输入价格可以降到十分之一左右，以官方为准）。
  要点只有一个：**让请求的「前缀」稳定** ——
  系统提示 + 工具描述放前面且别乱改，高命中率是「结构设计」出来的。
- **别在稳定前缀里放变化的东西**：把时间戳、随机 ID 挪出系统提示，
  否则你每轮都在「打破缓存」，全额付费。

**第 2 梯队（需要设计，收益可观）：**

- **模型分级/路由**：分类、判定、改写查询这类「简单活」给小模型，
  难关留给大模型。⚠️ 换完必须过评估（v9 的教训：不知道就换 = 瞎换）。
- **结果缓存/复用**：同一个问题问两次，很多场景可以直接答缓存；
  检索层我们已在做（v6 的 embedding 缓存、v7 的融合检索）；
  再往上可以缓存「最终回答」（FAQ 类场景）。
- **批处理 API**：离线任务（评估、批量摘要）走批处理接口，
  通常约半价（据我了解），代价是不保证时延。

**第 3 梯队（伤体验/伤能力，最后才动）：**

- 砍轮数、关规划、缩短输出 —— 每砍一刀，都要拿 v9 的尺子量
  「掉了多少分、省了多少钱」，再决定值不值。
- 主力模型降级 —— 评估分数先过线，再谈省钱。

**护栏（不管省不省都要有）：**

- 单任务上限：v1 的 `MAX_ROUNDS` 就是最原始版本；
  生产里是「单任务 token 预算 / 调用次数上限」。
- 熔断与告警：账单异常增长时能自动刹车、能通知人。

### 2.2 并发：四个可控变量

一句话原则：**无状态服务 + 外部化状态 + 受控吞吐 + 幂等副作用。**

**① 状态外置。**
进程无状态（随便重启、随便扩容），会话与检查点放共享存储。
v4 的 JSON → v12 的 SQLite 是这条路的头两步；生产就是换后端
（Postgres / Redis）——v12 用 LangGraph 的 checkpointer 接口时，
我们隐约体会过「接口不变、后端可换」的甜头。

**② 队列化（最简单、最可靠的一招）。**
请求先入队，worker 池按容量消费 ——
**把「并发」变成「受控吞吐」**。
多数 agent 任务是「异步任务」（几秒到几分钟），
本来就该按**任务**而不是按**请求**对待：
用户拿到 task_id，轮询或推送结果。

**③ 限流与退避。**
客户端按供应商配额**主动**限流（令牌桶），
撞到 429 用**指数退避 + 随机抖动**（防止所有客户端同时重试）。

**④ 幂等（重复执行的安全网）。**
三层各管一段：
- 请求层：带 idempotency key（部分供应商 API 原生支持）；
- 工具层：副作用操作配「去重表」（写之前问「这个操作做过吗」）——
  v12 的笔记场景可以演化为「同标题覆盖，而不是重复创建」；
- 结构层：**能读不写、能算不存**——把副作用面积缩到最小。

### 2.3 部署与运营：从脚本到服务

**① 服务化**：加一层 HTTP 接口（我们 v8 的 `--json` 契约
就是「给程序消费的接口」的雏形）；长任务配 SSE / WebSocket 流式
（见 10 的文档）。**先有接口，才有「别人来用」。**

**② 持久执行（durable execution）**：每步落盘、崩了能续 ——
v12 的 checkpointer 就是这个模式的迷你版；业界把它做成了通用基础设施
（工作流引擎领域的老思路：Temporal 等，agent 是它的新客户）。
共识：**多步骤 + 有副作用 = 每个边界都必须可恢复。**

**③ 可观测三件套**：结构化日志 → trace（每一步的调用链）→
指标面板（成本 / 延迟 / 成功率）。工具的选型变化很快
（OpenTelemetry 的 GenAI 语义约定、LangSmith 一族），
但「三层的事」是稳定的。

**④ 变更管理**：评估集（v9）+ prompt 指纹 + 改前改后跑分
= 小作坊版灰度；生产版是「灰度发布 + 指标对比 + 自动回滚」，
并且把**模型版本也当依赖锁**。

**⑤ HITL 的生产版**：v12 的 `interrupt` 是同步的（人在终端边等边批）；
生产必须**异步**：审批进队列、通知到人、批了继续跑
（v12 的检查点天然支持「暂停很久再恢复」）；
再配审计日志：谁批了什么、当时的上下文是什么。

## 三、为什么是这么解的：第一性 + 行业共识

### 3.1 成本的第一性：一个公式

```
任务成本 ≈ Σ每一轮（输入 tokens × 输入单价 + 输出 tokens × 输出单价）

其中：输入 tokens = 固定开销（系统提示 + 工具描述）
                  + 历史对话 + 检索注入 + 本轮新增
```

三条推论（都能在前面的方案箱里找到对应）：

1. **轮数是乘数**：调用次数直接乘总价 ——
   所以「少一轮」比「每轮抠一点」常常更有效；
2. **输入的杠杆大于输出**：输入占大头、且可以砍（剪枝/缓存）；
   输出关乎质量，砍它要过评估；
3. **缓存命中的本质 = 固定开销不再重复付费** ——
   所以「稳定前缀」是成本工程，不是小技巧。

### 3.2 可靠性的第一性：重试是常态，所以幂等是必须

网络会抖、会被限流、会超时 —— **重试不是可选项，是系统的常态**。
因此设计顺序应该是：

> 先问「这件事重做一遍会怎样」，再决定它能不能重试、怎么重试。

v12 的「重跑语法」是这个原则的微型课堂：
恢复时节点会重跑，所以「advance 只记账（幂等）、副作用放在审批之后」。
同样的推理放到生产：**但凡带副作用的操作，设计里必须先回答
「重复执行会怎样」**。回答不了，就不能让它进入「可重试」的世界。

### 3.3 行业共识（社区收敛出的「别拧着来」）

据我了解（2026-10 整理），下面几条在业界基本没有争议：

1. **简单优先**：能用确定性代码解决的部分别用模型（贵、慢、不稳）；
   一次调用能解决就别写循环；能单 agent 就别多 agent ——
   11 的文档里那条共识，在生产里继续成立。
2. **评估驱动一切变更**：prompt / 模型 / 结构，改任何东西先过评估。
   v9 是整个行业变更管理的最小学数学版。
3. **持久化是标配**：「durable execution」从工作流领域进入 agent 领域；
   多步骤 + 副作用 = 每个边界可恢复。
4. **HITL 分层**：低风险自动完成，高风险留闸门；
   闸门要能异步、要有审计。
5. **成本优化顺序：先测准 → 再砍量 → 最后动模型。**
   上来就换小模型，是经典翻车方式（分数掉在哪都不知道，
   省的钱也不知道去哪了 —— v9 的对比面板就是防这个的）。
6. **别提前上规模**：没有真实并发量之前，单机 + SQLite + 队列就够用。
   「过早 k8s 化」和「过早多 Agent 化」是同一种病：
   **用复杂度兑换不存在的问题。**

## 四、还有什么别的路：流派与取舍

| 问题 | 流派 A | 流派 B | 怎么选 |
|---|---|---|---|
| 编排与持久化 | 自建 + 组件库（我们这条线）| 平台化（LangGraph Platform / Temporal / 云厂商 agent 平台）| 看「基础设施」是不是你的核心竞争力；框架的 checkpointer 接口让「换后端」不等于「重写」|
| 任务形态 | 同步 API（请求-响应）| 异步任务（队列 + 通知/轮询）| agent 任务天然偏长 → 多数场景异步；秒级任务才值得同步 |
| 成本策略 | 上下文派（省输入：剪枝/缓存/检索）| 模型派（分级/换小模型）| **先上下文后模型**：上下文是零质量代价的省钱；换模型要评估兜底 |
| 部署路径 | 单机服务化（一个 FastAPI + SQLite + 队列）| 云原生（容器编排 + 共享存储 + 平台能力）| 按量走：先撞到「队列排满」「检查点库锁了」的痛，再逐件升级 |
| 人在环 | 同步审批（我们 v12 的 `interrupt`）| 异步工单（审批队列 + 通知 + 审计）| 生产必须异步 —— 没人会盯着终端等 agent |

## 五、怎么答（面试/讨论骨架）

**Q1「Agent 成本怎么控制？」**
> 先记账再优化：每次调用记 token 和归属（任务/用户/功能）——
> 没有这层就谈不上优化。然后按「零代价 → 有代价」的顺序来：
> 上下文精简、稳定前缀吃 prompt 缓存，是第一梯队；
> 模型分级、结果缓存是第二梯队；
> 砍功能、换模型要拿评估分数兜底。
> 护栏是单任务预算上限 —— 我从第一天就有一个 `MAX_ROUNDS`。

**Q2「多个用户同时用，怎么保证不串台、不重复？」**
> 状态外置（每 thread 隔离、检查点落共享存储），服务无状态随便重启，
> 任务队列控吞吐，上游限流加退避。
> 核心是「重试是常态」这个前提：**所有带副作用的操作按幂等设计** ——
> 要么幂等键，要么能检测重复。

**Q3「任务跑一半崩了怎么办？」**
> 每步落盘（checkpointer / durable execution），从最后一个完成节点续跑。
> 但续跑的设计纪律比机制更重要：**哪些节点能重跑、副作用在哪里** ——
> 我在项目里专门演示过「节点重跑」的语义（advance 重跑无害，
> 因为它是幂等的记账；副作用放在审批之后的节点里）。

**Q4（追问）「你一直在做教学项目，哪来的规模化经验？」**
> 诚实回答，这也是加分时刻：
> 我确实没跑过生产流量。但我把每个「生产开关」都亲手写到了它的最小形态 ——
> 预算护栏、上下文预算、缓存、检查点恢复、审批闸门、评估对比。
> 我知道每个开关背后的账；**生产化主要是把这些换成共享存储、
> 加上队列和仪表盘 —— 换的是后端，不是理解。**

## 六、回到 hello-agent

这一块你没有写 v13 的代码 —— 但其实**每个「生产开关」，你都写过它的最小形态**：

| hello-agent 里的 | 生产里的对应物 | 你的第一手证据 |
|---|---|---|
| v1 的 `MAX_ROUNDS` | 单任务预算护栏 | 防死循环烧钱的第一道闸 |
| v2 / v3 的上下文预算与压缩 | 成本优化第一梯队的原型 | 「压缩花 608+181 tokens 只省约 150」—— 省与不省，都有账 |
| v6 的 embedding 缓存 | 结果复用 / 缓存层 | 实测日志「缓存命中 2 段（没花钱）」 |
| v9 的评估 + 对比面板 | 变更管理（灰度/回滚的地基） | 「坏提示词 -5 分」是可量化的事实，不是感觉 |
| v10 的规划成本实测 | 特性 × 成本的乘数效应 | 26 → 55 次调用、22,885 → 79,729 tokens |
| v12 的 checkpointer | durable execution 的迷你版 | `--pause-at 1` 真猝死 → `--resume` 续上 |
| v12 的 `interrupt` | HITL 闸门的原型 | `⏸ 需要你批准`，拒绝 = 真的一动没动 |
| v12 的 `refused` / durability 实验 | 幂等与落盘时机的序章 | async 猝死丢快照 / sync 每步落盘的三档对照 |

**如果你以后想动手**（按「痛感」从低到高，先做哪个都行）：

1. **给 v12 加一本成本账本**（最省力）：每次模型调用记录 token 与用途，
   任务结束打印「这次任务花了多少、花在哪个节点」——
   验证方式：同一任务开/关重规划，账单差值应该约等于失败重试的真实开销。
2. **写一个「20 个并发任务」的小压测**：不用真的 20 个用户 ——
   自己开 20 个线程跑同一批任务，观察 SQLite 检查点库先碎在哪。
   大概率会撞上锁和写冲突 —— 那就是「换 Postgres」的业务理由。
3. **把 v12 服务化**：FastAPI 包一层 + 异步任务（提交任务 → task_id →
   查询状态），体会「暂停很久再恢复」（v12 检查点天然支持）。

> ⚠️ 三个都不急 —— 前十五个版本的经验是：**等真需求出现再动手，
> 假装的需求会教你假装的知识。**

- **durable execution**：工作流引擎领域的经典思路
