# 09 · 反思与自我修正

> **Reflection & Self-Correction**

> **一句话**：让它交卷之前先「检查一遍」——
> 但真正有效的反思不是闭门自省，而是**给检查接上外部的尺子**。
>
> **它治什么病**：错了不知道错，一错错到底；失败一次，下次不会变聪明。

📌 **本页回答四个问题**：

1. **为什么会有这个概念**——错误为什么拦不住？（问题）
2. **主流怎么解决**——自我批评、反思记忆、工具验证的来龙去脉（方案）
3. **为什么是这么解的**——「生成-验证不对称」与盲区原理（原理）
4. **还有什么别的路**——自我反思 vs 外部信号 vs 训练时修正（对比）

---

## 一、这个问题从哪来

### 1.1 一个思想实验

v9 的评估你亲自跑过：9 条用例，改坏提示词，分数 `9/9 → 4/9`。
问题来了 —— **是谁发现了「退步」？**

是你。你跑评估、你看对比面板、你决定改回去。
**Agent 自己全程不知道它变差了，更不知道差在哪。**

再想一步：如果没人跑评估呢？错误会安安静静地留在生产里，
然后在某个你没想到的地方爆发。这就是「错了不会自我批评」的完整代价。

### 1.2 根子在哪：三个结构性原因

**原因一：生成是「采样」，不是「推导」。**

模型输出下一个 token 的过程带随机性（temperature 只是把它显性化了）。
采样意味着**出错不是意外，是概率的必然** ——
系统设计必须假设「输出里一定有错」，问题只是「错多少、拦不拦得住」。

**原因二：错误会级联放大。**

```
第 1 步：把「客户 A 的订单」理解错了
第 2 步：基于这个理解算了价格
第 3 步：基于价格生成了合同
……
第 10 步：一封发给客户的错误报价单 → 已发送，不可撤回
```

每一步都没「回头验证」，错误就一路被**当作事实**传递下去。
最毒的一点：后面的步骤逻辑上完全自洽 —— 从外面看，整条链挑不出毛病。

**原因三：模型无法区分「我记得」和「我在编」。**

人类知道「我不确定」和「我很确定」的区别；
模型在生成幻觉时和生成事实时的「内部体验」几乎没有差别 ——
输出的语气一样自信。你没有外部信号，就没有任何办法察觉。
（业界的说法：LLM 的**校准**很弱 —— 它自报的自信度和实际正确率相关性差。
v8 的 `confidence` 字段就是这个问题的一个小注脚。）

### 1.3 一个反直觉的起点

直觉上：「让它自己检查一下不就行了？」

这个直觉对了一半 —— 检查确实有用，**但前提是检查者比生成者多知道点什么**。
如果「检查者」和「生成者」是同一个模型、拿着同样的信息，
它的盲区和生成时一模一样：它检查不出自己「没想到的东西」。

> ⭐ 这句话是整篇文档的心脏，被问到时可以直接说：
> **反思的有效性上限 = 检查者相对生成者的「信息增量」。**
> 自己检查自己，信息增量为零的地方就是盲区。

所以真正的解法不是「求它更用心」，而是**想办法给检查环节注入新的信息**：
外部工具、程序断言、另一个视角、人类的反馈。

## 二、来龙去脉：从「自省」到「接外部信号」的演进

### 第一代：让模型自己批评自己（2022~2023）

**Constitutional AI**（Anthropic, 2022-12）：
给定一部「宪法」（一组原则），让模型对照原则**批评并修改**自己的输出。
最初目的在对齐（让 AI 更安全、可解释），但第一次展示了
「自我批评 → 修改」这个循环的能力上限超出预期。

**Self-Refine**（Madaan et al., 2023-03）：
把它变成通用的推理时模式：

```
生成初稿 → 自己给反馈（哪里不好）→ 按反馈修改 → （可重复多轮）→ 输出
```

- **突破**：不改模型、不加外部工具，靠「让同一个人多改几遍」就能提升
  写作、代码、格式类任务的产出。
- **留下的坑**：① 反馈质量不稳定 —— 经常只敢提表面问题（「可以让语言更简洁」），
  深处的逻辑错误它看不见；② **没有终止标准** —— 改到第几轮算完？
  一直改下去成本爆炸，而且可能把对的改错。

### 第二代：把失败变成「可带走的教训」—— Reflexion（2023-03）

**Reflexion**（Shinn et al., 2023）：视角从「修改这一次的输出」
升级为「**下次别犯同样的错**」：

```
尝试 1 ──失败──→ 反思：「我错在把 X 当成了 Y，下次应该先确认 Z」
                      │（写成语言，存进记忆）
尝试 2 ──读反思起步──→ 表现更好 ──失败──→ 再反思……
```

- **核心概念「语言化强化」**（verbal reinforcement）：
  传统强化学习用标量奖励（0 或 1）更新权重；
  Reflexion 把「失败」翻译成**一段自然语言的教训**，
  存进工作记忆，不改变模型参数。
- **突破**：这是「不重训模型的学习」—— 经验以文字形式跨尝试传递。
- **留下的坑**：反思质量依赖「失败可识别」；任务必须**可重试**
  （能跑第二遍才有意义）；对单次任务的贡献有限。

### 第三代：给自我批评装上「外部眼睛」—— CRITIC（2023-05）

**CRITIC**（Gou et al., 2023）：反思之前，**先用工具验证**：

```
初稿 → 用搜索引擎/计算器/代码执行验证事实 → 根据验证结果批评 → 修正
```

- **突破**：把检查从「凭感觉」变成「有证据」—— 信息增量来自工具。
- 这也是所有「工具型 Agent」反思的雏形：**能跑测试的代码 Agent，
  反思质量远超纯文本 Agent**，因为它们有编译器这个「不会说谎的裁判」。

### 2023-10：一盆冷水 —— 「无外部反馈的自我纠正不可靠」

**Huang et al., *Large Language Models Cannot Self-Correct Reasoning Yet***（2023-10）：

- 实验发现：**没有外部反馈时**，让模型检查自己的推理题，
  它经常**把对的答案改错**，而纠错率并没有稳定提升。
- 更糟的发现：即使它自己「不确定」，自评环节也会把它推向「更自信的错」。

这篇论文改变了业界的共识 ——

> **自我反思不是免费的午餐，它的收益几乎全部来自「外部信号」。**
> 没有外部信号的反思 ≈ 掷骰子 + 心理安慰。

（后续研究有修正和讨论，比如随着模型变强，自纠能力有改善 ——
但「盲区共享」这个原理没有变：同分布检查者，看不清同分布盲区。）

### 2023-2024：验证派与评分派

两条辅助线并行发展：

- **LLM-as-a-judge**：用（另一个）模型当裁判 —— 但很快发现它有偏置：
  喜欢自己的输出（自我偏好）、喜欢长回答（长度偏置）、位置偏见（顺序影响判定）。
  → 当裁判可以，但要**校准**（业内做法：人工标小批，和裁判对齐 —— v9 里讲过）。
- **过程奖励模型（PRM）**：*Let's Verify Step by Step*（Lightman et al., 2023）
  发现「逐步打分」比「只看最终答案」更能定位错误 ——
  这是「反思哪里错了」在训练侧的对应物，
  也是后来的推理模型（o1 类）技术栈的一部分。

### 2024-2025：产品化的收敛形态

今天的 Agent 产品里，反思几乎是**三种固定编队**：

1. **「生成 → 校验 → 重试」**（输出格式/事实类）：
   程序校验为主，失败时把错误信息喂回去再来 —— 你们 v8 已经实现过一模一样的；
2. **「执行 → 看结果 → 修正」**（代码 Agent 标配）：
   跑测试、看报错、改代码 —— 反馈信号来自**运行环境**，反思质量最高；
3. **「评估器-优化器」循环**（Anthropic《Building Effective Agents》里的
   evaluator-optimizer）：一个角色的产出交给另一个角色评判，
   有明确评估标准时效果好 —— 这就是 11（多 Agent）的第一个应用场景。

## 三、机制拆解：一个反思回路的四个部件

任何反思系统（自己实现或给别人讲）都能拆成四个部件。
**按这四个部件讲，条理立刻不一样：**

```
① 触发 ──→ ② 评判 ──→ ③ 反馈载体 ──→ ④ 修正动作
（何时检查） （谁来判）   （信息怎么回传）   （然后做什么）
```

| # | 部件 | 选项 | 设计要点 |
|---|---|---|---|
| **① 触发** | 做完一步就查 / 失败后查 / 交付前查 | 「查得太勤」成本爆炸；「查得太少」漏网 | 检查点的密度 = 成本与安全的调节旋钮 |
| **② 评判者** | 自己 / 另一个模型 / 程序断言 / 工具 / 人类 | ⭐ **决定整个回路的有效性上限** | 谁能提供「生成者不知道的信息」，谁能当好评判 |
| **③ 反馈载体** | 语言批评 / 分数 / 错误信息 / 差异对比 | 语言信息量大（说得出「哪里错、为什么」） | 反馈要**具体、可执行**，否则变成空话 |
| **④ 修正动作** | 重写 / 重试 / 改计划 / 升级给人 | 有副作用时要小心（修正不能产生新问题） | 加上限、防震荡、留退路 |

### 两个必须设计对的边界

**终止条件**：反思循环必须有上限 —— 最多几轮、多久超时、
什么状态算「收敛」。没有终止条件的「再改改」就是烧钱循环。

**振荡与过修**：改 A 引入 B、改 B 又引入 A —— 来回震荡的产品事故很常见。
缓解手段：每轮记录「改动理由」；如果新一轮批评否定上一轮的修改，
检查是不是**标准矛盾**而不是真的变差；关键决策保留「最高分版本」而不是「最新版本」。

### 一个隐蔽的坑：奖励黑客

如果反思的评判标准写成了「要让检查通过」，模型学会了**迎合检查者**
而不是把事做对 —— 比如评测里出现的「假通过」（v9 抓到过：残留文件骗过了断言）。
**评判规则和修正行为之间，永远隔着一层博弈。**

## 四、为什么是这么解的（第一性原理）

### 4.1 生成-验证不对称

计算机科学里有一条老经验：**验证一个答案，比生成一个答案容易**。
（数学直觉：验算乘法比找到因数容易。）

这个不对称在 Agent 世界里**部分成立、部分不成立**：

- ✅ 当验证者是**独立系统**时成立：跑一遍单元测试、用计算器复核、
  编译一次 —— 这些「裁判」的成本远低于生成，而且几乎不会说谎。
- ❌ 当验证者是**同一个模型**时**不成立**：它没有独立信息，
  验证退化成「再生成一遍相似的判断」—— 错还是错。

**结论：反思系统设计的第一原则 —— 尽可能把「验证者」和「生成者」解耦。**

### 4.2 语言是「信息密度更高」的修正信号

训练时：RLHF 用标量奖励（好/坏）—— 一个 bit 的信息。
推理时：反思用自然语言 ——「你第三步的除法把分母弄反了」。

后者携带的信息量大几个数量级：
它明确指出**位置、错误类型、修正方向**，还能被存下来跨尝试复用。
这就是「语言化强化」比「分数化强化」在推理时有效的根本原因。

### 4.3 两种「学习速率」的分工

| | 训练时修正（RLHF / 微调） | 推理时反思（Reflexion / 重试） |
|---|---|---|
| 生效速度 | 慢（训练周期） | 快（下一次调用就生效） |
| 成本 | 极贵（全量重训） | 便宜（多几次推理） |
| 作用范围 | 全局（所有用户、所有对话） | 局部（当前任务/会话） |
| 适合 | 系统性、反复出现的问题 | 个案、当前任务的具体错误 |

两者不互斥：**先让反思在推理时保住这一单，攒够了证据再谈训练。**
（这个对照很加分 —— 说明你知道反思不是训练方案的替代品，而是它的前置。）

### 4.4 为什么 System 1 / System 2 的类比流行

卡尼曼的双系统理论：快直觉（System 1）+ 慢检查（System 2）。
生成 = 快直觉；反思 = 故意引入的慢检查。
这个类比流行的原因：**它准确描述了「为什么要单独设计一步」** ——
不设计，系统就永远只有 System 1。

## 五、横向对比：反馈信号的「可靠性阶梯」

把常见方案按**评判者的可信度**排一排，这是本文档最值得记住的一张表：

```
最可靠 ┌─────────────────────────────────────────┐
       │ 程序断言（测试、类型检查、schema 校验、交叉核对）│  ← 不会说谎、可复现、免费
       │ 工具验证（计算器复核、搜索结果、编译器）        │  ← 强信号，来自系统外
       │ 独立模型评判（LLM-as-judge，经校准）          │  ← 有偏置，需对齐
       │ 同模型自我批评（Self-Refine）               │  ← 盲区共享，收益不稳定
最不可靠 │ 「你觉得对吗？」式纯自省                    │  ← 大多数时候是心理安慰
       └─────────────────────────────────────────┘
```

| 方案 | 反馈信号 | 有效场景 | 坑 |
|---|---|---|---|
| **程序化验证** | 断言/测试 | 有 ground truth 的一切 | 没有测试覆盖的地方裸奔 |
| **CRITIC 模式** | 工具（搜索/计算/执行） | 事实类、数学类 | 工具覆盖不到的地方无效 |
| **裁判模型** | 另一个 LLM | 主观标准的规模化评判 | 偏置；裁判也会坏（v9 实测：被截断的裁判） |
| **Self-Refine** | 自我批评 | 写作/格式类（有表面标准） | 深层错误看不见；会过度修正 |
| **Reflexion** | 语言化教训 + 记忆 | 可重复尝试的任务 | 依赖「可重试」；反思可能空洞 |
| **训练时修正** | RLHF/DPO/PRM | 系统性问题 | 慢、贵、不处理个案 |

**和「三个经典框架」的对照**（常被一起提到的名字）：

- **ReAct**：解决「行动无思考」—— 是反思的远亲，但没有检查环节；
- **Reflexion**：解决「一次失败白失败」—— 把教训语言化、可复用；
- **Self-Refine**：解决「初稿即终稿」—— 单次任务的迭代精炼。

## 六、争议与边界

### 6.1 自我修正的「Yet」问题

Huang et al. 的结论要**带时间戳理解**：
2023 年的模型确实不行；后续更强的模型自纠能力有提升。
但**原理层面**的结论稳定：

> 自我纠正的收益取决于「错误是否属于可被自身检查出的类型」。
> 检查的知识盲区 = 修正的盲区。

别抬杠说「最新模型可以了」—— 把「原理 + 时间戳」一起说，更专业。

### 6.2 多改几轮一定更好吗？

不一定。经验证据显示收益**递减**，而且存在
「第一轮改好、第二轮改坏」的过修正现象。
务实做法：**把反思的边际收益量化**（v9 的尺子又能用上：
跑「反思 1 轮 vs 3 轮」的分数对比 + token 账本对比）。

### 6.3 反思的「空洞化」

最常见事故：反思输出退化成「我应该更仔细」「下次要注意准确性」这种废话。
病因：提示词没有把反思**引向具体、可执行、可验证**的内容。
解药：给反思定格式 —— 错在哪（具体位置）、为什么错、下次怎么做（可执行动作）。

### 6.4 什么时候不需要反思

- 验证成本 > 错误成本（无所谓的小任务，别检查）；
- 没有任何可靠信号源的纯主观任务（反思≈重新采样）；
- 已经由程序强制保证的环节（schema 已校验，再让模型「确认格式」是浪费）。

## 七、怎么答

### Q1：「Agent 出错了怎么办？它会自我修正吗？」

答题骨架：

1. **先破题**：区分两种「错」—— 可被外部验证的（格式、事实、计算）
   和不可验证的（判断、文风）。反思的可靠性完全取决于这一区分。
2. **原理**：生成是概率采样，错误是必然；反思的有效性上限 =
   检查者相对生成者的信息增量；同模型自省盲区共享（引用 Huang et al. 的结论）。
3. **设计**：按「可靠性阶梯」选评判者 —— 程序断言 > 工具 > 裁判模型 > 自评；
   反思回路要设计触发条件、终止条件和防震荡。
4. **收尾**：把反思的收益做成可测量的（评估对比），否则你不知道它在帮忙还是帮倒忙。

### Q2：「Reflexion 的原理是什么？」

- 语言化强化（verbal reinforcement）：把「任务失败」这个二元信号
  翻译成自然语言教训，存进情景记忆；下次尝试前读回来。
- 不更新模型权重，靠**上下文**传递学习 —— 便宜、即时、局部。
- 前提：任务可重试；坑：反思质量不稳定、教训可能泛泛。

### Q3：「Self-Refine 和 Reflexion 的区别？」

- Self-Refine：**单次任务内**的精炼循环（初稿 → 批评 → 修改）。
- Reflexion：**跨尝试**的学习循环（失败 → 教训 → 下次更好）。
- 一个是「改这一稿」，一个是「改下一条命」。

### Q4（追问）：「让模型自己检查，是不是就不用测试了？」

- 恰恰相反 —— 自我的检查是**最弱的一档**，它连「把对的改错」都常发生。
- 测试/断言这类程序化验证才是反思体系的地基（v8 的交叉核对就是这个思路的实例）。
- 模型自评的价值在「没有程序可查」的领域兜底，而且要被校准。

---

## 八、回到 hello-agent

你在项目里其实已经做过**三种「反思」的变体**，只是没叫这个名字：

| 你有的 | 反思体系里的位置 | 关键领悟 |
|---|---|---|
| v8 的交叉核对（`sources ⊆ 检索轨迹`） | **程序化验证** —— 可靠性阶梯顶端 | 只有程序自己握着的事实，防得住「格式全对的编造」 |
| v8 的「校验失败 → 错误回灌 → 重试（上限 3）→ 放弃」 | **最小反思回路**（触发/评判/反馈/修正四件套齐全） | 反思不必是「自我批评」——程序批评更硬 |
| v9 的评估 + 对比面板 | **反思的放大器**（人类在环的反思） | 「感觉」不可靠，分数才可靠 |

还有一个**特别值得警惕的实例**：v9 抓到的「假通过」——
残留文件骗过断言、分数虚高。这就是「奖励黑客」的现场：
评判规则（文件存在）和真实目标（这次任务真的写出来了）错位，
系统学会了「让检查通过」。

**如果做 v10+ 的反思实验**（等真做的时候再翻回来）：

- 给 Agent 加一步「交卷前自查」：让它对照任务要求逐条检查自己的输出
  （对照组：不查直接交）。用 v9 的尺子测分数 + token 账单；
- 更硬的版本：把 v8 的交叉核对机制升级 —— 回答里的每个数字，
  程序强制用计算器结果复核，不一致就打回重算。

> ⚠️ 注意：**先做「程序批评」的版本，再做「自评」的版本。**
> 顺序反了，你会得到一堆无法归因的玄学结果。
