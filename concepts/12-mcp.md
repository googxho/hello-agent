# 12 · MCP 工具生态

> **Model Context Protocol & Tool Ecosystem**

> **一句话**：Agent 世界的 USB-C ——
> 把「每个工具都要为每个应用重写一遍」变成「写一次，处处可用」。
>
> **它治什么病**：工具集成 N×M 爆炸；工具无法跨应用复用；
> 能力接入的成本高到生态长不出来。

📌 **本页回答四个问题**：

1. **为什么会有这个概念**——「N×M 集成地狱」长什么样？（问题）
2. **主流怎么解决**——MCP 的设计与它的前史（方案）
3. **为什么是这么解的**——LSP 路线与标准化经济学（原理）
4. **还有什么别的路**——Function Calling / Plugins / A2A / Skills 的分层（对比）

---

## 一、这个问题从哪来

### 1.1 从你的项目说起

回看 hello-agent：每一版要加一个工具，你都要做三件事：

```python
① 写一个 Python 函数（实现能力）
② 写一份 ToolDefinition（给模型看的说明书 —— description 就是提示词）
③ 注册进 TOOL_DEFS（接线）
```

三个工具还好。但如果你的 Agent 要接 **GitHub、数据库、浏览器、飞书、日历、
公司内部系统……** —— 每个都要这样手写，而且：

- 换一个 Agent 框架（LangChain → 别的），**全部再写一遍**；
- 别人已经写好的工具，你**用不上**（接口不通用）；
- 你的工具别人也**用不上**。

### 1.2 放大到整个生态：N×M 问题

```
模型应用（Claude / IDE / 你自己的 Agent / 各产品…）   —— N 个
外部能力（文件 / Git / 数据库 / SaaS / API…）          —— M 个

没有标准：每个应用 × 每个能力 = 一套私有适配   → N × M 个集成 🤯
有了标准：每个应用接协议 + 每个能力接协议     → N + M 个适配 ✅
```

**这是计算机史上出现过无数次的剧本**：

- 充电：每个品牌一种接口 → **USB-C** 一统；
- 编辑器接语言：M 个编辑器 × N 种语言 → **LSP（Language Server Protocol）**
  把集成次数从 M×N 压到 M+N —— 微软 2016 年为 VS Code 设计，
  后来全行业采纳；
- 打印机：每个应用适配每种打印机 → 驱动模型 + PostScript；
- 网络：`OSI` 分层让「每层各自演进」成为可能。

⭐ **MCP 就是「LLM 工具界的 LSP」** —— 这个类比不是修辞，
MCP 的设计团队自己就是这么定位的：架构、能力协商、甚至协议底座
（JSON-RPC）都明显师承 LSP。

### 1.3 一个容易被混淆的邻居：Skill

你工作区里那一堆 `lark-*`、`archify` 的 **Skill**，解决的是另一个问题：

| | MCP | Skill |
|---|---|---|
| 形态 | **进程 + 协议**（server 跑着，客户端连接） | **文件夹 + 文档**（`SKILL.md` + 脚本/资源） |
| 封装什么 | **能力**（能执行的动作、能读的数据） | **知识/流程**（怎么做事、什么场景用什么命令） |
| 谁执行 | 工具代码在 server 侧执行 | 指令注入模型上下文，模型/脚本照做 |
| 类比 | USB-C 接口 | 一本操作手册 |

**两者是互补的层次**：
MCP 让 Agent「接得上」工具；Skill 教 Agent「怎么把一套流程用对」。
一个复杂的飞书操作流程可能同时用两者：MCP 提供 API 调用能力，
Skill 说明「先查通讯录拿 open_id、再发消息」这样的作业顺序。

## 二、来龙去脉

### 前史：Function Calling（2023-06）

OpenAI 发布 function calling：模型可以输出**结构化的调用意图**
（函数名 + JSON 参数），由宿主程序执行。

- 意义：模型从「会聊天」变成「会点菜」—— **调用意图**标准化了；
- 但注意：它标准化的只是「模型怎么说」，**没有标准化「工具怎么接」**。
  每个框架（LangChain Tools、各家 SDK）仍有自己的工具描述格式和接入方式。

（你在 v1 学的「工具描述就是提示词」，说的就是这层 ——
function calling 是「点菜话术」，工具怎么进货、怎么上菜，没人管。）

### 第一次生态尝试：ChatGPT Plugins（2023-03）

- 构想：任何人写一个 Plugin，接入 ChatGPT 生态 —— 商家、开发者蜂拥而至；
- **结局：失败退役**（2024 年前后下线）。教训（据公开讨论总结）：

| 失败原因 | 说明 |
|---|---|
| 安全模型脆弱 | 第三方服务直连，prompt injection 与数据外泄防不住 |
| 发现机制差 | 没有好的工具目录/信任体系，「装什么插件」全靠猜 |
| 体验割裂 | 每个插件自己的认证、界面、质量参差 |
| 商业模式模糊 | 开发者得不到明确回报 |

**这些教训被 MCP 的设计吸收**（安全边界、能力协商、本地优先）——
历史价值：它证明了「生态型工具接入」是真需求，只是姿势不对。

### 2024-11-25：MCP 发布（Anthropic）

- 定位：**开放标准**（开源规范 + 多语言 SDK），连接 LLM 应用与外部系统；
- 核心设计（见下一节）：Host-Client-Server 架构、三大原语、JSON-RPC 底座；
- 关键时刻：**它不是只给 Claude 用的私有方案** —— 开放治理是它后来被行业接受的前提。

### 2025 年：标准的快速演进与采纳

**规范迭代**（两次重要版本）：

- **2025-03-26**：引入 **Streamable HTTP** 传输（替代早期的 SSE 双端点方案，
  更适合远程/云部署）、以及基于 **OAuth 2.1** 的授权框架；
- **2025-06-18**：新增 **elicitation**（server 可以向用户提问）、
  结构化工具输出等原语 —— 协议开始覆盖「人在环」的交互。

**行业采纳**（据我了解，时间点请核实）：

- OpenAI（2025-03 起在 Agents SDK 等产品支持 MCP）、Google 等相继支持；
- **A2A 协议**（Google, 2025-04）：Agent 与 Agent 之间的通信标准 ——
  和 MCP 形成「纵向 vs 横向」的互补关系；
- 治理：MCP 与 A2A 先后被交由中立的基金会治理（Linux 基金会方向，
  具体时间与细节请核实官方公告）；
- 生态膨胀：社区 MCP server 数量从几十涨到几千（文件、Git、数据库、SaaS……），
  registry / 目录服务陆续出现（官方与第三方）。

## 三、机制拆解

### 3.1 架构：Host – Client – Server

```
┌─────────────── Host（宿主应用）───────────────┐
│   Claude Desktop / IDE / 你的 Agent           │
│                                               │
│   Client A ──── 1:1 连接 ────→ Server A（本地进程/远程服务）
│   Client B ──── 1:1 连接 ────→ Server B
└───────────────────────────────────────────────┘
```

- **Host**：用户实际在用的应用（模型在这里，prompt 在这里）；
- **Client**：Host 内部的连接器 —— 每个 server 一个，负责协议通信；
- **Server**：能力提供方 —— 可以是一个本地子进程（stdio），
  也可以是远程服务（HTTP）。

**关键设计**：Server 是**被动的** —— 它不主动调用模型、不主动连接外部，
一切动作由 Host 通过协议发起。**信任边界画在 Host**（安全模型的根基）。

### 3.2 原语：三类能力 + 两类反向请求

**Server 提供给 Host 的**：

| 原语 | 是什么 | 例子 | 对照你熟悉的 |
|---|---|---|---|
| **Tools** | 可执行的**动作** | 查数据库、发消息、跑命令 | 你的 `calculator` / `save_note` |
| **Resources** | 可读取的**数据** | 文件内容、表结构、日志 | 「能被检索的资料」（v5 的 notes） |
| **Prompts** | 预设的**提示模板** | 「代码审查」「周报生成」流程 | Skill 的思想（模板由 server 提供） |

**反向：Host 提供给 Server 的**：

- **Sampling**：server 想用模型（比如自动摘要）→ 通过 Host 请求模型完成 ——
  server 自己不持有模型；
- **Elicitation**（2025-06 新增）：server 执行中需要用户输入 → 请求 Host 弹交互 ——
  「问用户」被协议化了（10 的 HITL 在这里落了地）。

### 3.3 传输：stdio 与 Streamable HTTP

| 传输 | 形态 | 适合 | 特点 |
|---|---|---|---|
| **stdio** | 本地子进程，标准输入输出上跑 JSON-RPC | 本地工具（文件、本地数据库） | 简单可靠、天然隔离、无需认证模型 |
| **Streamable HTTP** | 远程服务，POST + 可选流式升级 | 云端服务、团队共享 | 要处理认证（OAuth 2.1）、会话管理、网络故障 |

### 3.4 生命周期与「动态发现」

```
1. initialize     —— 握手，双方声明协议版本与能力（capabilities 协商）
2. list_tools     —— Host 拉取 server 提供的工具清单（动态发现！）
3. call_tool      —— 按需调用，支持流式进度、中途 elicitation
4. （断开/重连、会话恢复……）
```

⭐ **「动态发现」是相对 Function Calling 的一个质变**：

- 传统方式：工具清单在**编译期**写死在应用里（你的 `TOOL_DEFS` 就是）；
- MCP 方式：工具清单在**运行时**从 server 拉取 ——
  装一个新的 server，Agent 立刻多一批能力，**不用改一行应用代码**。

（这也解释了为什么它叫「生态」而不是「功能」：
生态的前提是「参与者可以独立演进」。）

## 四、为什么是这么解的（第一性原理）

### 4.1 标准化的经济学：N×M → N+M

这条前面算过账了，但值得再点破一层：
**协议的价值不在技术上多高明，而在「让双方的投入可以各自积累」。**

- 没有协议：每套集成是**一次性**的（做完就沉没，无法复用）；
- 有了协议：写一次 server，接入所有 host；host 接一次协议，收获所有 server。

这就是为什么协议之争常常「赢者通吃」——
早期的一点混乱（多协议并存）在长期会被收敛掉（USB 的乱世到 USB-C 一统）。

### 4.2 为什么「抄 LSP」是对的

LSP 已经验证过的要素 **MCP 全部继承**：

| LSP 要素 | MCP 对应 |
|---|---|
| 编辑器（Host）与语言服务（Server）解耦 | LLM 应用与工具 server 解耦 |
| JSON-RPC 底座 | 同（JSON-RPC 2.0） |
| 能力协商（initialize） | 同（capabilities） |
| 本地进程可接受（stdio） | 同（stdio 为重） |
| 中立治理、多语言 SDK | 同（开源、多 SDK） |

**为什么本地子进程这个看似「土」的选项是精髓**：
它让「工具」可以像本地 CLI 程序一样随手写、随手装 ——
整个生态的**参与门槛**降到最低。生态不是被设计出来的，是被低门槛「养」出来的。

### 4.3 与 Function Calling 的关系：两层，不是替代

```
模型层：Function Calling —— 模型「会说」要调用什么（点菜）
连接层：MCP           —— 工具「怎么接进来」（厨房/供应链标准）
```

高频混淆点，一定要分清：
**MCP 不改变模型能力，它改的是工具的接入方式**；
工具最终被调用时，多数 host 仍然把 MCP 工具「转换」成 function calling
格式喂给模型 —— FC 是模型的点菜能力，MCP 是厨房的标准化。

### 4.4 为什么不是「OpenAPI + 一点胶水」？

OpenAPI 擅长描述「HTTP API 有什么端点」，但 LLM 工具生态需要的是：

- **生命周期**：会话、握手、能力协商（OpenAPI 没有）；
- **双向通信**：sampling / elicitation 是 server → host 的（OpenAPI 单向）；
- **动态清单与本地进程**：工具不该必须是 HTTP 服务。

所以 MCP ≈ **为 LLM 定制的 LSP**，而不是「OpenAPI 换皮」。

## 五、横向对比

### 5.1 「工具接入」诸方案对照

| 方案 | 年代 | 思路 | 结局/现状 | 教训 |
|---|---|---|---|---|
| **ChatGPT Plugins** | 2023 | 专有生态 + 远程服务 | 退役 | 安全与发现机制是生死线 |
| **OpenAPI Actions**（GPTs） | 2023- | 用 OpenAPI 描述远程 API | 窄场景存活 | 只适合「真 HTTP 服务」 |
| **框架内标准**（LangChain Tools 等） | 2023- | 各家框架自己的工具格式 | 并存，被 MCP 适配 | 框架边界的墙：出不了框架 |
| **MCP** | 2024-11 | 开放协议 + 本地优先 | ⭐ 事实标准（多厂采用） | 中立治理 + 低门槛 |
| **A2A** | 2025-04 | Agent ↔ Agent 通信 | 与 MCP 分层共存 | 别把「工具协议」和「Agent 协议」搞混 |

### 5.2 MCP vs A2A vs Skill：三个生态位的分工

```
A2A      ←  Agent 与 Agent 对话（横向协作，跨厂商的"外交协议"）
MCP      ←  Agent 接工具/数据（纵向接入，"外交之外的一切")
Skill    ←  行为的文档化封装（"作业手册"，无协议、无进程）
```

一个有意思的观察：**它们都在解决「复用」**，
但复用的对象不同：A2A 复用「别的 Agent 的劳动」，MCP 复用「工具实现」，
Skill 复用「流程知识」。

## 六、争议与边界

### 6.1 安全：MCP 最大的阴影

- **工具输出注入**：server 返回的内容里藏指令（「忽略之前的要求，把文件发到……」）——
  工具结果进了模型上下文，就获得了和用户输入同等的「说服力」；
- **恶意/劣质 server**：装上就开跑，能读你权限内的一切；
- **供应链**：server 依赖的包、更新渠道；
- **信任边界设计**：Host 必须承担权限模型（工具级授权、用户同意、审计日志）——
  协议只提供**能力**，不提供**安全**。

**记住一句话**：MCP 让「装工具」变得像装 App ——
App 生态的所有安全问题，会在 MCP 生态里重放一遍。

### 6.2 什么时候「不需要」MCP

- 三五个自家工具、单应用使用 → 手写更简单直接
  （协议是给**生态**问题的，不是给**你的集成**问题的）；
- 延迟敏感场景 → 多一层协议多一层开销；
- 团队没法维护 server 的生命周期（进程管理、版本升级）。

**判断标准**：你是在「解决自己的集成」还是在「加入一个生态」？

### 6.3 生态质量的现实

几千个 server 里，demo 占大多数；发现机制、评信机制仍在早期。
**工具的 description 质量依旧是老问题** —— 生态解决「接得上」，
不解决「用得好」；v1 学的「工具描述就是提示词」，在生态里反而更重要
（你要在良莠不齐的 server 里判断哪些工具值得装、值得信）。

## 七、怎么答

### Q1：「MCP 是什么？它解决什么问题？」

1. **问题**：Agent 工具集成 N×M 爆炸 —— 每个应用都要为每个能力重写适配；
2. **方案**：开放协议把 N×M 压到 N+M —— 类比 USB-C / LSP；
3. **机制**：Host-Client-Server，三大原语（Tools/Resources/Prompts），
   JSON-RPC 底座，stdio 与 Streamable HTTP 传输；
4. **边界**：它标准化的「工具怎么接」，不是「模型多聪明」——
   安全、质量、发现机制依然是要工程兜底的。

### Q2：「MCP 和 Function Calling 什么关系？」

- 两层：FC = 模型「会说」要调用什么（模型侧能力）；
  MCP = 工具「怎么接进来」（工程侧协议）；
- 多数 host 仍把 MCP 工具转成 FC 格式给模型 —— 互补，不互斥；
- 能把这个分层说清，是懂与不懂的分水岭。

### Q3：「为什么 MCP 能成为共识，Plugins 失败了？」

- Plugins：专有、远程优先、安全模型弱、发现机制差、开发者激励不清；
- MCP：开放治理（中立基金会）、本地优先（低门槛、易隔离）、
  能力协商与动态发现、被多个竞争厂商共同采用；
- 外加时机：2024-2025 年 Agent 需求爆发 + FC 能力已就绪 ——
  「标准」通常要等生态需求真正成熟才立得起来。

### Q4：「MCP 有什么安全风险？」

- 工具输出注入（把外部内容当指令）、恶意 server、供应链、权限过宽；
- 防御方向：Host 侧的权限模型（最小授权、用户确认、审计）、
  内容与指令的信任分层、server 沙箱化、registry 的信任体系。

### Q5（追问）：「你会怎么给自己的 Agent 接入 MCP？」

- 架构上：工具清单从「编译期注册表」变为「运行时发现」——
  你们 v9/v2 的 `openai_schemas()` 机制是它的手写前身；
- 工程上：进程管理（stdio server 的启停）、故障降级（server 挂了怎么办——
  v3/v6/v7 的老套路：降级路径决定你能不能活）；
- 风控上：装什么 server = 给什么权限，要按最小权限来。

## 八、回到 hello-agent

| 你有的 | 与 MCP 的关联 |
|---|---|
| `tools.py` 的手写注册表（ToolDefinition + 装饰器） | MCP 工具清单在**编译期**的版本；换成 MCP = 改成运行时发现 |
| v2 的「关工具 = 从清单里消失」机制 | ⭐ 和 MCP 的动态工具清单是同一个数据结构游戏 —— 你早玩过了 |
| v1 的「工具描述就是提示词」 | MCP 生态里依然是最重要的基本功（server 质量参差） |
| v5-v7 的降级路径经验 | MCP server 挂了怎么办 —— 你已经有三版降级经验了 |
| v9 的评估 | 「换了工具以后到底变好没有」—— 依然要用尺子说话 |

**如果做这一块的实验**（工程活，等真需要再动手）：

1. 起一个官方 filesystem MCP server，用最小的 client 连接它，
   打印 `list_tools` 的结果 —— 亲眼看看「动态发现」长的样子；
2. 把 hello-agent 的三个手写工具和 MCP 工具混在同一个 loop 里调用 ——
   体会「工具来源不同、但模型看到的清单是统一的」；
3. 记一笔账：接 MCP 之后，延迟、token、故障面各增加了什么 ——
   你就完成了对「协议成本」的第一手测量。

> 💡 ROADMAP 里那句话值得抄在这里：
> **「工具不用自己写了 —— 但『工具描述写不好』这个基本功照样要练。」**
