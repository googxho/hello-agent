# 08 · 规划与任务拆解

> **Planning & Task Decomposition**

> **一句话**：复杂任务失败，不是因为它「笨」，而是因为它没有「全局」——
> 规划，就是把全局从模型的脑子里请出来，写在纸面上。
>
> **它治什么病**：走一步看一步，任务一长就迷路、丢步骤、绕圈。

📌 **本页回答四个问题**（读的时候心里默念这四个）：

1. **为什么会有这个概念**——上一版撞了什么墙？（问题）
2. **主流怎么解决**——方案的来龙去脉？（方案）
3. **为什么是这么解的**——原理和必然性？（原理）
4. **还有什么别的路**——流派对比与争议？（对比）

最后一节「怎么答」把全文压缩成**能直接说出口的话**。

## 一、这个问题从哪来

### 1.1 一个具体的翻车现场（本项目实测）

v9 的评估里有一条用例叫 `multi-step`，任务只有两步：

```
第一步：查询当前时间
第二步：把时间写进一个笔记文件
```

就这么点事，在「坏提示词」实验里**两步全挂**，是整卷 9 条用例里最先趴下的一类。

这不是模型不会用工具（另外 7 条单一任务的用例它都过了）。
它暴露的是：**模型没有「把任务当成一个整体」的视角** ——
它每一步都只看眼前，走一步算一步，任务稍微一长，就开始丢步骤。

### 1.2 根子在哪：三个物理事实

**事实一：它一次只决定「下一个词」。**

LLM 是自回归的：给定前面的文本，预测下一个 token。
这意味着它「心里」没有一张任务地图 —— 有的只是**到目前为止的文本**。
每一步都是局部最优，而局部最优的串联 ≠ 全局最优。
第三步的一个理解偏差，到第十步会被放大成完全走错路（**误差累积**）。

**事实二：注意力是有预算的。**

就算把任务目标写在第一句话里，执行到第 20 轮时，
目标在上下文里已经「离得很远」了 —— 注意力被最近的内容占满。
这不是错觉，有实证：论文 *Lost in the Middle*（Liu et al., 2023）
发现模型对长上下文**中间部分**的信息利用率明显下降，呈 U 型分布。

**事实三：它没有「回头看」的机制。**

人类做长任务会自然地在脑子里维护「目标 → 当前进度 → 下一步」，
发现走偏了会退回去重来。模型不会 —— 除非你把「回头看」也变成上下文里的动作。

### 1.3 用控制论翻译一下（这个类比很好用）

把 Agent 执行任务想象成**控制一台机器**：

| 模式 | 对应 | 特点 |
|---|---|---|
| **开环控制** | 一次性计划，然后埋头执行 | 计划错了，一路错到底，没有任何修正机会 |
| **反馈控制** | ReAct（边想边做） | 每步看观测，能应对意外 —— 但容易「短视」、绕圈 |
| **模型预测控制（MPC）** | 计划 + 滚动重规划 | ⭐ 实践收敛解：**计划给方向，反馈改路线** |

控制工程里早就知道：纯开环对误差零容忍，纯反馈在复杂目标下会抖。
真实系统用 MPC —— **先预测一段，执行一段，根据反馈修正，再预测**。
Agent 的规划，最后也收敛到了同一个结构。

### 1.4 那不规划行不行？

行 —— 但有条件。任务**短**（1~2 步）、环境**快变**、每步都能立刻看到结果，
那么「边做边看」反而更灵活。

问题在于：真实任务往往步骤多、有依赖关系（A 做完才能做 B）、
且中间没有人类检查点 —— 这些条件下，没有全局视野的代价会指数级放大。

> 💡 **一句话记住**：规划解决的从来不是「模型不够聪明」，
> 而是「再聪明的一次决策，也管不了它从未见过的全局」。

## 二、来龙去脉：五代方案的演进

> 这一节是「概念史」。每一代都在解决上一代的坑，
> 又都留下了新坑 —— 这就是技术演进的真实样子。

### 第 0 代：直接回答（2022 之前）

「问题进，答案出」。复杂一点的题立即崩 —— 因为模型必须在生成第一个字之前，
就把所有中间步骤「暗中」算完，没有草稿纸。

### 第 1 代：让它在「纸」上想 —— CoT（2022）

**Chain-of-Thought Prompting**（Wei et al., 2022）：
不直接要答案，而是让模型把推理步骤写出来。

```
❌ 「小明有 5 个苹果，吃了 2 个，又买了 3 倍于剩下的…答案？」
✅ 「让我们一步一步想：第一步…第二步…所以答案是…」
```

- **突破**：中间 token 变成了「草稿纸」，复杂推理准确率大幅提升。
  （Zero-shot 版：Kojima et al. 2022，就是那句著名的 *Let's think step by step*。）
- **留下的坑**：**想和做是分离的**。推理链再漂亮，它也只是「说」——
  不能查资料、不能跑代码、不能验证。链条再长，也是闭门造车。

### 第 2 代：想和做交织 —— ReAct（2022）

**ReAct: Synergizing Reasoning and Acting**（Yao et al., 2022）：

```
Thought: 我需要知道现在几点 → Action: get_current_time
Observation: 14:30                          ← 真实世界的结果喂回来
Thought: 好，现在把时间写进文件 → Action: save_note
...
```

- **突破**：让「思考」和「行动」交错发生，观测结果实时修正路线。
  它同时治好了两边的病：纯行动（瞎走）和纯思考（闭门造车）。
- **留下的坑**（⭐ 正是我们这篇的主题）：**它没有「先想完」这一步**。
  每一步的 Thought 只考虑「下一步做什么」，**全局一致性无人负责**。
  任务一长，它就开始漂 —— 现象就是丢步骤、绕圈、忘记最初的目标。

### 第 3 代：先想完再做 —— Plan-and-Solve（2023）

**Plan-and-Solve Prompting**（Wang et al., 2023）：
让模型**先写出一份完整的计划，再照着计划执行**。

- **突破**：很多任务里，「先列步骤」这一个动作就能把准确率提上去 ——
  因为计划的文字本身，成了后续每一步都能看到的「全局」。
- **留下的坑**：**计划是「一次性」的**。世界变了、执行失败了，
  计划不会自动改 —— 变成了开环控制（见 1.3）。

> **工程上的分体化**（2023 年，LangChain / BabyAGI 这一波）：
> 把「计划」和「执行」交给**两个不同的调用**：
> planner 出计划 → executor 逐步执行 → （可选）replanner 审视进展。
> 这就是 **Plan-and-Execute** 架构。

### 2023 年中的插曲：自治 Agent 大爆发 —— Todo List 的胜利

2023 年 3~4 月，**AutoGPT** 和 **BabyAGI** 火了。大众第一次看到：

```
目标 → 生成任务清单 → 循环：取一个任务执行 → 反思 → 生成新任务 → …
```

- **贡献**：奠定了实践定式 —— **「待办清单 + 循环执行」是撑得住的骨架**。
- **教训**：没有边界的目标分解会「迷路」——绕圈、重复劳动、烧钱。
  光有清单没有收敛条件，是灾难。

（这段历史在 ECOSYSTEM 的时代里值得单独记一笔：
**学术界在做「怎么让计划更对」，产品界先撞到的是「怎么让循环别失控」。**）

### 2023 年中的另一条路：搜索式规划 —— Tree of Thoughts

**Tree of Thoughts**（Yao et al., 2023）：把「想」从一条链变成一棵树 ——
每个节点是一个「想法」，可以评估好坏、可以回退、可以做深度/广度搜索。

```
       想法A ──┬── 想法A1 ✓
    ┌── Node ─┤
起点       └── 想法A2 ✗ ← 评估后剪掉，换分支
    └── Node ──── 想法B1 …
```

- **突破**：允许**试错和回退**，推理从「一发定生死」变成「搜索」。
  搭配 LATS（2023-10，Tree of Thoughts + ReAct + 反思）在解题任务上很强。
- **为什么真实 Agent 里少用**：树搜索成立的前提是「状态可模拟、可评估、可回退」。
  而真实世界：动作不可逆（发了的邮件收不回）、状态不可重置、
  评估中间状态成本极高。**所以它活在了「解题」里，没活在「做事」里。**

### 2024 至今：工程收敛 —— 计划 + 滚动重规划

几条线汇合成了今天的实践共识：

- **Anthropic《Building Effective Agents》**（2024-12）把常见结构归纳成五种工作流，
  其中 **orchestrator-workers**（中央规划者 + 工人）和
  **evaluator-optimizer**（生成 + 批评循环）都和规划相关；
- **LangGraph** 把「计划 → 执行 → 重规划」变成显式的状态机循环（plan-and-execute 模板）；
- **现代编程 Agent**（Claude Code 等）几乎都维护一个**外显的 Todo 列表**：
  边做边更新，用户能看到「做到哪了」——计划从「私房草稿」变成了「工作台」；
- **Deep Research 类产品**（2025）：先给用户一份研究计划（可以改！），再执行，
  执行中动态修正 —— **计划第一次成了「人机接口」**。

### 2025：推理模型 —— 把规划「压进」token 里

o1/o3 这类推理模型用很长的内部思考（test-time compute）来自我规划，
**一部分场景下不再需要外显的计划结构** —— 规划发生在思维链里。

但注意边界：**跨轮次、跨工具、要给人看、要给人改、要被程序检查**的部分，
外显计划仍然不可替代 —— 因为「在模型脑子里」的东西，你无法确认、无法编辑。
（2025 年的主流答案是「两者都要」：能力强的模型负责想得深，系统负责记得住、看得见。）

## 三、机制拆解：把「规划」拆成六个设计决定

如果你要自己实现一版规划（比如给 hello-agent 写 v10），
真正要拍板的就是下面六件事。**每一件都值得展开讲。**

| # | 维度 | 要回答的问题 | 常见选项 |
|---|---|---|---|
| 1 | **载体** | 计划存在哪？ | 提示词里 / 上下文消息里 / 外部文件 / 结构化对象（JSON） |
| 2 | **粒度** | 拆到多细？ | 只到阶段（粗）/ 每一步都写死（细） |
| 3 | **形态** | 什么结构？ | 线性清单 / DAG（可并行）/ 树（可回退） |
| 4 | **生成时机** | 何时做计划？ | 先验（开始前一次性）/ 增量（边走边定）/ 混合 |
| 5 | **绑定强度** | 计划是命令还是参考？ | 契约（必须执行）/ 宣言（仅供参考） |
| 6 | **更新机制** | 计划是死是活？ | 静态 / 动态重规划（何时、如何） |

展开两个最关键的：

### 载体：为什么主流是「写进上下文」

- **可干预**：写在上下文里的计划，人类能读（确认/修改）、程序能校验（解析结构）、
  模型能更新（改状态）。**藏在模型脑子里的计划，以上三件事全做不到。**
- **持久化**：如果要跨进程（重启后继续任务），计划得落盘 ——
  和 v4 的会话持久化是同一类问题。
- 经典设计：把计划做成**工具调用**（`submit_plan`），
  或让模型维护一段结构化的 todo 区域 —— 你们在 v8 已经学过「工具即 schema」，
  这个套路可以直接复用。

### 粒度与重规划：两个最容易翻车的地方

- **粒度**：太粗没有指导意义，**太细会僵化** —— 执行中发现「计划的第 5 步根本不成立」，
  而计划是契约的话，要么硬着头皮做，要么推翻重来（都很难看）。
  主流折中：**粗计划 + 细执行** —— 计划只定阶段和大方向，细节留给执行时生成。
- **重规划设计**（高频问题）：
  - **触发条件**：步骤失败？观测和预期不符？定期审视？（不能每步都重规划，成本爆炸）
  - **防震荡**：重规划不要推倒重来，而是**最小修订** —— 保留已完成部分，
    只改后面受影响的步骤。否则会出现「改来改去回到原点」的死循环。
  - **进度记账**：哪些完成了、哪些作废了 —— 重规划需要一份可信的状态账本。

## 四、为什么是这么解的（第一性原理）

把这节当成「万一被追问原理」的弹药。

### 4.1 规划的本质：一次上下文工程，不是一次能力升级

模型的能力边界没有变。变的是**每个 token 生成时它能看到什么**：

```
无规划：任务书 → [黑盒里连续决策] → （鬼知道经过了什么）→ 结果
有规划：任务书 → 计划（可见！）→ 每步执行时都带着 [任务书 + 计划 + 进度] → 结果
```

「把全局放进局部视野」—— 这就是 planning 的全部秘密。
也正因如此，它才和 **08 之前学过的所有东西**（压缩、持久化、检索）
是同一族技术：**都在管理「此刻模型眼前有什么」。**

### 4.2 分解为什么有效：两个数学直觉

- **失败率的乘性**：一个 10 步任务，每步 90% 靠谱，整体成功率是 $0.9^{10} \approx 35\%$。
  分解 + 每步校验，等于把「一个大错」变成「小错可早期拦截、单步可重试」。
- **注意力预算**：每一步只需要装「当前步相关信息」。
  与其在一个上下文里硬塞全任务，不如每步只给该步的材料（回到 *Lost in the Middle*）。

### 4.3 外显化 = 可审计、可协作、可教

- 计划是**给人看的**：用户可以确认方向（Deep Research 模式）；
- 计划是**给程序的**：可以被解析、校验、并行调度（LLM Compiler 的 DAG 思想）；
- 计划是**给多个 Agent 的**：共享的工单比口头传递可靠（这是 11 的主题伏笔）。

## 五、横向对比：两大流派与它们的混合

| 流派 | 代表 | 计划何时生成 | 遇到意外 | 适合 | 坑 |
|---|---|---|---|---|---|
| **反应式** | ReAct、几乎所有 function-calling Agent 的默认形态 | 不预先生成，每步临时决定 | 立即就地调整，灵活 | 短任务、探索型、环境不确定 | 长任务迷路、丢步骤、上下文漂移 |
| **先计划后执行** | Plan-and-Solve、Plan-and-Execute、BabyAGI | 开工前一次性生成 | 计划不动，硬做或人来救 | 步骤明确、依赖清晰、需要人确认 | 计划僵化；做错了开环放大 |
| **计划 + 重规划** ⭐ | LangGraph plan-execute、现代编程 Agent | 开工前生成，执行中滚动修正 | 检测偏离 → 最小修订计划 | **长任务、真实生产**（实践收敛解） | 重规划成本与震荡；触发条件难调 |
| **搜索式** | Tree of Thoughts、LATS | 边想边展开树，评估后剪枝 | 回退到上一分支 | 可模拟可评估的解题环境 | 动作不可逆的真实任务用不了；成本高 |
| **并行式** | LLM Compiler | 编译成任务 DAG | 无依赖的子任务并行跑 | 大量可并行的工具调用 | 依赖关系分析错了全乱套 |

**还有一个更本质的对照维度：显式 vs 隐式。**

| | 显式规划（写下来） | 隐式规划（模型脑内） |
|---|---|---|
| 形态 | 上下文/文件里的计划 | 推理模型的长思维链 |
| 擅长 | 长任务、跨轮次、人审、程序消费 | 单次高难度推理题 |
| 弱点 | 有额外 token 成本、需要设计结构 | 不可见、不可改、不可跨轮保持 |

> 💡 结论不是「哪个好」，而是**看需求在谁那边**：
> 需要「看得见、改得动、接得上人」的任务，永远需要显式计划 ——
> 这跟模型强弱无关，是工程需求。

## 六、争议与边界（进阶理解）

### 6.1 「LLM 到底会不会规划？」之争

2025 年苹果的论文 *The Illusion of Thinking* 提出：
模型在任务复杂度超过某个阈值后推理性能崩塌，
质疑它是在「真规划」还是「模式匹配见过的解法」。
这篇论文本身争议很大（被质疑实验设置），但它提醒了一个务实的态度：

> **别把 planning 当智力问题，当工程问题。**
> 不纠结「它是不是真会想」，只问「这套结构在什么条件下稳定提升结果」——
> 用评估说话（v9 的尺子）。

### 6.2 什么情况下**不该**做规划

- 任务 1~2 步能完（规划是纯税：多的调用、多的延迟）；
- 环境快变、步骤高度不确定（细计划写完就过期）；
- **过度规划的陷阱**：把每一步都写死 = 假控制感 ——
  现实会把每步都推翻一次，最后你维护的是一个没人看的计划。

### 6.3 常见翻车模式清单（都是真实项目里的）

| 症状 | 病因 | 处理 |
|---|---|---|
| 计划做出来，执行时忘了 | 计划放在上下文最前面，第 10 轮后注意力已稀释 | 每轮重读计划 / 把「当前步骤」置顶 |
| 一直重规划，原地打转 | 没有「最小修订」约束，每次推倒重来 | 锁定已完成部分，只改受影响的后缀 |
| 计划永远对不上现实 | 计划太细 | 粗计划 + 细执行 |
| 简单任务也先列 10 步 | 没有分流 | 按复杂度决定是否规划 |

## 七、怎么答（把上面的内容变成话）

### Q1：「说说你理解的 Agent 规划能力？」

答题骨架（约 1 分钟）：

1. **问题的本质**：LLM 是自回归的局部决策器 —— 每一步都只有局部视野；
   而长任务需要全局一致性。这个矛盾就是 planning 要解决的。
2. **解法的一句话**：把全局「外显化」—— 写进上下文，
   让每一步执行时都能看到目标、计划、进度。本质是上下文工程。
3. **演进线**：CoT（在文字里想）→ ReAct（想和做交织，但短视）→
   Plan-and-Execute（先想完再做，但僵化）→ 计划 + 滚动重规划（实践收敛解）。
4. **边界感**：短任务不用规划；计划粒度要「粗计划细执行」；
   重规划要防震荡。

### Q2：「ReAct 和 Plan-and-Execute 怎么选？」

- ReAct 强在**适应性**：每步看观测，环境不确定时是唯一理智的选择；
  弱在**全局**：长任务丢步骤。
- Plan-and-Execute 强在**全局与可控**：计划可审、进度可查、步骤有依赖也能排；
  弱在**僵化**：世界变了它不改。
- 实践答案：**混合** —— 粗计划管方向，执行步内用 ReAct 式反应；
  加一条「偏离检测 → 最小修订」的重规划回路。

### Q3：「计划执行到一半发现不对，怎么办？」

- 先讲**触发条件**（什么时候承认「计划错了」）：步骤连续失败 / 观测与预期不符 /
  定期审视。
- 再讲**修订方式**：最小修订 —— 锁定已完成，只动后缀；从原点重来是禁忌。
- 最后讲**成本与控制**：重规划本身是额外调用；要有上限（不能无限改），
  改了几次还不行要**升级给人**（人机协同的伏笔 —— 10 的主题）。

### Q4：「Tree of Thoughts 为什么没成为主流 Agent 架构？」

- 它需要三个前提：状态可模拟、中间态可评估、可回退。
- 真实 Agent 的动作大多**不可逆**（发邮件、改文件、下单），
  而且评估中间态成本极高。
- 所以它活在「解题环境」里；真实任务收敛到了「计划 + 重规划」这条线上。
  （说出这个「为什么不同的规划技术适配不同环境」，是区分背题和真懂的关键。）

## 八、回到 hello-agent

你在这个项目里已经摸到过规划的两面：

| 你有的 | 和规划的关联 |
|---|---|
| v1 的主循环（模型自己决定何时收工） | 最原始的「反应式」——无计划 |
| v9 实测：`multi-step` 最先趴下 | 规划要解决的病，你**亲脚踩过** |
| v4 的 session.json | 计划要持久化的话，技术底座你已经有了 |
| v8 的「工具即 schema」 | 计划落地成 `submit_plan` 工具的现成套路 |
| v9 的评估尺子 | 验证规划有效性的唯一可信手段（改前先扩长任务用例！） |

**ROADMAP 里 v10 的墙**（提前知道，到时候不慌）：

- 计划做出来但执行偏了 —— 计划是「宣言」，执行是另一套循环，两边怎么对齐；
- 计划要不要给用户确认 —— 人机协同的种子（10 的伏笔）；
- 「计划好不好」比「答案对不对」更难判 —— 长任务用例怎么设期望；
- 规划多花的 token 值不值 —— 用 v9 的账本说话。

**最小验证思路**（成本从低到高，动手时挑一个）：

1. **零代码**：`prompts/system.md` 里加一句「动手前先列出步骤」，
   用 v9 的尺子跑一遍完整评估 —— 先看「提示词级规划」有没有用；
2. **小代码**：给用例集加 3~4 步的长任务（v9 动手练习 4 预留的题），
   对比「有规划 vs 无规划」的分数差；
3. **完整版**：计划做成结构化工具调用（`submit_plan`），
   执行循环每轮把「当前步骤」置顶 —— 这时你才真正在做 v10 的正题。

> ⚠️ 顺序不要反：**先用尺子，再改架构。**
> 没有 v9 的评估，你无法回答「规划到底让什么变好了」。
