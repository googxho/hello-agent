# 第一组 · 它终于能读你的资料了

## 实验 1：它读到了你的笔记 ⭐⭐⭐

**🎯** 同一份笔记，v4 说「我没有读取笔记的能力」，v5 能答出来。

**⏱ 2 分钟**

**📋 步骤**

**起点** 🆕 新会话（用下面这条命令启动）

**第 1 步** —— 启动（带上 `LLM_PERSIST_ENABLED=0`，从白纸开始）：

```bash
LLM_PERSIST_ENABLED=0 python main.py
```

✅ 横幅里应该有红字：`持久化 已关闭 —— 退出就忘光`

**第 2 步** —— 让它存一条笔记：

```
请把这句话存成笔记，标题叫 chenxi：晨曦项目本周五交付第一版，负责人是老王。
```

✅ 它调用 `save_note`，报告「已保存到 chenxi.md」。

**第 3 步** —— 问一个**只有笔记里才有**的问题：

```
我的笔记里，晨曦项目什么时候交付？负责人是谁？
```

**👀 你应该看到**

```
  🔍 检索 晨曦项目 交付 → 3 段命中（最高分 2.41 / 1.29 · 扫描 6 块 · 0.8 ms）
      chenxi.md:3（chenxi） · 命中 晨曦、曦项、项目、交付
```

然后它带着**出处**回答：

> 根据你的笔记（chenxi.md）：
> - **交付时间**：本周五交付第一版
> - **负责人**：老王

**💡 所以呢**

**它多了一个动作：先找，再答。**

```
问题 → 检索器 → 最相关的几段 → 塞进上下文 → 回答
```

而 v4 在这一步的结局是：**「我没有读取或检索已有笔记的能力」** ——
注意，那份笔记当时就躺在它的 `notes/` 目录里，离它只有几厘米。

> 问题从来不是它「不想看」，而是**没人给它一把钥匙**。

## 实验 2：它是怎么「找」的 ⭐⭐

**🎯** 检索不是一个黑盒 —— 每一段结果都有**出处**和**命中的词**。

**⏱ 1 分钟**

**起点** ↩️ 接着实验 1 的对话（不用重启）

**📋 步骤**

随便问点跟笔记相关的事：

```
笔记里还提到什么别的内容吗？
```

再敲一次：

```
/knowledge
```

**👀 你应该看到**

检索那几行里，每段结果都带着三样东西：

```
      chenxi.md:3（chenxi） · 命中 晨曦、曦项、项目、交付
      ↑ 出处：哪个文件哪一行    ↑ 命中了哪些词
```

`/knowledge` 显示：

```
资料目录  .../agent-v5/notes · 1 个文件 / 3 块 · 索引重建过 1 次
```

**💡 所以呢**

这三样东西不是装饰：

| 它告诉你 | 为什么重要 |
|---|---|
| **哪个文件哪一行** | 你可以自己去看原文，核对它有没有在编 |
| **命中了哪些词** | 你能判断「为什么这段被选中」—— 调不动的东西，就是信不过的东西 |
| **得分** | 一眼看出「最相关」和「陪跑」的差距（2.41 vs 0.35） |

**没有这些，检索就是个黑盒。** 结果对不对，你只能靠感觉。

# 第二组 · 亲手撞天花板

## 实验 3：换个说法，它就找不到了 ⭐⭐⭐

**🎯** 这一版最该记住的一件事：**它认的是「字」，不是「意思」。**

**⏱ 2 分钟**

**起点** 🆕 新会话（先 `/exit` 退出，再启动 —— 这个实验是重点，给它最干净的环境）

**📋 步骤**

**第 1 步** —— 启动：

```bash
LLM_PERSIST_ENABLED=0 python main.py
```

**第 2 步** —— 存一条特定的笔记：

```
请把这句话存成笔记，标题叫 perf：性能优化有三个方向：加缓存、减少重复计算、把串行改并行。
```

**第 3 步** —— 用**另一种说法**问：

```
我想让程序跑得更快一点，有什么建议？
```

**第 4 步** —— 再换回**笔记里的原话**问一次：

```
性能优化有哪些方向？
```

**👀 你应该看到**

| 你问的 | 检索结果 | 它的回答 |
|---|---|---|
| 「跑得更快一点」 | `🔍 检索 … → 0 段命中` | 「我的笔记里没有相关内容」❌ |
| 「性能优化」 | `🔍 检索 … → 1 段命中` | 完整答出三个方向 ✅ |

**同一件事，两种说法，一个找到一个找不到。**

**💡 所以呢**

因为这一版靠**字面匹配**：「跑得更快」和「性能优化」，
在它眼里是**两串完全不同的字符**。

> 这不是 bug —— 是这一类方法的**天花板**。

要用上它，你得**说它资料里的词**。这在真实产品里是个很烦的体验问题：
用户不知道你库里怎么写的。

**下一版要解决的就是这个**：把「关键词打分」换成
**embedding（向量检索）** —— 让文字按**意思**而不是按**字面**匹配。

> 💡 顺手体会一下：这个问题可以用「同义词表」硬凑吗？
> 可以，但「跑得更快 / 响应慢 / 卡顿 / 提速 / 优化性能」——
> 你要维护多少条同义词？这正是 embedding 存在的理由。

## 实验 4：问它资料里没有的东西 ⭐⭐

**🎯** 检索落空时，是**幻觉最容易发生**的时刻。盯着它。

**⏱ 1 分钟**

**起点** ↩️ 接着实验 3 的对话（不用重启）

**📋 步骤**

问一个笔记里**绝对没有**的东西：

```
我的笔记里对量子计算机有什么看法？
```

**👀 你应该看到**

```
  🔍 检索 量子计算机 → 0 段命中（扫描 6 块 · 0.4 ms）
      ⚠ 资料里没有相关内容 —— 它接下来应该说「不知道」，而不是编一个〔盯一下〕
```

然后看它怎么答。**理想答案**是：「你的笔记里没有关于量子计算的内容。」

**💡 所以呢**

那一行 `⚠` 是刻意加的 —— 它在提醒你：**这时候要盯住模型。**

模型手里此刻有两样东西：一个是「什么都没找到」，
另一个是它训练时学过的、关于量子计算的**一堆知识**。
它完全可能顺着后者编下去。

这一版的防线有两道：

1. **工具返回里直接写了指令**：「请如实告诉用户『你的笔记里没有相关内容』，不要编造」
2. **工具描述里也写了**：「若检索结果里没有相关信息，就如实告诉用户笔记里没有」

> 但说到底，这是**提示词级别的防线**，不是硬保证。
> 真正严格的系统会在这一层加校验 —— 那是后面「评估与可观测」（知识块 07）的活。

## 实验 5：一次带太多回来 ⭐⭐

**🎯** 召回不是越多越好 —— 带回来的每一段，都要挤占上下文。

**⏱ 1 分钟**

**起点** 🆕 新会话（要换配置，必须重启）

**📋 步骤**

退出，换个配置再进来：

```bash
LLM_PERSIST_ENABLED=0 LLM_RETRIEVAL_TOP_K=20 python main.py
```

问同一句话：

```
性能优化有哪些方向？
```

> 💡 **这两行前缀不是摆设**：配置是启动时读的，所以必须重启；
> 而 `LLM_PERSIST_ENABLED=0` 保证它**不记得**上一轮实验 ——
> 它此刻能答出「性能优化」，**只能靠检索**。变量只剩下要测的那一个。

**👀 你应该看到**

- 检索那行还是几段命中，但**返回给模型的段落变多了**
- 本轮请求的 token 数明显上涨（看 `· 本次请求 N tokens`）

**💡 所以呢**

这是检索系统里最经典的权衡：

| | 找得全 | 省 token |
|---|---|---|
| top_k 大 | ✅ | ❌ |
| top_k 小 | ❌ | ✅ |

而且更糟的是：**带回来越多，噪音越多** —— 20 段里可能只有 2 段真相关，
剩下 18 段会稀释模型的注意力，答案反而更容易跑偏。

> 这正是社区方案要加**重排（rerank）**的原因：
> 先粗召回 20 条，再用一个更准的模型挑出前 3 条。
> 两步走，比「一次就要选对」容易得多。

# 第三组 · 两个旋钮

## 实验 6：切分粒度 ⭐⭐

**🎯** 「一块切多大」是检索系统里最典型的旋钮 —— 两头都有坑。

**⏱ 2 分钟**

**起点** 🆕 新会话

**📋 步骤**

**第 1 步** —— 启动：

```bash
LLM_PERSIST_ENABLED=0 python main.py
```

**第 2 步** —— 先造一篇**长一点的**笔记：

```
请把这段话存成笔记，标题叫 story：
我们团队三月份开始做晨曦项目，目标是替换老系统。
五月份遇到了性能问题：订单查询慢到三秒以上，排查发现是数据库没有加索引。
六月份加了索引，顺便做了一次缓存改造，查询时间降到两百毫秒。
七月份开始灰度，第一批用户反馈不错。
八月份全量上线，老系统下线。负责人是老王，他是从三月份就参与的人。
```

**第 3 步** —— 退出，用**大切分粒度**问（默认 600 字符，整篇就是一块）：

```bash
LLM_PERSIST_ENABLED=0 LLM_CHUNK_MAX_CHARS=600 python main.py
```

问：

```
订单查询慢的问题是怎么解决的？
```

**第 4 步** —— 再退出，用**很碎的粒度**再问一次：

```bash
LLM_PERSIST_ENABLED=0 LLM_CHUNK_MAX_CHARS=40 python main.py
```

> 💡 **这个实验离开 `LLM_PERSIST_ENABLED=0` 就废了**：
> 第 2 步存笔记的那段话就摆在对话历史里。不关持久化的话，重启后它**记得全文**，
> 切分再碎也能答对 —— 你会得出「切分粒度无所谓」的错误结论。
> 关掉之后，它唯一的信息来源是「检索到了什么」，粒度的影响才会原形毕露。

**👀 你应该看到**

- `600`：整篇一块 —— 命中没问题，但**带回来的是一整篇**（上下文里塞了很多无关内容）
- `40`：切成了很多小碎块 —— **可能命中，但块里只剩半句话**，模型看得云里雾里

**💡 所以呢**

| 切分 | 好处 | 代价 |
|---|---|---|
| 太大 | 上下文完整 | 一块里混着好几件事，召回不准 + 占 token |
| 太小 | 精准、省 token | 前后文被切断，**关键词被劈成两半**（「订单查询」被切成「订单」和「查询」）|

实验里那个 `40` 特别能说明问题：**bigram 是两个字一组，
块太小的时候，匹配到的碎片根本拼不回一句人话。**

> 社区的常规做法是**重叠切分**（overlap）：相邻两块留一点重复，
> 牺牲一点冗余，换取「边界上的信息不会被切断」。

## 实验 7：关掉检索 ⭐

**🎯** 确认这个能力确实来自检索 —— 关掉它，就退回 v4。

**⏱ 1 分钟**

**起点** 🆕 新会话

**📋 步骤**

```bash
LLM_PERSIST_ENABLED=0 LLM_RETRIEVAL_ENABLED=0 python main.py
```

✅ 横幅里会出现**红色两行**：
`持久化 已关闭 —— 退出就忘光` 和 `本地检索 已关闭 —— 它读不到你的笔记`

> 💡 这个实验**尤其**需要两个开关一起关：
> 它要证明的是「**没有检索它就是不知道**」——
> 如果会话把上次的内容带了回来，它照样答得出来，你会误以为检索没用。

再问实验 1 那个问题：

```
我的笔记里，晨曦项目什么时候交付？
```

**👀 你应该看到**

- 终端里**一次 `🔍` 都没有**（因为没有这个工具了）
- 模型只能靠对话里的信息回答 —— 笔记里的内容它一无所知

**💡 所以呢**

关掉开关的方式很关键：**`search_notes` 直接从模型的工具清单里消失了**，
而不是「它调了、但被拒绝」。

差别在于：

| 做法 | 模型的感受 | 代价 |
|---|---|---|
| **从清单里摘掉**（这一版） | 它根本不知道有这个能力，不会去试 | 无 |
| 让它看见、调用时报错 | 它会困惑、会重试、可能绕路 | 多烧几次调用 |

这是 v2 就用过的套路（`LLM_DISABLED_TOOLS`）：
**权限设计 > 提示词防御**。

# 做完之后

你现在应该对下面这些有了第一手的判断：

- ✅ 检索就是「先找出来，再塞进去」—— 一条五步的流水线
- ✅ **出处和命中词**是检索系统可信的前提（否则你只能靠感觉）
- ✅ ⭐ **关键词检索靠字面，天生不认同义词** —— 这是这一版的天花板
- ✅ 检索落空 = 幻觉高发时刻，要盯住它
- ✅ 召回数量和切分粒度，是两根两头扎手的旋钮
- ✅ 关掉一个能力最好的方式，是让它从工具清单里消失
- ✅ ⭐ **实验要有干净的起点** —— v4 起它会记得上次对话，
  做对照实验时要先关掉记忆，否则你测的是「记忆」而不是「检索」

## 下一步

| 你的感受 | 下一步做什么 |
|---|---|
| 「换个说法就找不到，太蠢了」 | → **v6：embedding 检索**（按意思找，不按字找） |
