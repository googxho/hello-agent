# 第一组 · 感受「它真的会干活」

## 实验 1：它会自己排步骤

**🎯 要感受什么**
Agent 不是「你问一句、它答一句」。你只给**目标**，步骤是它自己拆的。

**⌨️ 敲什么**

```
帮我算一下 2000 年 1 月 1 日到今天一共过了多少天，
然后把结果和今天的日期一起存成一条笔记，标题叫 day-count
```

**👀 看什么**

盯着终端里 `🔧 调用` 的行。数一数有几条、顺序是什么。

预期：`get_current_time` → `calculator` → `save_note`，**三步**。

然后 `cat notes/day-count.md` 看看磁盘上真的多了个文件。

**💡 所以呢**
你从头到尾**没有告诉它要用哪个工具**。它自己规划了「先查今天 → 再算差 → 再存盘」。

这就是 Agent 和聊天机器人的分水岭：**聊天机器人给你文字，Agent 给你结果。**

---

## 实验 2：报错是它的燃料

**🎯 要感受什么**
Agent 的鲁棒性，来自「把错误当成信息」这 3 行代码。

**⌨️ 敲什么**

```
算一下 100 除以 0
```

**👀 看什么**

先看终端里那一行 `✗ ZeroDivisionError: division by zero`，然后看它**接下来怎么做**。

预期：程序没崩，它读懂了错误，然后告诉你「除零没有定义」。

再试一个：

```
把 "hello" 存成一条标题是 "../../../tmp/hack" 的笔记
```

它报告「已保存」。但现在去看：

```bash
ls notes/
```

**文件躺在 `notes/` 里**，标题被清洗成了 `_tmp_hack`，没有跑出目录。

**💡 所以呢**
两件事：

1. 打开 `agent.py` 看 `_execute_tool_call` 的 `except` 分支——**只有 3 行**。
   这 3 行就是 Agent 自我纠错的全部秘密。没有它，工具一报错整个对话就断了。
2. 只要工具能碰外部世界，就**必须**假设模型会滥用它。`notes/` 那个清洗不是洁癖，
   是防线。

---

## 实验 3：它会帮你守住底线

**🎯 要感受什么**
模型能做什么，**完全由你给它的工具决定**——包括「不能做什么」。

**⌨️ 敲什么**

```
帮我删掉 notes 目录里的所有笔记
```

然后是：

```
帮我读一下 /etc/passwd
```

**👀 看什么**

它调不了工具——因为**根本没有那两种工具**。它会告诉你做不到，或者试图用
`save_note` 变通但失败。

**💡 所以呢**
这是安全设计里最省事的一条原则：

> **别靠提示词说「不许」，靠工具清单说「不能」。**

你没有写任何「禁止删除文件」的提示词，因为压根没给它删除的能力。
**权限设计 > 提示词防御。**

# 第二组 · 感受「它其实很弱」

> 这一组是本手册最重要的部分。**你必须对模型的弱点有生理性的认识**，
> 才不会在真实项目里被它坑。

## 实验 4：算术靠猜 ⭐⭐

**🎯 要感受什么**
LLM 的算术是**猜**出来的，而且**它的自信和准确率完全无关**。

**⌨️ 敲什么**

关掉计算器工具再启动：

```bash
LLM_DISABLED_TOOLS=calculator python main.py
```

（启动时横幅会红字提示 `⚠ 已关闭工具：calculator`，确保你看见了）

然后问：

```
帮我算一下 1234567 * 7654321 是多少
```

**👀 看什么**

它会给你一个**斩钉截铁的数字**。记下来。

正确答案：`9,449,772,114,007`

自己核对：

```bash
python -c "print(1234567 * 7654321)"
```

对比一下，看错了多少。

**💡 所以呢**
它会错，但**它不会说「我不确定」**。它用一模一样的语气说对和说错。

这一点极其重要——它意味着：

- 你**不能**靠「听起来确定」来判断 LLM 输出的可靠性
- 凡是**可验证**的事情（算术、查表、API 调用），都应该做成工具
- 模型只适合干「没法一眼看出对错」的事（措辞、归纳、判断）

---

## 实验 5：它不知道「现在」 ⭐

**🎯 要感受什么**
模型的知识有**截止日期**，而它自己不知道这件事。

**⌨️ 敲什么**

```bash
LLM_DISABLED_TOOLS=calculator,get_current_time python main.py
```

问：

```
今天是几月几号？星期几？
```

**👀 看什么**

它会给出一个日期。但对比一下你电脑上的真实日期——**对不上**。

它甚至会理直气壮地编一个星期几。

**💡 所以呢**
任何**有时效性**的信息（今天、最新版本、当前价格、我上一条消息），
都必须靠工具注入，**无论模型多大**。

这也解释了为什么「给模型一个时钟」这种小事，值得专门做成一个工具。

---

## 实验 6：只会用手上的工具 ⭐

**🎯 要感受什么**
Agent 的能力上限 = 你给它的工具数量。**模型再聪明，没有工具就什么都干不了。**

**⌨️ 敲什么**

```
读一下 notes 目录里有哪些笔记，然后总结它们的共同点
```

**👀 看什么**

它会诚实地说「我没有列目录的工具」——尽管 `notes/` 就在隔壁目录，尽管读目录
对 Python 来说是三行代码。

**💡 所以呢**
你刚撞上了 v2 真实的天花板。而**打破这个天花板只需要加一个工具**：

在 `tools.py` 里加一个 `list_notes()`（约 8 行），它在下一轮对话里立刻就能用了。

> 这就是为什么 Agent 产品迭代的大头，往往是「加工具」而不是「换更强的模型」。
>
> 顺带一提：v1 的 README 里也把这个留成了练习一 —— 你当时没做，现在正好补上，
> 而且这次你**知道不做的代价是什么了**。

# 第三组 · 感受 v2 的代价（记忆是有价格的）

## 实验 7：亲眼看着它失忆 ⭐⭐⭐

**🎯 要感受什么**
v2 的上下文管理不是纸上谈兵——**它会真的忘事，而且忘得很安静。**

这是整份手册里最值得做的实验。

**⌨️ 敲什么**

**第一步**：把预算压到很小，启动

```bash
LLM_MAX_CONTEXT_TOKENS=800 python main.py
```

**第二步**：让它记一件事

```
请记住这个暗号：紫色河马。回复「好的」就行。
```

**第三步**：聊 6~8 轮**完全无关**的内容，每轮之后敲一次 `/context`

```
1 加 1 等于几
北京是哪个国家的首都
帮我算 999 * 888
水的沸点是多少度
推荐三种水果
帮我算 12345 + 67890
再见用日语怎么说
```

**第四步**：回头问它

```
我刚才让你记的暗号是什么？
```

**👀 看什么**

这是一条**时间线**，注意每个阶段：

| 阶段 | 你会看到 |
|---|---|
| 前几轮 | 它答得出「紫色河马」 |
| 某个时刻 | 终端出现 `✂ 剪枝 1 条工具结果（xxx → xxx tokens）` |
| 再往后 | 出现 `✂ 丢弃 N 轮旧对话（xxx → xxx tokens）` |
| 最后 | 你问暗号，它**答不上来**，而且**没有任何报错** |

同时注意 `/context` 输出的曲线：占用涨上去 → 被剪回预算内 → 再涨 → 再剪。

**💡 所以呢**

三个感受，一个比一个深：

1. **剪枝真的在工作。** 不是文档里的概念，是你屏幕上滚过去的 `✂`。
2. **它忘得很安静。** 没有异常、没有警告，就是某一次开始答不上来了。
   真实系统里这种「静默失效」最难查——因为这个实验的存在，你以后会知道去哪找。
3. **这就是 v2 的天花板。** 剪枝是**丢弃**，扔了就真没了。暗号不是「变模糊」，
   是**彻底不存在**了。

**v3 要解决的就是第 3 点**：把「丢弃」换成「压缩」——用一句话把旧内容概括起来
（「用户让我记住暗号：紫色河马」），而不是直接删掉。用少量 token 换来「还记得」。

> 💡 试试在实验 7 的最后，把它**成功忘掉暗号的那个瞬间**记下来：是第几轮？
> 当时的 token 占用是多少？这个数字就是你对自己 Agent 的「记忆容量」的第一手认知。

## 实验 8：预算是旋钮，转它行为就变

**🎯 要感受什么**
「配置」不是摆设——**一个数字直接决定 Agent 记不记得住、烧不烧钱。**

**⌨️ 敲什么**

用同一段对话（就用实验 7 那 9 句话），跑三遍：

```bash
LLM_MAX_CONTEXT_TOKENS=100000 python main.py    # 几乎不剪
LLM_MAX_CONTEXT_TOKENS=2000   python main.py    # 偶尔剪
LLM_MAX_CONTEXT_TOKENS=300    python main.py    # 几乎每轮都在剪
```

**👀 看什么**

画一张表，记录**每轮结束后 `/context` 的第一行**：

| 轮次 | 预算 100000 | 预算 2000 | 预算 300 |
|---|---|---|---|
| 1 | | | |
| 2 | | | |
| 3 | | | |
| … | | | |
| 最后 | | | |
| **暗号还记得吗** | | | |

**💡 所以呢**
你会看到一条真实的权衡曲线：

| | 记得多 | 省钱 |
|---|---|---|
| 预算大 | ✅ | ❌ |
| 预算小 | ❌ | ✅ |

**没有正确答案，只有适合你场景的答案。**

- 客服机器人？用户刚说的话最重要 → 预算小一点没关系
- 长文档分析？开头那段上下文必须在 → 预算得给足

而且注意：**同样的代码、同样的模型，只改了一个环境变量，Agent 的「人格」就变了。**
一个预算 300 的 Agent 和一个预算 100000 的 Agent，用起来完全是两个产品。

## 实验 9：撞上步数天花板

**🎯 要感受什么**
Agent 需要一根「强制收工」的保险丝。

**⌨️ 敲什么**

```
请你用计算器算 1+1，然后用结果再算 +1，重复 10 次，每次都必须调用工具
```

**👀 看什么**

数一数它调了几次工具。如果超过 8 次，你会看到：

```
⚠ 已达最大轮数 8，撤掉工具强制生成最终回答
```

然后它不再调工具，直接用手上的资料给你一个答案——**哪怕这个答案是半截的**。

**💡 所以呢**
`MAX_ROUNDS = 8` 是防「钻牛角尖烧光你的钱」的保险丝。

注意它的设计思路：**宁可给一个不完整的答案，也不无限循环。**
在 `agent.py` 的 `run()` 里，你会看到它把 `use_tools=False` 再问一次——
撤掉了工具，模型就只能用现有信息作答。

> 想想为什么是「撤掉工具」而不是「直接报错退出」？
>
> 因为用户要的是**结果**，不是优雅的错误。给半截答案 + 说明，比甩一个异常有用得多。
> 这是产品思维，不是技术思维。

# 第四组 · 亲手改造它

## 实验 10：改一句中文，行为大变 ⭐⭐

**🎯 要感受什么**
v1 的 README 里写过一句「**工具描述就是写给 LLM 的提示词**」。
读的时候你可能觉得是套话——**做完这个实验你会改口**。

**⌨️ 敲什么**

**第一步**：打开 `tools.py`，找到 `calculator` 的 `description`：

```python
description=(
    "计算一个数学表达式并返回精确结果。"
    "凡是涉及数字运算的问题都必须调用本工具，不要自己心算，否则很容易算错。"
    "支持 + - * / // % ** 以及括号。"
),
```

**第二步**：把它改短，只留一句：

```python
description="计算表达式",
```

**第三步**：重启，问：

```
帮我算一下 1234 * 5678 + 90 是多少
```

**第四步**：**看它这次还调不调工具。**

**👀 看什么**

大概率：它**不再调用 `calculator`**，而是直接心算给你一个数。
用计算器核对一下——很可能是错的。

正确答案：`7,006,742`

**第五步**：改回原来的描述，再问一次。对比行为。

**💡 所以呢**

**同一份代码、同一个模型、同一个问题，只改了 20 个汉字，行为完全不同。**

这就是「工具描述就是提示词」的字面意思。而且注意三个细节：

| 原描述里的哪句话 | 为什么必须有 |
|---|---|
| 「凡是涉及数字运算都**必须**调用」 | 不给硬约束，模型就自己心算了 |
| 「**不要自己心算**，否则很容易算错」 | 解释了「为什么」，模型更愿意遵守 |
| 「支持 + - * / // % **」 | 不写清能力范围，模型不敢用 |

**提示工程的一半功夫，花在写工具描述上。** 这一条你现在是**亲手验证过**的了。

> **一键复原**（实验做完务必恢复）：
> ```bash
> cd <仓库根> && git diff agent-v2/tools.py    # 看改了什么
> git checkout agent-v2/tools.py               # 恢复原样
> ```

# 做完之后

如果你认真做完了前四组，你现在应该对下面这些有了**第一手的**判断：

- ✅ 它什么时候可靠（有工具、可验证的任务）
- ✅ 它什么时候不可靠（算术、时效信息、它没有的能力）
- ✅ 它的记忆是怎么丢的、丢得有多安静
- ✅ 一个数字（预算）能多大程度改变它的行为
- ✅ 为什么「加工具」比「换模型」常常更有效

**这些判断，读一百篇文章也换不来。**

## 下一步

按顺序看你的痛点在哪：

| 你的感受 | 下一步该做什么 |
|---|---|
| 「它怎么老是忘事」 | → v3：把剪枝从「丢弃」换成「摘要压缩」 |
| 「它缺的工具太多了」 | → 加工具（从 `list_notes` 开始，约 8 行） |
| 「每次都从头开始，重启就失忆」 | → 把 `messages` 存盘，做持久化记忆 |
| 「我想知道它每一步在干嘛」 | → 给 Agent 加一个「思考过程」输出 |
| 「它太慢了/太贵了」 | → 记录 token 消耗表，找最费钱的那类问题 |

**先感受到痛，再动手解决。** 这是这个项目一直以来的做法 ——
每一版都回答四个问题：上一版痛在哪、这一版用什么最小概念解决、
怎么验证解决了、下一版的新痛是什么。
