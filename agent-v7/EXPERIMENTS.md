# 第一组 · 两个救场的场面

## 实验 1：换个说法，两路一起兜 ⭐⭐⭐

**🎯** 笔记里写的是「性能优化」，你问的是「怎么让程序跑得更快」——
**一个字都不重叠**。这一版里，即使字面对不上，向量那一路也会把它找到，
而结果日志会告诉你「这条是怎么被找到的」。

**⏱ 2 分钟**

**起点** 🆕 新会话（用下面的命令启动）

**📋 步骤**

**第 1 步** —— 启动：

```bash
LLM_PERSIST_ENABLED=0 python main.py
```

✅ 横幅里要有红字 `持久化 已关闭 —— 退出就忘光`
✅ 横幅里要有 `本地检索 开 · 模式 hybrid · … · RRF k=60 · 每边取前 10 段进融合`

**第 2 步** —— 敲这一句：

```
我想让程序跑得更快一点，有什么建议？
```

**👀 你应该看到** —— 检索那段长这样（真实输出）：

```
  🔧 调用 search_notes({"query": "程序 性能 优化 加速"})
  🔍 检索 程序 性能 优化 加速 （混合） → 1 段命中（关键词提名 1 段 + 向量提名 1 段 → RRF k=60 · 扫描 2 块 · 241.3 ms）
      perf.md:3（性能） · 关键词#1（打分 0.74） + 向量#1（余弦 0.730） → 融合 0.0328
```

⚠️ **里面的数字每次都不一样，这是正常的**。你要确认的是这四样东西：

| 确认什么 | 它在告诉你 |
|---|---|
| 有 `🔧` + `🔍` 两行 | 它**真的去查了**，不是凭自己的知识答 |
| `（混合）` 标签 | 走的是「两个都跑」这条路 |
| `关键词提名 X 段 + 向量提名 Y 段` | 两路各出了多少力 —— 这次是各提名 1 段 |
| 下一行的 `关键词#1 + 向量#1 → 融合 0.0328` | **双票**：两路都说这段相关，各贡献一份融合分 |

> ⚠️ **那个 `query` 是模型自己改写过的搜索词**，每次都会变 ——
> 实测见过「程序 性能 优化 加速」「怎么让程序跑得更快」等好几种。
> 有时它改写出的词恰好带「优化」二字（比如这次），于是关键词那一路也命中；
> 有时它给的词字面全不沾，就只剩向量那一路的票。
> **这就是为什么实验 3 要「固定查询词、绕开模型」** ——
> 在对话里，检索器本身和模型改写两个变量是混在一起的。

**第 3 步（观察）** —— 继续聊，看它自己怎么收尾。实测它中途还会再查一次
（比如查「项目 技术栈 语言 框架」，0 命中），然后在回答里引用 `perf.md`
的三个方向，并如实说「笔记里没有关于你具体项目的记录」。

那次的 0 命中日志长这样（真实输出）：

```
  🔍 检索 项目 技术栈 语言 框架 （混合） → 0 段命中（关键词 0 词命中；向量最高 0.444 < 门槛 0.5 · 扫描 2 块 · 113.3 ms）
      ⚠ 资料里没有相关内容 —— 它接下来应该说「不知道」，而不是编一个〔盯一下〕
```

注意 0 命中的解释格式：**关键词 0 词命中**（一个词都没对上）**；向量最高 0.444 < 门槛 0.5**（差 0.056 够不着）。
两路各自「为什么没找到」，一句话说清。

**💡 所以呢**

```
关键词保精确：字对上了就稳（但换个说法就全灭）
向量保语义：  意思近就能找到（但精确串靠猜）
混合：        都不要全灭 —— 各自的强项都进最终榜单
```

## 实验 2：精确编号，稳稳命中 ⭐⭐

**🎯** `ERR_5002` 这种编号，是 v6 向量检索的软肋（实测余弦只有 0.556）。
看混合模式怎么处理它。

**⏱ 2 分钟**

**起点** 🆕 新会话

**📋 步骤**

**第 1 步** —— 启动：

```bash
LLM_PERSIST_ENABLED=0 python main.py
```

**第 2 步** —— 敲这一句：

```
笔记里 ERR_5002 这个故障代码是什么情况？
```

**👀 你应该看到**（真实输出）：

```
  🔧 调用 search_notes({"query": "ERR_5002 故障代码"})
  🔍 检索 ERR_5002 故障代码 （混合） → 1 段命中（关键词提名 1 段 + 向量提名 1 段 → RRF k=60 · 扫描 2 块 · 2461.2 ms）
      model.md:3（设备） · 关键词#1（打分 1.11） + 向量#1（余弦 0.662） → 融合 0.0328
```

它然后会告诉你「解决办法是重启电源模块」。

**这三行里藏着两件事**：

1. `关键词#1（打分 1.11）` —— 字面稳稳命中，而且打分绝对值不小（编号罕见，IDF 高）
2. `向量#1（余弦 0.662）` —— 这次向量也投了票（查询里带着「故障代码」，
   把语义拉近了些）。**双票 → 融合 0.0328**

> ⚠️ 如果模型改写的查询只有光秃秃的 `ERR_5002`（没带上下文词），
> 余弦会掉到 0.556 附近 —— 但**照样有票**（0.5 门槛），双票依旧。
> 真正会把向量票拿走的是**门槛** —— 那就是实验 4。

**💡 所以呢**

v6 实验 7 里那个「门槛一抬编号就死」的脆弱场景，现在有了兜底：
**关键词那一路是独立的保险**。它不依赖模型「见没见过」这个编号，只依赖字面对上。

## 实验 3：一张表看清「两个都跑」⭐⭐

**🎯** 同一批问题喂给三个检索器（v5 / v6 / v7），一眼看出混合站在哪里。

**⏱ 2 分钟**

**起点** ↩️ 不用启动 Agent（直调检索器，跑脚本）

**📋 步骤**

**第 1 步** —— **整段复制粘贴**：

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

queries = ["性能优化", "怎么让程序跑得更快", "缓存", "ERR_5002", "番茄需要浇多少水"]
kw  = KnowledgeBase(NOTES_DIR, mode="keyword")
vec = KnowledgeBase(NOTES_DIR, mode="semantic", embedder=_embedder, cache=_embed_cache, min_similarity=0.5)
hyb = KnowledgeBase(NOTES_DIR, mode="hybrid", embedder=_embedder, cache=_embed_cache,
                    min_similarity=0.5, rrf_k=60, hybrid_depth=10)

print(f"{'查询':<22} {'关键词':<8} {'向量':<14} {'混合':<16}")
print("─" * 66)
for q in queries:
    k, v, h = kw.search(q, top_k=2), vec.search(q, top_k=2), hyb.search(q, top_k=2)
    k_txt = f"{len(k.hits)} 段" if k.hits else "0 ✗"
    v_txt = f"{len(v.hits)} 段（{v.best_score:.2f}）" if v.hits else f"0 ✗（{v.best_score:.2f}）"
    h_txt = f"{len(h.hits)} 段（{h.keyword_count}+{h.semantic_count} 提名）" if h.hits else "0 ✗"
    print(f"{q:<22} {k_txt:<8} {v_txt:<14} {h_txt}")
PY
```

**👀 你应该看到**（真实输出，数字可能有小浮动）：

```
查询                     关键词      向量             混合
──────────────────────────────────────────────────────────────────
性能优化                   1 段      1 段（0.80）      1 段（1+1 提名）
怎么让程序跑得更快              0 ✗      1 段（0.65）      1 段（0+1 提名）
缓存                     1 段      1 段（0.64）      1 段（1+1 提名）
ERR_5002               1 段      1 段（0.56）      1 段（1+1 提名）
番茄需要浇多少水               0 ✗      0 ✗（0.36）      0 ✗
```

一行一行读：

- **「怎么让程序跑得更快」**：关键词 0 命中 —— 但混合有结果。
  看提名数就知道：`0+1`，**是向量那一路单独把它救回来的**。
- **「ERR_5002」**：这一行最值钱 —— 两个单路**都能**找到（1 段 / 1 段），
  混合后拿的是 `1+1` **双票**。
- **「番茄需要浇多少水」**：两路都空 → 混合也空 ✓。
  **RRF 不是战斗力加成，它只是把两路的票合起来数。**

**第 2 步** —— 再看一眼「每条结果的票长什么样」：

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

hyb = KnowledgeBase(NOTES_DIR, mode="hybrid", embedder=_embedder, cache=_embed_cache,
                    min_similarity=0.5, rrf_k=60, hybrid_depth=10)
for q in ["怎么让程序跑得更快", "ERR_5002"]:
    out = hyb.search(q, top_k=3)
    print(f"  问：{q}")
    for h in out.hits:
        parts = []
        if "keyword" in h.ranks: parts.append(f"关键词#{h.ranks['keyword']}（{h.raw_scores['keyword']:.2f}）")
        if "semantic" in h.ranks: parts.append(f"向量#{h.ranks['semantic']}（{h.raw_scores['semantic']:.3f}）")
        print(f"    {h.chunk.citation():<22} {' + '.join(parts)} → 融合 {h.score:.4f}")
PY
```

**👀 你应该看到**（真实输出）：

```
  问：怎么让程序跑得更快
    perf.md:3（性能）          向量#1（0.650） → 融合 0.0164
  问：ERR_5002
    model.md:3（设备）         关键词#1（0.28） + 向量#1（0.556） → 融合 0.0328
```

看出票价的差别了吗：**单票 0.0164，双票 0.0328 —— 正好一倍**。
（k=60 时，两边都排第 1 = `1/61 + 1/61 = 2/61 ≈ 0.0328`。）

**💡 所以呢**

| | 关键词（v5）| 向量（v6）| 混合（v7）|
|---|---|---|---|
| 换说法 | ✗ | ✓ | ✓（向量救）|
| 精确编号 | ✓ | 脆弱 | ✓（关键词兜）|
| 两路都空 | ✗ | ✗ | **✗（不会硬凑）** |
| 成本 | 0 | 按 token | 0 + 一份查询向量 |

## 实验 4：双票的价钱 ⭐⭐

**🎯** 同一条结果、同一个查询，只把门槛从 0.5 抬到 0.6 ——
它的「票数」变少了，融合分**正好腰斩**。v6 的那个脆弱点，现在能被看见。

**⏱ 1 分钟**

**起点** ↩️ 不用启动 Agent

**📋 步骤**

**第 1 步** —— **整段复制粘贴**：

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

for th in (0.5, 0.6):
    hyb = KnowledgeBase(NOTES_DIR, mode="hybrid", embedder=_embedder, cache=_embed_cache,
                        min_similarity=th, rrf_k=60, hybrid_depth=10)
    out = hyb.search("ERR_5002", top_k=3)
    print(f"门槛 {th}：关键词提名 {out.keyword_count} 段 + 向量提名 {out.semantic_count} 段")
    for h in out.hits:
        parts = []
        if "keyword" in h.ranks: parts.append(f"关键词#{h.ranks['keyword']}（{h.raw_scores['keyword']:.2f}）")
        if "semantic" in h.ranks: parts.append(f"向量#{h.ranks['semantic']}（{h.raw_scores['semantic']:.3f}）")
        print(f"    {h.chunk.citation()}  {' + '.join(parts)} → 融合 {h.score:.4f}")
PY
```

**👀 你应该看到**（真实输出）：

```
门槛 0.5：关键词提名 1 段 + 向量提名 1 段
    model.md:3（设备）  关键词#1（0.28） + 向量#1（0.556） → 融合 0.0328
门槛 0.6：关键词提名 1 段 + 向量提名 0 段
    model.md:3（设备）  关键词#1（0.28） → 融合 0.0164
```

三件事：

1. **门槛 0.5 时**：`ERR_5002` 的余弦 0.556 ≥ 0.5 → 向量投票 → **双票 0.0328**
2. **门槛 0.6 时**：0.556 < 0.6 → 向量弃权 → **只剩关键词的单票 0.0164**（腰斩）
3. ⭐ **但结果没丢** —— 单票依然把它带回给了你。**这就是「兜底」二字的样子。**

（对照 v6 实验 7：在只有向量的 v6 里，门槛 0.6 会让这条**彻底搜不到**。）

**💡 所以呢**

门槛不再是一票否决 —— 它只影响「另一边要不要加进来」。
两路各按自己的标准发言，**任何一路足够强，结果就还在**。

## 实验 5：k 的含金量 ⭐⭐

**🎯** 实验 4 告诉你「票多重要」。这个实验让你亲手把「票多」和「名次高」
的优先级**拧反** —— k 就是那个旋钮。

**⏱ 2 分钟**

**起点** ↩️ 不用启动 Agent（纯构造名单，连向量服务都不用）

**📋 步骤**

**第 1 步** —— **整段复制粘贴**：

```bash
python - <<'PY'
from retrieval import Chunk, SearchHit, rrf_fuse

def hit(tag, score):
    return SearchHit(chunk=Chunk(source="t.md", line=1, heading="", text=tag), score=score)

# 两份名单：B 两边都进；A 是向量侧第一名，但只有单边提名
kw  = [hit("B", 0.9), hit("C", 0.5), hit("D", 0.3)]
sem = [hit("A", 0.95), hit("E", 0.8), hit("B", 0.7), hit("C", 0.6)]

print("两路名单：")
print("  关键词：[B#1, C#2, D#3]")
print("  向量：  [A#1, E#2, B#3, C#4]")
print()
for k in (0, 60):
    fused = rrf_fuse([("keyword", kw), ("semantic", sem)], k=k)
    print(f"k={k}：")
    for h in fused:
        mark = "单边提名" if len(h.ranks) == 1 else "两边都提名"
        print(f"    {h.chunk.text}   融合 {h.score:.4f}   {h.ranks}  ← {mark}")
    print()
PY
```

**👀 你应该看到**（真实输出）：

```
k=0：
    B   融合 1.3333   {'keyword': 1, 'semantic': 3}  ← 两边都提名
    A   融合 1.0000   {'semantic': 1}  ← 单边提名
    C   融合 0.7500   {'keyword': 2, 'semantic': 4}  ← 两边都提名
    E   融合 0.5000   {'semantic': 2}  ← 单边提名
    D   融合 0.3333   {'keyword': 3}  ← 单边提名

k=60：
    B   融合 0.0323   {'keyword': 1, 'semantic': 3}  ← 两边都提名
    C   融合 0.0318   {'keyword': 2, 'semantic': 4}  ← 两边都提名
    A   融合 0.0164   {'semantic': 1}  ← 单边提名
    E   融合 0.0161   {'semantic': 2}  ← 单边提名
    D   融合 0.0159   {'keyword': 3}  ← 单边提名
```

**盯着 A 和 C 看**：

- **k=60**：C（两边都提名，但名次平平 2/4）排在 A（向量侧第一名）**前面**
- **k=0**：A 反超了 C —— 因为 `1/1 = 1.0` 太值钱了，**单边第一名说了算**

k 调的从来不是「分数」，是**「共识的含金量」**：

```
k 小 → 名次尖子更值钱（单边霸权抬头）
k 大 → 被两边都提名更值钱（委员会投票）
```

顺便验证一下「B 为什么稳」：它两边都拿第一（`1/1 + 1/3`），
无论 k 取什么都是老大 —— **又强又有共识，没有争议**。

**💡 所以呢**

默认 60 是文献里的经验值（k 越大越「平缓」，弱化了单边第一名）。
这个值没有普适真理 —— 但你现在能看懂它**在干什么**了。
（想调它：`LLM_RRF_K=0 python main.py` 或改实验脚本。）

# 第三组 · 拆掉一个会怎样

## 实验 6：向量服务挂了 ⭐

**🎯** 依赖外部服务，就必须回答一个问题：**它挂了怎么办？**
这一版是两路并跑 —— 那挂掉一路，另一路能撑住吗？

**⏱ 1 分钟**

**起点** 🆕 新会话

**📋 步骤**

**第 1 步** —— 故意把向量模型名写错：

```bash
LLM_PERSIST_ENABLED=0 EMBEDDING_MODEL=不存在的模型 python main.py
```

**第 2 步** —— 问：`笔记里性能优化有哪些方向？`

**👀 你应该看到**（真实输出）：

```
  🔧 调用 search_notes({"query": "性能优化 方向"})
  🔍 检索 性能优化 方向 （关键词） → 1 段命中 （最高分 1.29 · 扫描 2 块 · 145.6 ms）
      perf.md:3（性能） · 命中 性能、能优、优化、方向
      ⚠ BadRequestError: Error code: 400 - {'code': 20012, 'message': 'Model does not exist. ...'}
```

三件事：

1. **对话照常进行** —— 没崩、没卡，笔记找到了
2. 检索那行的 tag 是 `（关键词）` 而不是 `（混合）` —— 它退回 v5 的找法了

**💡 所以呢**

代价也说得很清楚：**同义词又搜不到了**（换成「怎么让程序跑得更快」再问一次，
你会看到它 0 命中，然后如实说没找到）。

# 第四组 · 想一想

## 实验 7：思考题 —— 为什么 RRF「敢」扔掉分数 ⭐

**🎯** 这是这一版最反直觉的一点：两个检索器辛辛苦苦打的分，
RRF **看都不看，只数名次**。凭什么？

**⏱ 2 分钟（不用启动任何东西，对着前面实验的数字想）**

**问题一** —— 实验 4 里那条结果，两个原始分是 `打分 0.28` 和 `余弦 0.556`。
请把它们加起来：`0.28 + 0.556 = 0.836`。

这个 0.836 代表什么？如果换一条结果，`打分 2.4` 和 `余弦 0.31` —— 加起来 `2.71`。
**2.71 就比 0.836「更相关」吗？** 还是说，只是第一项恰好数值大？

**问题二** —— 如果不服气，说「那就归一化之后再加权」：
把每路的分数都缩放到 0~1（min-max），再加起来。再想：

- 一次查询里只有 2 条结果时，min-max 后一条永远是 1、另一条永远是 0 ——
  **分数之间的差距被抹掉了**
- 下次资料多了一条、或某条被删了，同一段文字的归一化分**会跟着变** ——
  分数成了「和谁同场」的函数，不再属于它自己

**问题三** —— 反过来：什么情况下「学出来的加权融合」比 RRF 更好？
（提示：当你有一批**标注过的数据**能回答「哪条才算对」时 ——
那是知识块 07「评估」的地盘，不是现在能拍脑袋的。）

> 想系统补这一课：看 [RETRIEVAL-PRIMER.md](RETRIEVAL-PRIMER.md) 的
> §1.6（分数为什么不可解读）和 §3.1~3.2（分数融合 vs 名次融合）。

**💡 所以呢**

RRF 的「扔掉分数」不是偷懒，是**承认两把尺子量不出可比的单位**。
名次是它们唯一能共同表达的语言 —— 而事实证明，「数票」这件事
比「量距离」稳得多、也便宜得多。

# 做完之后

你应该对下面这些有了一手的判断：

- ✅ **混合 = 各救各的场**：换说法靠向量，精确编号靠关键词 —— 而不是「效果翻倍」
- ✅ ⭐ **共识是真金白银**：两边都提名（双票 0.0328）> 单边第一名（单票 0.0164）——
  但「强到没争议」的（两边都第一）永远最稳
- ✅ **k 是共识的含金量**、**depth 是隐藏门槛**、**门槛管两路各自的发言权** ——
  三个旋钮，各自管一件事（这就是「从手工实验到系统评估」的起点）
- ✅ **0 命中不会被融合硬凑**：RRF 没有无中生有的本事
- ✅ **降级是一个基本盘问题**：v6 时退回关键词是无奈，v7 时它是并跑的一路
- ✅ ⭐ **评估组件要绕开模型**（v6 的老教训继续生效）：模型改写的搜索词
  会把「哪一路在救场」搅浑 —— 所以实验 3/4/5 全都固定输入直调组件
