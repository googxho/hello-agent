# hello-agent v12 · 实验手册

> **目标**：亲手感受 LangGraph 的三个机制 —— **检查点（checkpointer）、
> 人机协同（interrupt）、条件边（重规划）**。
>
> 全部是「亲眼见证」级别的演示：进程真猝死、图真停在半路等你点头、
> 失败真触发重规划。每个实验 1~3 分钟。

## 实验 1：第一张图跑起来（1 分钟）

**起点状态**：🆕 新线程 `demo1`（跑过就 `rm -f checkpoints.sqlite`）

### 🎯 要感受什么

**看节点们怎么「接力」** —— 一个任务的执行流，在日志里一行行显形：

```
plan → step → tools → step → advance → step → ... → finish
```

### ⌨️ 敲什么

```bash
python main.py --run "先算出 88 × 12 的结果，再告诉我今天是星期几。" --thread demo1
```

### 👀 看什么

```
🧵 线程 demo1 · 检查点 → checkpoints.sqlite
📋 计划建成（2 步）：
   1. 计算 88 × 12 的结果
   2. 获取当前日期并确定今天是星期几
▶ 第 1/2 步：计算 88 × 12 的结果
  🔧 calculator({'expression': '88 * 12'}) → 1056
  ✅ 第 1 步完成：已完成第 1 步：88 × 12 = 1056。
▶ 第 2/2 步：获取当前日期并确定今天是星期几
  🔧 get_current_time({}) → 2026-10-03 16:43:32（星期六）
  ✅ 第 2 步完成：……
✅ 全部步骤完成。
```

**每个标记对应图上的一个节点**（复盘）：

| 日志 | 谁打印的 | 图上的动作 |
|---|---|---|
| `📋 计划建成` | `plan` 节点 | 调一次模型拆步骤 |
| `▶ 第 N 步` | `step` 节点 | 调模型（让它调工具或汇报） |
| `🔧 calculator(...)` | `tools` 节点 | 真正执行工具 |
| `✅ 第 N 步完成` | `advance` 节点 | 判定成败、指针 +1 |
| `✅ 全部步骤完成` | `finish` 节点 | 汇总收尾 |

### 💡 所以呢

- v10 里那个「黑盒主循环」，现在每一段都有名字、都能在图上指出来
- 注意 `▶ 第 1 步` 和 `✅ 第 1 步完成` 之间**有两次模型调用**（一次决定调
  calculator，一次看完结果汇报）——这就是「step → tools → step」小回环

## 实验 2：⭐ 猝死与恢复（3 分钟）

**起点状态**：🆕 新线程 `demo-resume`（`rm -f checkpoints.sqlite` 后开始）

### 🎯 要感受什么

**进程被 `kill -9` 级别的猝死打断后，任务还能从断点续上。**
（`--pause-at 1` 会在第 1 步收尾时直接 `os._exit(1)` —— 不清理、不告别。）

### ⌨️ 敲什么

**第一步：故意猝死**（任务有 3 步，死于第 1 步）：

```bash
python main.py --run "先算 3 × 14，再把结果写进一条标题为 demo-resume 的笔记，最后告诉我现在几点。" --thread demo-resume --pause-at 1 --yes
```

### 👀 看什么（第一段）

```
🧪 演示模式：第 1 步完成后会模拟进程猝死（os._exit）
📋 计划建成（3 步）：
   1. 计算 3 × 14 得到结果 42
   2. 将结果 42 写入标题为 demo-resume 的笔记
   3. 获取当前时间并告知用户
▶ 第 1/3 步：计算 3 × 14 得到结果 42
  🔧 calculator({'expression': '3 * 14'}) → 42
  ✅ 第 1 步完成：3 × 14 = 42。
  🧪 演示模式：第 1 步完成后模拟进程猝死（os._exit）—— 刚才的状态已落盘，试试用 --resume 找回
```

命令**正常退出，但退出码是 1**（真猝死）。任务明明没干完，进程却没了。

**第二步：从断点继续**：

```bash
python main.py --resume demo-resume --yes
```

### 👀 看什么（第二段）

```
🧵 线程 demo-resume · 上次停在：第 1/3 步
  下一个要跑的节点：advance
  ✅ 第 1 步完成：已完成第 1 步：3 × 14 = 42。      ← ⚠ 这行【又】打了一遍！
▶ 第 2/3 步：将结果 42 写入标题为 demo-resume 的笔记
  🔧 save_note({'title': 'demo-resume', 'content': '3 × 14 = 42'}) → 已保存到 demo-resume.md
  ✅ 第 2 步完成：……
▶ 第 3/3 步：获取当前时间并告知用户
  🔧 get_current_time({}) → 2026-10-03 16:48:58（星期六）
  ✅ 第 3 步完成：……
✅ 全部步骤完成。
```

### 💡 所以呢

三个要读懂的点：

1. **恢复点是「最后一个完成的节点」**：`下一个要跑的节点：advance` ——
   猝死时 `advance` 刚被点名、还没干完，所以恢复时**它得重跑**。
2. **「✅ 第 1 步完成」出现两次是设计，不是 bug**：advance 第一次跑到一半
   被杀死（状态没落盘），第二次从头重跑、再打印一遍。
   ⇒ **节点必须幂等/无副作用**（advance 只做判定和记账，重跑无害；
   真正的副作用在 `tools` 节点，它不会被重跑因为「tools 完成」的快照已落盘）。
3. **检查点的粒度 = 每个节点一快照**：救回来的是「节点边界」，
   不是「节点内部」。这就是「重放从最后一个完整快照开始」的真实含义。

### ➕ 加餐（30 秒，零成本）：`durability` 三档 —— 快照到底什么时候落盘？

你可能想问：**exactly 是「advance 没落盘」，为什么？** 一行命令看真相：

```bash
python durability-lab.py
```

这是一个**假图实验**（a → b → c 三个假节点，c 里猝死），**不需要 API Key**：

```
══ durability='async'（LangGraph 默认）：猝死后盘上有 1 张检查点
    #0 next=('__start__',) 状态 n=[] meta.step=-1

══ durability='sync'（本版 main.py 显式采用）：猝死后盘上有 4 张检查点
    #0 next=('c',) 状态 n=['a', 'b'] meta.step=2
    #1 next=('b',) 状态 n=['a'] meta.step=1
    #2 next=('a',) 状态 n=[] meta.step=0
    #3 next=('__start__',) 状态 n=[] meta.step=-1

══ durability='exit'：猝死后盘上有 0 张检查点
```

| 模式 | 语义 | 猝死时 |
|---|---|---|
| `async`（框架默认） | 后台异步落盘，快 | **在途的快照会丢**（假图里几乎全丢） |
| `sync`（本版显式用） | 每步同步落盘后才继续 | 快照精确到最后一步，恢复点确定 |
| `exit` | 只在正常退出时写 | 猝死 = 这个线程白干活 |

**我们为什么显式选 `sync`**：教学演示要**确定的故事** ——「重跑哪个节点」
完全可预测。真实生产里 `async` 是性能默认，代价就是这里的不确定性。

## 实验 3：⭐ 人工审批（2 分钟）

**起点状态**：🆕 新线程 `demo-hitl`（`rm -f checkpoints.sqlite` 后开始）

### 🎯 要感受什么

**图能在危险动作前停下来，等你点头。**
（模型想写文件 → 图暂停 → 你按 Enter 之前，它一步都不动。）

### ⌨️ 敲什么

```bash
python main.py --run "先算 109 × 7，再把结果写进一条标题是 demo-hitl 的笔记。" --thread demo-hitl
```

（注意：**不要**加 `--yes` —— 那会自动批准，看不到暂停。）

### 👀 看什么

```
▶ 第 2/2 步：创建标题为 demo-hitl 的笔记并将计算结果写入其中

╭─────────────────────────── 人机协同（interrupt） ────────────────────────────╮
│ ⏸ 需要你批准                                                                 │
│                                                                              │
│ 模型要写文件（save_note：demo-hitl）——批准这次写入吗？                       │
╰──────────────────────────────────────────────────────────────────────────────╯
批准吗？ > 
```

**敲 `y` + Enter**（或直接 Enter = 拒绝）后：

```
批准吗？ >   🖐 人工审批：✅ 批准
  🔧 save_note({'title': 'demo-hitl', 'content': '109 × 7 = 763'}) → 已保存到 demo-hitl.md
  ✅ 第 2 步完成：……
✅ 全部步骤完成。
```

### 💡 所以呢

- 暂停点是 `approve` 节点里的 `interrupt()` —— 图在这里把控制权交给外面
- **注意设计**：审批是一个**独立节点**，它只读不写；真正写文件的
  `tools` 节点在审批**通过之后**才跑 ——「副作用放到审批之后」是 HITL 第一纪律
- 想验证「暂停时图真的停住了」：暂停时看另一个终端里
  `python main.py --inspect demo-hitl`，能看到一张 `⏸等你批准` 的快照（实验 5）

## 实验 4：⭐ 条件边：失败就换路（3 分钟）

**起点状态**：🆕 新线程 `demo-replan2`（`rm -f checkpoints.sqlite` 后开始）

### 🎯 要感受什么

**第 2 步的工具「全坏了」，任务却不放弃也不硬撑** ——
图自动重拆计划，修不好就**如实认输**。

`--sabotage-step 2`：让第 2 步的所有工具调用强制返回错误（演示开关）。

### ⌨️ 敲什么

```bash
python main.py --run "先算 42 × 3，再把结果写进一条标题是 demo-replan 的笔记，最后告诉我今天星期几。" --thread demo-replan2 --sabotage-step 2 --yes
```

### 👀 看什么（关键片段）

```
▶ 第 2/3 步：写入标题为 demo-replan 的笔记……
  🔧 save_note({'title': 'demo-replan', 'content': '42 × 3 = 126'}) → 错误：演示用故障（--sabotage-step 2）
  🔧 save_note({'content': '42 × 3 = 126', 'title': 'demo-replan'}) → 错误：演示用故障（--sabotage-step 2）
  ✗ 第 2 步失败：本步无法完成：写入标题为 demo-replan 的笔记时工具连续两次返回错误……
  🔁 重规划（第 1/2 次）：第 2 步……反复失败
   新计划（剩余部分）：
     2. 查找是否已存在标题为 demo-replan 的笔记……若不存在，则直接新建……
     3. 若上一步发现已存在同名笔记但写入失败，则改用「新建一条标题为 demo-replan-126 的笔记」作为替代方案……
     …（重拆出 5 步）
▶ 第 2/6 步：查找是否已存在标题为 demo-replan 的笔记……
  ✗ 第 2 步失败……（第 2 次重规划）
  🔁 重规划（第 2/2 次）：……
▶ 第 2/6 步：直接新建一条标题为 demo-replan-126 的笔记……
  🔧 save_note({'title': 'demo-replan-126', 'content': '126'}) → 已保存到 demo-replan-126.md
```

最后收尾（注意口径 —— **不装成功**）：

```
🏁 任务执行报告：
- 第 1 步（计算 42 × 3…）：已算出 42 × 3 = 126。
- 第 2 步（写入标题为 demo-replan 的笔记…）：本步无法完成：……save_note 反复返回错误……
- …（若干步因「没有读取工具」等如实标注无法完成）
⚠ 有步骤未能完成（重规划次数已用尽或没有更好的拆法）——不装成功。
```

### 💡 所以呢

- 控制流转弯全靠**条件边**：`advance` 发现「失败」→ 走 `replan`；
  `replan` 重拆计划（只动失败步及以后，**最小修订**）→ 回到 `step` 继续
- **防震荡护栏**：`MAX_REPLANS=2` —— 重规划最多两次，防止「拆了改、
  改了拆」的死循环。上限一到，宁可不装成功也不无限烧钱
- 「**不装成功**」是收尾纪律：宁可报告难看，也不假装完成
- 想感受护栏：把 `config.py` 里 `MAX_REPLANS` 改成 `1` 再跑一遍，
  重规划次数一到就收尾，日志里会出现「重规划次数已用尽」

## 实验 6：⛔ 拒绝审批：安全底线（2 分钟）

**起点状态**：🆕 新线程 `demo-reject3`（`rm -f checkpoints.sqlite` 后开始）

### 🎯 要感受什么

**「不批准」也是一等公民** —— 拒绝后没有任何写入发生，
而且模型被明确告知「这是最终决定，别绕路」。

### ⌨️ 敲什么

```bash
python main.py --run "先算 5 × 5，再把结果写进一条标题是 demo4 的笔记。" --thread demo-reject3
```

审批时**敲 `n` + Enter**（拒绝）。

### 👀 看什么（关键片段）

```
批准吗？ >   🖐 人工审批：⛔ 拒绝
  🔧 save_note({'title': 'demo4', 'content': '25'}) → 
用户拒绝了这次写入（未批准）。这是最终决定：不要重试、不要换其它方式写入，直接汇报本步现状……
  ✗ 第 2 步失败：本步无法完成：创建笔记 demo4 的写入操作被拒绝（未获批准），按指示不再重试……
  🔁 重规划（第 1/2 次）：……（模型又试了两轮，都被「已拒绝」挡回）
```

收尾：

```
- 第 2 步（创建笔记 demo4 写入操作）：本步无法完成：写入被拒绝……
⚠ 有步骤未能完成（重规划次数已用尽或没有更好的拆法）——不装成功。
```

**验证安全**：`ls notes/` —— **没有 demo4.md**（拒绝 = 真的一动没动）。

### 💡 所以呢

- **拒绝不等于错误**：代码里是一个独立的 `refused` 通道（黄色标记），
  不计入「工具连续报错」（否则会误导重规划机制）
- 有趣的是**模型的表现**：它老老实实照「最终决定」执行了 ——
  但图还是**多绕了两圈重规划**（试着重拆「同一个被拒绝的写」）。

  这是一个**诚实的欠账**：更好的设计是让「拒绝」直接给相关步骤**发通行证/
  终止符**，而不是掉进「失败 → 重试 → 重规划」的通道。留到以后。
- 底线价值：**没有任何一次写入真的发生** —— 这就是审批的意义
