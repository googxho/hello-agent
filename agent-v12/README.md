## 每一版都回答四个问题

### ① 上一版遇到了什么具体问题？

**v10 留下的两个真实伤口**（都不是假想——是 v10 实验里亲眼见过的）：

1. **「断在第 5 步就永远断了」**：八步挑战被模型输出格式问题中断，
   `📋 计划进度：8 步：4 完成 / 4 未标记` 就停在磁盘上 —— 手写版没有任何恢复手段。
2. **「危险操作没有把关」**：模型想写文件就直接写，没有任何一层能说「等一下」。

**v11 验证了另一半**：`create_agent` 一行很方便，但它的内核是
`langgraph.graph.state`（模块名都打印出来了）——想加**检查点、人工审批、重规划**，
LangChain 的界面就不够了：**得把那张图拆开**。

### ② 这一版引入什么最小概念？

> **LangGraph = 编排层。把 Agent 的流程画成显式状态图：**

```
                   ┌──────────────────────────────────────────┐
                   ▼                                          │
  START ──► [plan] ──► [step] ──┬─（要用 save_note）─► [approve] ──┐
                            ▲   ├─（普通工具调用）───────────────► [tools]
                            │   └─（本步说完了）───────┐          │
                            │                          ▼          │
                            │                     [advance] ◄──────┘
                            │        ┌─────────────────┼──────────────┐
                            └───── [step]          [replan]       [finish] ──► END
```

七个节点、八条边——**v1 那个 40 行的神秘大循环，现在是一个可以画出来的东西**。
控制权的一部分从模型手里拿回来：

| 谁来负责 | v10 手写版 | v12 图版 |
|---|---|---|
| 「第几步、算不算完成」 | 模型自由心证（+ update_plan 打勾） | `step` / `advance` 节点 |
| 「危险操作放行吗」 | 无人把关 | `approve` 节点（**interrupt**） |
| 「这步做不成怎么办」 | 没有出路 | `replan` 节点（条件边） |
| 「进程死了怎么办」 | 重来 | **checkpointer** 一步一快照 |

三个机制都是面试考点（README 后面有答题版）：

1. **状态 + reducer**：节点返回「增量」，框架按 reducer 合并——默认覆盖，
   要「追加」得显式声明（`step_outputs` 用 `operator.add`；`messages` 用 `add_messages`）。
2. **检查点（checkpointer）**：每个节点执行后状态快照落盘（SqliteSaver）。
   进程猝死 → `--resume` 从上一次完整状态继续。
3. **interrupt（人机协同）**：节点里调用 `interrupt()` 图就暂停，外面用
   `Command(resume=答案)` 恢复。⚠️ **恢复时整个节点从头重跑**——所以
   interrupt 之前的代码必须无副作用（我们把审批做成独立的 `approve` 节点，就是为了这个）。

### ③ 如何验证它真的解决了？

**离线验证**（`--selftest`，**39 项断言**，零 API Key、零花费）：

- 图结构：编译、七个节点、六条关键边，全部按名字断言
- 路由纯函数：`route_after_step`（approve/tools/advance 三出口 + `--yes` 变体）、
  `route_after_advance`（replan/step/finish + 防震荡上限）
- **状态机制用「假节点小图」测穿**：reducer 累加、interrupt 暂停、
  `Command(resume)` 恢复、检查点历史一张张落盘——不联网、不花钱
- 失败判定、收尾口径（「不装成功」）、计划解析、日志格式

**真实运行验证**（全部真跑捕获）：

| 场景 | 结果 |
|---|---|
| 3 步任务 + 写文件审批 | 停在 `⏸ 需要你批准`，批准后写入成功、报告完整 |
| **猝死与恢复** | `--pause-at 1` 真猝死 → `--resume` 显示「上次停在：第 1/3 步」→ 补完收尾 → 继续跑完 |
| **固定失败 + 重规划** | 第 2 步工具全坏 → 两次（上限）重规划 → 跳过坏步 → 最后 **`⚠ 有步骤未能完成——不装成功`** |
| **拒绝审批** | 写入被拒 → 模型按指示不再重试 → 如实报告（也暴露一个设计欠账，见下） |
| `--inspect` 时间线 | 28 张快照躺在磁盘里：哪一步重规划过、哪个瞬间在等你审批，一目了然 |

### ④ 下一版的新痛点是什么？

这一版把「控制的骨架」搭好了，但骨架要上生产还差一层：

- **成本与并发**：checkpointer 让每一步都落盘，长任务跑起来更贵了；
  多线程（多用户）怎么隔离、怎么清理旧检查点——没碰。
- **部署**：SqliteSaver 是单机玩具；生产要用 PostgresSaver / Redis——
  以及「图跑一半需要水平扩展」这种真问题。
- 顺带的欠账：「拒绝」的语义没设计好（见下面的诚实清单）。

**→ 下一版方向：14 · 成本、并发与部署。**
（把 v9~v12 攒下的账本、并发、持久化全部推到「上线」这个标准下审视。）

## ⭐ 面试问答（LangGraph 版）

### Q1 「LangGraph 是什么？和 LangChain 什么区别？」

**骨架**：两层职责——
**LangChain（组件层）**：把和模型打交道的零件标准化（消息/工具/模型/组装）；
**LangGraph（编排层）**：把 agent 的流程变成显式状态图（循环/分支/检查点/人机协同）。
同门（LangChain 团队），LangGraph 建在 langchain-core 之上；
**LangChain 1.x 的 agent 门面（create_agent）内核就是 LangGraph 的图**。

**本版证据**：v11 的 `--demo agent` 打印过 `langgraph.graph.state`；
v12 的 `_selftest` 里七节点图的节点/边可以逐条断言——「流程是代码，不是黑盒」。

### Q2 「为什么 Agent 需要『图』，链（LCEL）不够吗？」

**骨架**：链是**数据流**（DAG：有方向、无环）；Agent 是**控制流**——
需要**循环**（工具回环）、**状态**（第几步、计划）、**分支**（失败换路）、
**暂停**（审批）。用链写 agent，最后一定要在链里手搓循环和状态——那就是在
重新发明图，而且还不是显式的。

**本版证据**：v12 的图里 `step → tools → step` 就是一个环；
`advance → replan / step / finish` 就是分支。**它们在图上看得见**。

### Q3 「checkpointer 怎么工作的？」

**骨架**：三句话——① 每个**节点执行后**，整个状态快照落盘（SqliteSaver 到一个文件）；
② 快照按 `thread_id`（会话/任务）分组，`get_state_history` 能拿到**完整时间线**；
③ 恢复 = 用同一个 `thread_id` 重新 `invoke(None)`，图从**最后一个完整快照**继续。
额外加分：这就是「时间旅行」的基础（理论上可以从任一快照分叉重跑）。

**本版证据**：实验 2 的真猝死恢复；`--inspect demo-replan2` 打出的 28 张快照
（能看到重规划第 1 次、第 2 次留下的每一步）。

### Q4 「interrupt 怎么实现 HITL？有什么坑？」

**骨架**：节点里调 `interrupt(问题)` → 图暂停、把你带回外面（返回 `__interrupt__`）；
外面 `Command(resume=答案)` 恢复，**interrupt 那一行返回答案**。
**最大的坑**：恢复时**整个节点从头重跑**——所以：① interrupt 之前的代码必须幂等/
无副作用（我们的 `approve` 节点里只有读操作）；② 真实副作用（写文件）要放在
**interrupt 之后**的流程里（我们放在 `tools` 节点，它拿 `approved` 标记再执行）。
**加分**：把审批做成独立节点（而不是塞进干活节点），是让「重跑」无害的常用手法。

**本版证据**：`--inspect demo-hitl` 里能看到一个快照 `下一节点=approve ⏸等你批准`——
暂停状态也是落盘的（跨进程见：`--resume` 时它会重新问你）。

### Q5 「什么时候该上图框架（而不是继续手写循环）？」

**骨架（信号，不是版本号）**：① 主循环里出现 3+ 个 if/else 决定「接下来干嘛」；
② 想加「失败换路走」发现要嵌循环；③ 需要「暂停 → 等人 → 继续」，发现自己要
管一大堆状态；④ 需要「进程死了能恢复」——这时图的成本（抽象税、学习曲线）
才开始回本。反过来：单轮工具调用、简单链式流程，手写 40 行比图清楚。

**本版证据**：v10 的八步挑战「断就断了」vs v12 的 `--resume`——
**第 ④ 条信号我们用真需求撞出来的**。

### Q6 「用框架的图 vs 自研状态机，怎么选？」

**骨架**：框架给你「快照序列化/恢复/中断协议」这些**难写对的基础设施**（谁自己写
过就懂）；代价是调试要穿透抽象、行为跟着版本走。判断：**先问『我缺的是不是
基础设施』**——缺，上框架；不缺，一个小状态机字典可能更可控。

## ⚠️ 诚实的话（这一版踩的坑与欠账）

1. **最大的坑差点让整版翻车**：`The reasoning_content … must be passed back` 的
   400 报错——查了半天「包不兼容」，真因是**我们自己把请求排成了非标准序列**
   （`[system, assistant]` 收尾，缺 user 引导）。把步骤指令改成 `HumanMessage`
   就全好了。**教训（面试可讲）**：报错文案说的是服务端「想要的字段」，
   不一定是「真因」；先怀疑自己组装的请求形态，再怀疑库。
   （源码都翻了：langchain-openai 明确声明「不处理供应商私有字段」——
   差点去换 langchain-deepseek，那就错过了真问题。）
2. **一个真实越界 bug**：`--sabotage-step` 场景里「**最后一步**失败」时，
   `advance` 已把指针推进越界，`replan` 再取 `plan[step_index]` 就崩了。
   修法：明确数据流——失败步 = `step_index - 1`，重规划后**回退指针**重做它。
   （这个 bug 离线断言测不出来——是靠真跑场景撞出来的。）
3. **「拒绝」的语义没设计好**：用户拒绝写入后，模型说「无法完成」→ 触发重规划
   → 新计划又要写 → 又被提示「已拒绝」……绕了两次圈子才收尾（浪费调用）。
   正确的设计应该让「拒绝」**直接给相关步骤发通行证/终止符**，而不是进失败重试通道。
   这是个明确的欠账（也是「拒绝处理」这个进阶话题的入口）。
4. **演示模式的「重跑」痕迹**：`--pause-at` 猝死恢复后，`advance` 节点会重跑，
   你会看到「✅ 第 1 步完成」打印两次——这不是 bug，是**节点重跑语义**的现场教学
   （副作用幂等设计的重要性，见 Q4）。
5. **本版不带**：流式（`stream`）、多 Agent、消息压缩——图的这几点没展开，
   够用就好（概念课里有对照）。
