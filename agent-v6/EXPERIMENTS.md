# 第一组 · 它现在按「意思」找了

## 实验 1：换个说法，它这次找到了 ⭐⭐⭐

**🎯** 笔记里写的是「性能优化」，你问的是「怎么让程序跑得更快」——
**一个字都不重叠**。这一版找得到，上一版（只会比字面）找不到。

**⏱ 2 分钟**

**起点** 🆕 新会话（用下面的命令启动）

**📋 步骤**

**第 1 步** —— 启动：

```bash
LLM_PERSIST_ENABLED=0 python main.py
```

✅ 横幅里要有红字 `持久化 已关闭 —— 退出就忘光`

**第 2 步** —— 敲这一句（注意：笔记里可没有「跑得更快」这几个字）：

```
我想让程序跑得更快一点，有什么建议？
```

**👀 你应该看到** —— 检索那段长这样（真实输出）：

```
  🔧 调用 search_notes({"query": "程序 性能 优化 速度"})
  🔍 检索 程序 性能 优化 速度 （向量） → 1 段命中 （相似度 0.745 · 扫描 1 块 · 202.8 ms）
      perf.md:3（性能） · 相似度 0.745
```

⚠️ **里面的数字每次都不一样，这是正常的** —— 换你跑，搜索词、相似度、毫秒数都会变。
你要确认的是这四样东西：

| 确认什么 | 它在告诉你 |
|---|---|
| 有 `🔧` + `🔍` 两行 | 它**真的去查了**，而不是凭自己的知识答 |
| `（向量）` | 走的是「比意思」这条路，不是比字面 |
| 相似度 0.6 以上 | 它确实找到了相关内容（0.745 就是「挺近」） |
| 下一行的 `perf.md:3（性能）` | 有出处 —— 你可以翻开笔记自己核对 |

然后它带着笔记里的三个方向回答了你。

> ⚠️ **那个 `query` 是模型自己改写过的搜索词**，每次都会变。
> 实测见过：「程序 性能 优化 项目」「程序 性能 优化 慢」「程序 性能 优化 速度」——
> 它甚至会把「性能优化」这个词**替用户塞进去**。记住这个现象，第 3 步会告诉你它有多要命。

**第 3 步（对照）** —— 上一版为什么做不到？
下面这段**整段复制粘贴**进终端、回车。它在干一件事：
拿同一句话，同时问两个检索器 —— 上一版的找法和这一版的找法：

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

q   = "怎么让程序跑得更快"
kw  = KnowledgeBase(NOTES_DIR, mode="keyword")     # 上一版：比字面
vec = KnowledgeBase(NOTES_DIR, mode="semantic",    # 这一版：比意思
                    embedder=_embedder, cache=_embed_cache, min_similarity=0.5)

k, v = kw.search(q), vec.search(q)
print(f"问：{q}")
print(f"  比字面： {len(k.hits)} 段命中")
print(f"  比意思： {len(v.hits)} 段命中 · 相似度 {v.best_score:.3f}")
PY
```

**👀 你应该看到**（真实输出）

```
问：怎么让程序跑得更快
  比字面： 0 段命中
  比意思： 1 段命中 · 相似度 0.651
```

同一句话、同一份笔记：**0 段 vs 1 段**。

> ❓ **为什么不干脆「切到关键词模式，再对话问一次」来做对照？**
> 因为**行不通**。我刚替你试了：关键词模式下问同一句话，
> 模型把搜索词改写成「程序性能优化 让程序跑得更快」——
> 里面**带着「性能优化」四个字**，于是连「比字面」都命中了。
>
> 一次对话里混着两个变量：**检索器本身** + **模型怎么改写**。
> 结果对了，你都说不清该归功给谁。想看清一个组件的真实水平，
> 就得像第 3 步这样**固定查询词、把它单独拎出来**。
> （这条经验是「评估」那一块的核心 —— 后面会专门讲。）

**💡 所以呢**

```
比字面：找「字长得像的」  → 用户换个说法就全灭
比意思：找「意思离得近的」 → 这才是搜索该有的样子
```

「性能优化」和「怎么让程序跑得更快」，在字面上是两串毫不相干的字符，
但意思很近 —— 向量干的事，就是把「意思」变成一串数字，让机器能比大小。

## 实验 2：「相似度」到底是个什么数字 ⭐⭐

**🎯** 多高才算「相关」？—— 这是这一版唯一没法靠代码解决的问题。

**⏱ 1 分钟**

**起点** ↩️ 不用启动 Agent（这个实验直接调检索器，跑脚本）

**📋 步骤**

**第 1 步** —— **整段复制粘贴**：
它会一口气问你 5 个问题（从「几乎原话」到「完全无关」），把分数全打出来。

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

# min_similarity=0.0 = 先把门槛关掉，多低的分都能看到
vec = KnowledgeBase(NOTES_DIR, mode="semantic", embedder=_embedder,
                    cache=_embed_cache, min_similarity=0.0)

for q in ["性能优化有哪些方向", "怎么让程序跑得更快", "这段代码太慢了",
          "番茄需要浇多少水", "今天天气怎么样"]:
    print(f"  {vec.search(q).best_score:.3f}   {q}")
PY
```

**👀 你应该看到**（真实输出按分数重排了一下，你的数字可能浮动一两位小数）

```
  0.787   性能优化有哪些方向     ← 几乎就是笔记原话
  0.651   怎么让程序跑得更快     ← 意思很近
  0.580   这段代码太慢了        ← 意思近
  0.425   今天天气怎么样        ← 无关
  0.362   番茄需要浇多少水       ← 无关
```

**看出那条沟了吗**：相关的三个都在 **0.58 以上**，无关的两个在 **0.43 以下** ——
中间空出来的那一段，就是「门槛」该站的地方。默认值 0.5 正好落在沟里。

**💡 所以呢**

记住三件事：

1. **沟的位置每个模型都不一样** —— 换个 embedding 模型，「无关」可能整体上移
2. **它也取决于你的资料** —— 全是技术笔记时，沟可能变窄、甚至挤在一起
3. **所以 0.5 不是真理**，是「这个模型 + 这份资料」量出来的

> 真实产品里，这个数字是**测出来的**：拿一批「已知相关 / 已知无关」的问题跑一遍，
> 找分得最干净的那个点。这活儿就是「评估」的雏形。

# 第二组 · 两个旋钮和一场事故

## 实验 3：门槛挡住不该进来的 ⭐⭐

**🎯** 把门槛关掉会怎样 —— top_k 会把最不相关的也硬塞给你。

**⏱ 2 分钟**

**起点** ↩️ 不用启动 Agent

**📋 步骤**

**第 1 步** —— 同一句无关的话，门槛 0 和 0.5 各搜一次（**整段复制粘贴**）：

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

for threshold in (0.0, 0.5):
    kb = KnowledgeBase(NOTES_DIR, mode="semantic", embedder=_embedder,
                       cache=_embed_cache, min_similarity=threshold)
    out = kb.search("番茄需要浇多少水", top_k=3)
    print(f"  门槛 {threshold}：{len(out.hits)} 段命中（最高相似度 {out.best_score:.3f}）")
PY
```

**👀 你应该看到**（真实输出）

```
  门槛 0.0：1 段命中（最高相似度 0.362）   ← 一点都不相关，也塞了进来
  门槛 0.5：0 段命中（最高相似度 0.362）   ← 挡住了
```

**第 2 步** —— 在真对话里看它长什么样：

```bash
LLM_PERSIST_ENABLED=0 python main.py
```

问：`我的笔记里，番茄需要浇多少水？`

**👀 你应该看到**（真实输出）

```
  🔧 调用 search_notes({"query": "番茄 浇水"})
  🔍 检索 番茄 浇水 （向量） → 0 段命中 （最高相似度 0.373 < 门槛 0.5 · 扫描 1 块 · 218.1 ms）
      ⚠ 资料里没有相关内容 —— 它接下来应该说「不知道」，而不是编一个〔盯一下〕
```

（0.373 和脚本里的 0.362 略有出入，正常 —— 它自己改写过搜索词，分数就会变。）

> 💡 **盯住它的下一个动作**：实测它**不甘心，换个词又试了一次**（「番茄」）——
> 还是 0 命中 —— 然后才如实说「你的笔记里没有相关内容」。
> 一次没找到会再试，这本身就是「它在真的找」的证据。
> （具体试几次每次不一样：我见过 1 次、2 次、4 次。模型不是螺丝钉，别期待完全一致。）

**💡 所以呢**

**门槛就是「宁滥」和「宁缺」之间拧一下：**

| | 门槛低 | 门槛高 |
|---|---|---|
| 该找到的能找到 | ✅ | 可能漏掉 |
| 塞进无关内容 | ✅（模型会被带偏）| ❌ |

而检索空手而归那一刻，是**幻觉最容易发生的时候**：模型手里有「什么都没找到」，
也有它自己学过的知识 —— 它完全可能顺着后者编下去。
那行 `⚠ 资料里没有相关内容` 就是给它打的预防针（提示词级防线，不是硬保证）。

## 实验 4：钱花在哪了 ⭐⭐

**🎯** embedding 是**按 token 计费**的。这一版最关键的代码，是让它别重复花钱。

**⏱ 2 分钟**

**起点** ↩️ 不用启动 Agent（账本只能在代码里看）

**📋 步骤**

**第 1 步** —— 先把缓存清掉，这样才能看到「从零开始」的完整过程：

```bash
rm -f embedding-cache.json
```

**第 2 步** —— **整段复制粘贴**：
它会跑两次检索，相当于两次独立启动，然后把各自的账本打出来。

```bash
echo '════ 第 1 次 ════'
python - <<'PY'
from tools import KNOWLEDGE
KNOWLEDGE.search("性能优化")
print("  账本：", KNOWLEDGE.embedder.stats.describe())
PY

echo '════ 第 2 次（又一个新进程）════'
python - <<'PY'
from tools import KNOWLEDGE
KNOWLEDGE.search("性能优化")
print("  账本：", KNOWLEDGE.embedder.stats.describe())
print("  缓存：", KNOWLEDGE.cache.note)
PY
```

**👀 你应该看到**（真实输出）

```
════ 第 1 次 ════
  账本： 调用 2 次 · 2 段 · 29 tokens · 0.9s
════ 第 2 次（又一个新进程）════
  账本： 缓存命中 1 段（没花钱） · 调用 1 次 · 1 段 · 5 tokens · 0.8s
  缓存： 从磁盘读回 1 个向量
```

这样读账本：

- **第 1 次：调用 2 次** —— 资料块算一遍（1 段）+ 你查的词算一遍（1 段）
- **第 2 次：资料块的向量不花钱了** —— 从磁盘读回来了（`缓存命中 1 段（没花钱）`），
  只有你查的那 1 段词要重新算

**第 3 步** —— 改一下笔记，再跑一次：

```bash
echo '性能优化有三个方向：加缓存、减少重复计算、把串行改并行。另外还有一点：用更好的算法。' > notes/perf.md
python - <<'PY'
from tools import KNOWLEDGE
KNOWLEDGE.search("性能优化")
print("  账本：", KNOWLEDGE.embedder.stats.describe())
PY
```

✅ 会发现它**又花钱了** —— 内容变了，指纹就变了，缓存自然失效。

**💡 所以呢**

```
块内容 ──sha256──→ 指纹 ──→ 向量（存起来）
```

- 内容没变 → 指纹没变 → 命中缓存，**不花钱**
- 内容变了 → **只有变的那一块**重算，不是整个库重来

> 💡 顺手想一下：查询词为什么不进缓存？
> 因为你每次问的都不一样 —— 存进去只会把缓存撑大，命中率还极低。
> **缓存是给「反复要用、总量有限」的东西准备的。**

**🎯** 依赖外部服务，就必须回答一个问题：**它挂了怎么办？**

**⏱ 1 分钟**

**起点** 🆕 新会话

**📋 步骤**

**第 1 步** —— 故意把向量模型名写错（模拟服务出问题）：

```bash
LLM_PERSIST_ENABLED=0 EMBEDDING_MODEL=不存在的模型 python main.py
```

**第 2 步** —— 问：`我的笔记里，性能优化有哪些方向？`

**👀 你应该看到**（真实输出）

```
  🔧 调用 search_notes({"query": "性能优化"})
  🔍 检索 性能优化 （关键词） → 1 段命中 （最高分 0.42 · 扫描 1 块 · 139.4 ms）
      ⚠ BadRequestError: Error code: 400 - {'code': 20012, 'message': 'Model does not exist. ...'}
```

三件事：

**💡 所以呢**

这是 v3 压缩失败、v4 坏文件之后，**第三遍同样的工程思路**：

> **主路径决定你有多好，降级路径决定你能不能用。**

注意那行错误提示**必须说出来** —— 你以为在用向量、实际走的是关键词，
不说的话你永远发现不了。降级的代价也很具体：**同义词又搜不到了**。

# 第三组 · 并排看，然后想一想

## 实验 6：一张表看清两种找法 ⭐

**🎯** 同一批问题喂给两个检索器，一眼看出各自的性格。

**⏱ 2 分钟**

**起点** ↩️ 不用启动 Agent

**📋 步骤**

**第 1 步** —— **整段复制粘贴**，它会把两种找法的结果并排打一张表：

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

queries = ["性能优化", "怎么让程序跑得更快", "把串行改并行", "缓存"]
kw  = KnowledgeBase(NOTES_DIR, mode="keyword")
vec = KnowledgeBase(NOTES_DIR, mode="semantic", embedder=_embedder,
                    cache=_embed_cache, min_similarity=0.5)

print(f"{'查询':<20} {'比字面':<12} {'比意思'}")
print("─" * 50)
for q in queries:
    k, v = kw.search(q, top_k=2), vec.search(q, top_k=2)
    k_txt = f"{len(k.hits)} 段" if k.hits else "0 ✗"
    v_txt = f"{len(v.hits)} 段（{v.best_score:.2f}）" if v.hits else f"0 ✗（{v.best_score:.2f}）"
    print(f"{q:<20} {k_txt:<12} {v_txt}")
PY
```

**👀 你应该看到**（真实输出）

```
查询                 比字面        比意思
──────────────────────────────────────────────────
性能优化             1 段         1 段（0.80）    ← 原话，两个都行
怎么让程序跑得更快     0 ✗         1 段（0.65）    ← 换个说法，只有它行
把串行改并行          1 段         1 段（0.57）    ← 原话
缓存                 1 段         1 段（0.64）    ← 原话
```

**💡 所以呢**

**「比字面」不是没用的东西** —— 看「原话」那几行，它一次都没失手，
而且**免费**、还快。

| | 比字面 | 比意思 |
|---|---|---|
| 原话 | ✅ 稳 | ✅ 稳 |
| 换个说法 | ❌ 全灭 | ✅ 它行 |
| 精确编号（ERR_5002 那种）| ✅ 稳 | ？—— 实验 7 细看 |
| 成本 | 免费 | 按 token 付费 |

所以真实产品里，**主流答案是「两个都跑」**：

```
粗召回：比字面来一份 + 比意思来一份
        ↓  用 RRF（倒数排名融合）之类的办法合并
精排：  再挑出前几条塞进上下文
```

这叫**混合检索** —— 它就是下一版的正题。

## 实验 7：思考题 —— 什么时候「比意思」反而不如「比字面」 ⭐

**🎯** 别把新玩具当万能药。亲手找一次向量的软肋。

**⏱ 2 分钟**

**起点** ↩️ 不用启动 Agent

**📋 步骤**

**第 1 步** —— 造一条带「精确编号」的笔记：

```bash
cat > notes/model.md <<'EOF'
设备型号 X1000-3 的故障代码是 ERR_5002，解决办法是重启电源模块。
EOF
```

**第 2 步** —— **整段复制粘贴**，用三种问法各搜一次：

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

kw  = KnowledgeBase(NOTES_DIR, mode="keyword")
vec = KnowledgeBase(NOTES_DIR, mode="semantic", embedder=_embedder,
                    cache=_embed_cache, min_similarity=0.0)   # 门槛关掉，看原始分

for q in ["ERR_5002", "X1000-3", "设备报错了怎么办"]:
    k, v = kw.search(q, top_k=1), vec.search(q, top_k=1)
    print(f"  {q:<16} 比字面 {len(k.hits)} 段 | 比意思 {v.best_score:.3f}")
PY
```

**👀 你应该看到**（真实输出，你的数字可能差一点）

```
  ERR_5002         比字面 1 段 | 比意思 0.556
  X1000-3          比字面 1 段 | 比意思 0.617
  设备报错了怎么办    比字面 1 段 | 比意思 0.628
```

**第 3 步** —— 再把门槛从 0.5 抬到 **0.6**，只看前两个编号：

```bash
python - <<'PY'
from config import NOTES_DIR
from retrieval import KnowledgeBase
from tools import _embedder, _embed_cache

vec = KnowledgeBase(NOTES_DIR, mode="semantic", embedder=_embedder,
                    cache=_embed_cache, min_similarity=0.6)
for q in ["ERR_5002", "X1000-3"]:
    print(f"  {q:<16} {len(vec.search(q, top_k=1).hits)} 段")
PY
```

**👀 你应该看到**（真实输出）

```
  ERR_5002         0 段      ← 丢了！
  X1000-3          1 段      ← 还在
```

**💡 所以呢**

自己看数字，回答三个问题：

1. **`ERR_5002` 这种编号**：比字面是稳稳命中（两个字符串相等，不玩花样）；
   比意思只有 **0.556** —— 勉强蹭过 0.5 的线。
   为什么这么勉强？因为这是**模型没见过的无意义串**，
   它没法「理解」，只能拆成碎片去猜 —— **猜对是运气**。
2. **门槛从 0.5 抬到 0.6**：同一条笔记里的两个编号，`ERR_5002` 丢了、`X1000-3` 还在。
   同一份资料、同一个模型，**门槛动一点点，一个编号就彻底搜不到了**。
3. 如果两种各有各的强项 —— **那为什么只选一个？**

> 想清楚这题，下一版（混合检索）为什么存在，就不用我讲了。

# 做完之后

你应该对下面这些有了一手的判断：

- ✅ **比意思 = 能懂近义词**，它治好了 v5 那个「换个说法就找不到」的死穴
- ✅ ⭐ **评估一个组件要把它单独拎出来测** ——
  模型会自己改写搜索词、甚至干脆不查，会把真实差别搅浑（实验 1）
- ✅ **相似度门槛没有普适值**，只能在你自己的模型和资料上量（实验 2 / 3）
- ✅ **embedding 要花钱**，所以缓存是刚需；失效靠「内容指纹」（实验 4）
- ✅ 依赖外部服务，就一定有降级路径（实验 5 —— v3 / v4 / v6 同一个套路）
- ✅ **「比字面」不是过时的东西**，它和「比意思」各有各的强项（实验 6 / 7）
- ✅ ⭐ **实验要有干净的起点** —— 直调组件的脚本天然干净；
  真对话实验要先关掉记忆，否则测的是「它记不记得住」（开始之前）
