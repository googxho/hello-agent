## 每一版都回答四个问题

### ① 上一版遇到了什么具体问题？

v5 的检索器靠**字面匹配**：字一样才算命中。

**干净对照**（固定查询词，直接调检索器 —— 绕开模型，见下面「一个反直觉的发现」）：

| 查询 | 关键词检索（v5）| 向量检索（v6）|
|---|---|---|
| 怎么让程序跑得更快 | **0 命中 ✗** | **1 命中（0.651）** ✓ |
| 这段代码太慢了怎么改善 | **0 命中 ✗** | **2 命中（0.621）** ✓ |
| 番茄需要浇多少水 | 0 命中 | 0 命中（0.362 < 门槛 0.5）✓ |

笔记里写的是「**性能优化**有三个方向……」，而用户问的是「**怎么让程序跑得更快**」——
同一个意思，零个重叠的字。

> ⚠️ **一个反直觉的发现**：v5 的检索器其实没我在手册里说的那么没用 ——
> 因为**模型会自己改写查询**：你问「怎么让程序跑得更快」，
> 它交给检索器的可能是「怎么让程序跑得更快 **性能优化**」—— 自己塞了同义词进去。
>
> 所以真实对话里，v5 有时也能命中。**但那是在赌模型的临场发挥**，
> 而且让「检索器到底行不行」变得很难判断。
> 想看清检索器的真实水平，就得像上表这样**固定查询词、绕开模型**。
> （这个坑，是「评估」那一块的核心议题 —— 先埋个伏笔。）

### ② 这一版引入什么最小概念？

> **把文字变成一串数字（向量）。意思相近的文字，向量也相近。**

```
「性能优化…」   → [ 0.12, -0.03, …, 0.44]   ┐ 方向接近（余弦 0.65）
「怎么让它更快」 → [ 0.11, -0.02, …, 0.41]   ┘
「番茄需要浇水」 → [-0.31,  0.22, …,-0.08]     方向差很远（余弦 0.36）
```

于是「找相关内容」变成了**找夹角最小的向量** —— 一个纯数学问题，
跟「字面上一样不一样」彻底无关。

**流水线一步没变**（切分、塞上下文、出处全都照旧），只换掉了 `search()` 里那段打分逻辑。
这就是 v5 把检索器单独拆成一个文件的回报。

### ③ 如何验证它真的解决了？

1. **离线**：`--selftest` 共 **101 项**，其中 12 项专测向量这条线
   （缓存命中、门槛过滤、换模型作废、失败降级、坏缓存）—— 不联网、不花钱
2. **干净对照**：上面那张表，直接调检索器，固定查询词
3. **跨进程验证**：第 2 次启动「缓存命中 2 段（没花钱）」

### ④ 下一版的新痛点是什么？

| 坑 | 说明 |
|---|---|
| **门槛是拍出来的** | 0.5 这个值只对 bge-m3 + 我这份资料成立。换模型/换语料就得重新校准 —— **没有普适值** |
| **精确匹配可能变弱** | 向量擅长「意思」，但对型号、编号、代码这类**精确串**未必比关键词强（实验 7 让你自己测）|
| **规模** | 现在是「每个查询跟所有向量算一遍」。几百块无感，几万块就得上专业向量库 |
| **成本** | embedding 按 token 计费。缓存挡住了重复计算，但**改资料就是要花钱重算** |
| **查不查，是模型说了算** | 不是 `if` 语句。v6 用「提示词 + 低温度」把它稳下来了（见下方 FAQ），但本质上仍是模型在判断 |

**→ 下一版方向**：**混合检索** —— 关键词和向量**两个都跑**，
用 RRF（倒数排名融合）之类的办法合并结果。这是生产里的标准做法：
「能精确匹配的让它精确匹配，剩下的交给语义」。

## 快速开始

```bash
myenv
cd agent-v6

# 自检 —— 不需要任何 API Key（向量部分用假替身），不花钱
python main.py --selftest

# 开始对话
python main.py
```

**要配一个新的东西**：向量模型（和对话模型是**两家服务**）。
在**仓库根**的 `.env` 里加这三行（模板见 `.env.example`）：

```bash
EMBEDDING_API_KEY=sk-...                                  # 向量服务的 Key
EMBEDDING_BASE_URL=https://api.siliconflow.cn/v1          # 默认值
EMBEDDING_MODEL=BAAI/bge-m3                               # 默认值（1024 维）
```

> ⚠️ 没配 Key 也不会崩：它会**退回关键词检索**，并在横幅里说明原因。

v6 新增的配置项：

| 参数 | 默认 | 说明 |
|---|---|---|
| `LLM_RETRIEVAL_MODE` | `semantic` | `keyword` = 退回 v5 的字面匹配 |
| `LLM_MIN_SIMILARITY` | 0.5 | 相似度门槛，低于它不算命中 |
| `LLM_EMBEDDING_CACHE` | `agent-v6/embedding-cache.json` | 向量缓存文件 |
| `LLM_TEMPERATURE` | 0.3 | 采样温度。**v6 修正**：v1~v5 从没设过，模型行为飘忽 |

## 核心概念：三个新问题

### 问题一：向量从哪来？

远程服务（SiliconFlow 的 `BAAI/bge-m3`，1024 维）。

但代码里它被抽成了一个接口：

```python
class Embedder(Protocol):
    @property
    def model_id(self) -> str: ...
    def embed(self, texts: list[str]) -> list[list[float]]: ...
```

**理由和 v3 的 `Summarizer` 一模一样**：真实实现要联网、要花钱、
结果还不可复现 —— 测试里塞一个**确定性的替身**（词袋向量），
整条流水线就能离线测穿，一分钱不花。

### 问题二：算好的向量放哪？—— 必须存盘

> **embedding 是按 token 计费的。**
> 一个几百块的资料库，每次启动都重算一遍 = 每次启动都重新烧钱。

所以有一个磁盘缓存，**按「内容指纹」索引**：

```
块内容 ──sha256──→ 指纹 ──→ 向量
```

内容没变 → 指纹没变 → 缓存命中 → 不花钱。
内容变了 → 只有**变了的那一块**重算（不是整个库）。

这是 v4「目录指纹」的精确版：从「整个目录」精确到**每一块**。

实测（跨进程）：

```
第 1 次：调用 2 次 · 3 段 · 44 tokens · 0.9s      ← 算块 + 算查询
第 2 次：缓存命中 2 段（没花钱）· 调用 1 次 · 5 tokens  ← 只算查询词
```

另外两个容易忽略的细节：

- **缓存按模型分区**：换个向量模型，同一段文字的向量完全不同 ——
  混用就是一堆噪音。所以缓存里存了模型名，对不上就整份作废
- **查询词不进缓存**：用户每次问的都不一样，存进去只会把缓存撑大、
  命中率还极低。缓存是给「资料块」用的（反复要用、总量有限）

### 问题三：相似度多高才算「相关」？

**这是这一版唯一没法靠代码解决的问题。**

实测（bge-m3 + 这份资料）：

| 对比 | 余弦相似度 |
|---|---|
| 「性能优化…」↔「怎么让程序跑得更快」 | **0.65** ← 相关 |
| 「性能优化…」↔「番茄需要浇多少水」 | **0.36** ← 无关 |

所以设了 `LLM_MIN_SIMILARITY = 0.5`。但注意：

> **这个值只对「这个模型 + 这份资料」成立。**
> 不同向量模型的相似度分布完全不同 —— 有的模型里，
> 「相关」和「无关」都落在 0.7~0.9 之间。换模型就得重新校准。

没有门槛会怎样？**top_k 会把最不相关的也硬塞给你** —— 实测过：
「番茄需要浇多少水」在没门槛时照样返回 1 段（0.36）。

## 它会告诉你「为什么是 0 命中」

```
🔍 检索 怎么让程序跑得更快（向量） → 1 段命中（相似度 0.651 · 扫描 2 块 · 320.0 ms）
      perf.md:3（perf） · 相似度 0.651
```

没找到时，也说清楚是哪一种「没找到」：

```
🔍 检索 番茄需要浇多少水（向量） → 0 段命中（最高相似度 0.362 < 门槛 0.5 · …）
      ⚠ 资料里没有相关内容 —— 它接下来应该说「不知道」，而不是编一个〔盯一下〕
```

向量检索和关键词检索的「没找到」**原因完全不同**：

| | 没找到 = | 你该做什么 |
|---|---|---|
| 向量 | 相似度不够高 | 调门槛？还是资料里真的没有？ |
| 关键词 | 一个字都没对上 | 换个说法再试 |

`/knowledge` 会告诉你缓存和账本：

```
资料目录  .../agent-v6/notes
1 个文件 / 1 块 · 索引重建过 1 次
检索模式：semantic（模型 BAAI/bge-m3）
向量：已算 1 块（全库算过 1 次） · 缓存里 2 个
缓存状态：从磁盘读回 2 个向量
向量账本：缓存命中 2 段（没花钱） · 调用 1 次 · 1 段 · 5 tokens · 0.8s
```

## 常见问题

**Q：一定要配向量服务吗？我只想用 v5 的方式。**
不用配。`LLM_RETRIEVAL_MODE=keyword python main.py` —— 立马退回字面匹配。
（没配 Key 时它也会**自动**退回去，并在横幅里说明。）

**Q：`embedding-cache.json` 好大（2 个向量 45 KB）。**
正常 —— 1024 维的浮点数用 JSON 存就是这么占地方（每个向量约 22 KB）。
几百块也无所谓（十几 MB），**几千块就该换存储了**（这也是「规模」那堵墙）。

**Q：改了笔记之后，缓存会怎样？**
只重算改过的那一块 —— 靠的是「内容指纹」。
没变的块继续命中，一分钱不花。

**Q：它还是把不相关的东西找回来了，怎么办？**
调高 `LLM_MIN_SIMILARITY`（比如 0.6）。或者先跑实验 3 看看当前的门槛在哪。

**Q：为什么有时候它**不**去查笔记？**
因为「查不查」是模型自己决定的，不是一个 `if` 语句。

v1~v5 一直没设过 `temperature`（默默吃着 API 默认值 1.0），
系统提示词里也没提检索 —— 后果实测：同句「我想让程序跑得更快」问两次，
一次它去查了笔记、一次它凭自己的知识答了一大篇，**实验根本没法复现**。

v6 补了两刀：

1. 系统提示词加一条：**回答前先想「答案会不会在笔记库里」，有可能就先查**
2. `LLM_TEMPERATURE` 默认 **0.3** —— Agent 要的是稳定，不是文采

修完实测：该查的 6/6 都查了；不该查的（算数、问时间、闲聊）没有乱查。

**Q：`⚠ 向量失败，已降级` 是什么意思？**
向量服务调不通（断网 / 配额用完 / 模型名写错），它退回了关键词检索。
功能没丢，但「同义词又搜不到了」—— 日志里会留着这句话。

## 动手练习

1. **测量你资料上的相似度分布** —— 问几个「明显相关」和「明显无关」的问题，
   把 `/knowledge` 里的数字记下来，看看 0.5 这个门槛对你的资料合不合适
2. **把两种模式并排跑** —— 同一批问题，`keyword` 和 `semantic` 各来一遍，
   做一张你自己资料上的对照表
3. **给缓存加个上限** —— 现在它会一直长。试试超过多少条就淘汰最老的
4. **做一次真正的混合检索** —— 两个检索器都调，用 RRF 合并排名（这是下一版的正题）
5. **思考题**：为什么 `EmbeddingCache` 里要存 `model` 字段？
   如果不存、换模型后硬用旧向量，会发生什么？（提示：算出来的相似度还有意义吗）
